# Интеграции Ф13: Rocket Data (отзывы с карт) и справочник объектов

Требования M-CH-10, M-ORG-06; вопросы В-32, В-42 (`Контакт-центр/planning/04-открытые-вопросы.md`).

**Основание — описания заказчика (01.10.2026)**, взятые с действующей системы контакт-центра:
«Требования по интеграции с программным обеспечением контакт-центра» (обмен с Rocket Data) и Приложение 2
«Требования по интеграции с системой АСУ НПО ЭК ПО «Белоруснефть»» (справочник АЗС). Rocket Data подключается к
контакт-центру сама по этим правилам; авторизация и ограничения доступа — на стороне Rocket Data (решение заказчика).
До 01.10 интеграции были сделаны по контрактам-заглушкам (опрос API Rocket Data); они заменены.

Форматы внешних систем собраны в адаптерах — при изменении формата меняются только они:

| Интеграция          | Адаптер                                                                                         | Мок для проверок                            |
| ------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------- | ----- |
| Rocket Data         | `apps/connector-rocketdata/src/rocketdata-api.ts` (разбор отзыва, ответ, коды ошибок)           | `apps/mock-selfservice/src/rocketdata.ts`   |
| Справочник объектов | `packages/domain/src/objects-sync.ts`: `fetchObjectFeed` (загрузка), `parseObjectFeed` (разбор) | там же (`/objects/asu`, `/objects/feed.json | csv`) |

> **Безопасность стендов.** Реальных адресов Rocket Data и АСУ НПО ЭК нет ни в коде, ни в демо-данных, ни в тестах:
> проверки идут только против мока. Ответы операторов уходят, только если в канале задан адрес сервиса ответов
> (по умолчанию пусто — ответ получает статус «не доставлено»). Тестовый или демо-стенд не должен получать адрес
> сервиса ответов рабочей Rocket Data — иначе ответы операторов будут опубликованы клиентам на площадках.

## 1. Rocket Data

### 1.1 Отзыв: Rocket Data → контакт-центр

`POST https://<адрес КЦ>/rd/<id канала>` (адрес показывается в «Администрирование → Каналы», колонка «Адрес»; его
передают Rocket Data), тело — JSON в UTF-8, один отзыв:

| Поле          | Описание                                                            | Обязательно | Тип (ограничение) |
| ------------- | ------------------------------------------------------------------- | ----------- | ----------------- |
| `TicketMapId` | Уникальный номер отзыва (по нему уходит ответ)                      | да          | число или строка  |
| `DateReceipt` | Дата регистрации отзыва                                             | да          | дата              |
| `StationGuid` | Глобальный идентификатор объекта = `objguid` справочника АСУ НПО ЭК | да          | GUID              |
| `StationType` | Тип АЗС                                                             | да          | текст (16)        |
| `StationNum`  | Номер АЗС                                                           | да          | текст (120)       |
| `EmitentName` | Название предприятия                                                | да          | текст (120)       |
| `ClientName`  | Имя клиента                                                         | нет         | текст (70)        |
| `Message`     | Текст отзыва                                                        | да          | текст (3000)      |
| `Link`        | Ссылка на отзыв                                                     | да          | текст (3000)      |
| `Site`        | Источник отзыва (`yandex.ru`, …)                                    | да          | текст (100)       |

Ответ: **200** `{"result": "ok", "TicketMapId": "…"}` — отзыв принят (записан в поток `CC_INBOUND` и уже не
потеряется); **400** `{"error": "validation", "message": "…", "details": [{"field", "message"}]}` — ошибка формата
или нет обязательного поля; **404** — канал не найден или выключен; **503** — временная ошибка, запрос можно повторить.

Правила приёма (решения по умолчанию, где описание не уточняет):

- имена полей — без учёта регистра (в примере описания — и `Site`, и `SITE`); пример описания — не строгий JSON
  («типографские» кавычки, пропущенные запятые) — такие ошибки исправляются при разборе;
- `TicketMapId` описан как число, в примере — строка: принимаются оба;
- `DateReceipt` без часового пояса (`2016-11-23T10:08:05`) — время Минска; также ISO с поясом и `ДД.ММ.ГГГГ чч:мм`;
- ограничения длины из описания соблюдает отправитель; приём — с запасом (текст до 20 000 символов, ссылка до 4000),
  чтобы отзыв не терялся из-за длинной ссылки;
- оценки в описании нет — в карточке и отчёте отзыв «без оценки»; если Rocket Data начнёт передавать поле `Rating`
  (1–5), оно используется (низкая оценка — срочное обращение, настройка канала);
- **повтор** того же отзыва (тот же `TicketMapId` и текст) — 200 без дубля; изменённый текст с тем же номером —
  новое сообщение того же открытого обращения (если обращение закрыто — новое обращение).

Приём ведут оба экземпляра `connector-rocketdata` (маршрут Traefik `/rd/` → сервис коннектора); при обновлении
коннектора отзывы принимаются без перерыва (проверка `ops/test/reviews-under-rollout.mjs`).

### 1.2 Как отзыв становится обращением

- Канал «Отзыв» («Администрирование → Каналы», тип «Отзывы с карт (Rocket Data)»): очередь канала — очередь отзывов,
  настройка — адрес сервиса ответов.
- **Клиент** обращения — автор отзыва (у площадок нет устойчивого идентификатора автора — каждый отзыв свой клиент).
- **АЗС и предприятие**: `StationGuid` сравнивается с GUID объекта справочника (`external_ids.objguid`, без дефисов и
  регистра: в отзыве GUID с дефисами, в выгрузке АСУ — без), затем с кодом объекта. Найдено — объект и его
  предприятие (права: видят те, чья область включает предприятие). Не найдено — обращение без предприятия
  (видят те, кому разрешены неклассифицированные) и служебная подсказка оператору с реквизитами АЗС из отзыва
  (тип, номер, предприятие, GUID). В карточке оператора — площадка, ссылка, автор, АЗС из отзыва и объект справочника.
- Автоответы, приветствия, автозакрытие по молчанию и сообщение о передаче на 2-ю линию **на отзывы не отправляются**
  (ответ публичный), кроме правил автоответов, где канал «Отзыв» выбран явно.

### 1.3 Ответ на отзыв: контакт-центр → Rocket Data

`POST <адрес сервиса ответов канала>`, `Content-Type: application/json; charset=utf-8`:

```json
{ "Review_id": "100", "DateAnswer": "2016-11-23T10:08:05", "Text": "Спасибо за отзыв! …" }
```

`Review_id` — `TicketMapId` отзыва, `DateAnswer` — время отправки по Минску в формате описания. Дополнительно
передаётся заголовок `Idempotency-Key` (id сообщения) — Rocket Data может его не учитывать.

| Ответ сервиса                    | Статус сообщения у оператора                |
| -------------------------------- | ------------------------------------------- |
| 2xx                              | ✓ отправлено                                |
| 4xx (кроме 408/429)              | ⚠ не доставлено (без повторов)             |
| 408, 429, 5xx, сеть              | повторы с паузой до `OUTBOUND_MAX_ATTEMPTS` |
| адрес не задан, вложение, пустой | ⚠ не доставлено сразу                      |

Повторную отправку одного ответа исключает отметка «отправлено» коннектора (NATS KV). Выход в интернет — только к
сервису ответов, через прокси `ROCKETDATA_PROXY` (`infra/compose/.env`, передаётся коннектору как `HTTPS_PROXY` с
`NODE_USE_ENV_PROXY=1`). Входящие запросы Rocket Data приходят на внешний адрес КЦ через Traefik.

## 2. Справочник объектов: АСУ НПО ЭК (Приложение 2)

Источник — выгрузка всех АЗС: HTTP GET, JSON-массив станций (адрес — из Приложения 2, задаётся администратором в
«Администрирование → Синхронизация объектов», формат «АСУ НПО ЭК»; сервер КЦ к нему доступ имеет). Пока в
справочнике — только АЗС (решение заказчика 01.10). Используемые поля:

| Поле выгрузки                   | Объект справочника                                                                           |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| `objguid`                       | ключ сверки и код нового объекта; `external_ids.objguid` (заглавными, без дефисов)           |
| `name1`                         | название: «`name1`, `town`» (номера АЗС повторяются в разных областях); без `town` — `name1` |
| `mailaddress`                   | адрес                                                                                        |
| `status`                        | «действующий» (или пусто) — активен; любой другой — деактивируется                           |
| `unitcode`                      | предприятие: исключение из настройки, иначе предприятие всей выгрузки (по умолчанию «ПОН»)   |
| `azsnum`, `complex`, `unitcode` | сохраняются во внешних идентификаторах (`external_ids`)                                      |

Остальные поля (координаты, топливо, цены, сервисы, акции, фото) не используются. Ответ JSON — массив или объект с
массивом внутри; кодировка — из `Content-Type` (`windows-1251` и т.п.), по умолчанию UTF-8.

**Предприятия.** Справочник предприятий ведётся вручную: ПОН (все предприятия нефтепродуктообеспечения из выгрузки
объединены в одно, решение заказчика 01.10), Управление цифровизации, Управление «Маланка», Центральный аппарат,
Мингорисполком. Все АЗС выгрузки относятся к предприятию из настройки «Предприятие объектов выгрузки» (по умолчанию
код `ПОН`); при необходимости отдельные `unitcode` направляются в другие предприятия («Исключения», строки
`20=КОД`). Нет такого предприятия в справочнике — запуск с ошибкой, справочник не меняется.

Общие форматы для других источников и ручной загрузки — **JSON** (массив объектов или `{"items": [...]}`: `code`,
`name`, `address`, `enterprise_code`, `external_ids`, `is_active`; принимаются и `enterpriseCode`, `externalIds`,
`isActive`) и **CSV** (колонки ручного импорта `code;name;address;enterprise_code`, а также `rocketdata`,
`ext_<ключ>` — внешние идентификаторы, например `ext_objguid`, и `is_active`).

### 2.1 Правила сверки (одной транзакцией)

- ключ объекта — GUID (`external_ids.objguid`), если он есть, иначе код; объект, заведённый вручную или импортом с
  тем же GUID (поле «GUID объекта» в карточке) или кодом, переходит под синхронизацию без дубля — его код сохраняется;
- нет в справочнике — добавляется (`source = sync`); есть — обновляются название, адрес, предприятие, внешние
  идентификаторы (ключи из выгрузки перекрывают, прочие сохраняются);
- статус не «действующий» или объекта нет в выгрузке — деактивируется (только синхронизируемые; заведённые вручную
  не трогаются); вернулся — снова активен;
- строка с ошибкой (нет GUID/названия, неизвестное предприятие, повтор) пропускается и попадает в «замечания»;
  такой объект не деактивируется;
- **защита от ошибочной выгрузки**: пустая выгрузка или деактивация большей доли синхронизируемых объектов, чем
  задано (по умолчанию 30 %), — запуск с ошибкой, справочник не меняется;
- синхронизируемые поля вручную не правятся (карточка объекта, активность, импорт CSV) — ответ 400 с пояснением.

Плановый запуск — worker (pg-boss раз в минуту проверяет время дня; после ошибки — повтор не чаще раза в час до конца
суток). Там же — «Проверить (без изменений)», «Синхронизировать сейчас» и журнал запусков с перечнем изменений.
