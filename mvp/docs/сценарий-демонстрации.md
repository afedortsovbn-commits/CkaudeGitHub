# Сценарий демонстрации MVP

Показ всех сквозных демо-сценариев (01-требования, раздел 5) на демо-стенде. Каждый сценарий также проходится
автоматически — ссылка на тест в последнем столбце таблицы в конце документа; все они выполняются в CI при каждом
изменении.

## Подготовка (≈ 10 минут)

```bash
cd mvp
ops/demo.sh up        # сборка образов (если нет) и запуск стека с демо-данными и заглушками внешних систем
ops/demo.sh check     # (по желанию) автоматический прогон демо-сценариев в браузере
ops/demo.sh reset     # вернуть стенд к чистым демо-данным после показа
```

Нужны 3–4 окна браузера (Chrome / Яндекс Браузер / Edge; удобно — разные профили или окна инкогнито):
**администратор** `admin@cc.local` / `Admin12345!`, **оператор** `operator1@demo.local`, **ответственный**
`resp1@demo.local`, **супервизор** `supervisor@demo.local` (пароль сотрудников — `Demo12345!`). Один раз откройте
`https://localhost:8443` и примите сертификат (софтфон), разрешите микрофон.

Демо-данные: предприятия «Север» и «Юг», подразделения, темы АЗС/ЭЗС (в т.ч. особо важная «Жалобы на персонал АЗС»),
матрица ответственности, очереди «Общая» и «B2B», IVR «сеть АЗС» (номер 2000), бот веб-чата,
шаблоны, база знаний, интеграция с «системой самообслуживания» (мок), LLM (мок, выключен), подписка «Демо:
анализатор» (выключена).

## 1. Звонок

1. Оператор: статус **«Готов»**.
2. Клиент: `https://localhost/demo-call`, номер **2000**, имя и телефон → «Позвонить». Звучит объявление о сбое и
   приветствие; клавиатура: **1** (бонусная программа) → **1** (баланс) — система запрашивает баланс во «внешней
   системе» и озвучивает сумму; **0** — оператор.
3. Оператор отвечает (кнопка или гарнитура): карточка открылась, в переписке — путь по IVR и тема «Баланс бонусов»,
   во вкладке «Клиент» — история и данные из внешней системы. **Удержание** → снять, **Перевести** оператору
   `operator2@demo.local`, завершить.
4. Клиент остаётся на линии и ставит оценку **4**. Вкладка «Звонки» — путь по IVR, оценка, **запись разговора**.

## 2. Чат на сайте

1. Клиент: `https://localhost/widget/demo.html?key=demo-webchat-bot` — согласие на обработку ПДн, «Здравствуйте».
   Автоответ и бот: кнопки меню → бот просит телефон → перевод на оператора.
2. Оператор берёт чат: в панели подсказок — шаблон и статья базы знаний по вопросу клиента → **«Вставить»** → Enter.
3. Тема «Сайт», результат «Решено на 1-й линии» → «Завершить обращение». Клиент в виджете ставит оценку.

## 3. Telegram и email — единая история

1. Администратор: «Каналы» → добавить Telegram-бота (адрес Bot API `http://mock-telegram:3000`, любой токен вида
   `123:abc`) и почтовый ящик (IMAP/SMTP `mail`, порты 3143/3025 без TLS) — каналы подключаются без перезапуска.
2. Клиент пишет в виджет, указав в форме телефон и email; затем звонит с того же номера (`/demo-call`, номер 1000);
   затем пишет письмо с того же адреса (SMTP `127.0.0.1:3025`) — у оператора это **один клиент**: «Клиент» →
   «История обращений» — чат, звонок и письмо.
3. Сообщение в Telegram (`curl` из вывода `ops/demo.sh up`) попадает в ту же очередь «Общая».

## 4. Вторая линия

1. Администратор: «Предприятия» — новое предприятие; «Подразделения» — одно подразделение в двух предприятиях;
   «Матрица ответственности» — ответственный и куратор на подтему; «Темы и поля» — срок подтемы 10 дней
   («Настройки» — глобальный 15).
2. Оператор по обращению: результат **«Передать на 2-ю линию»** → предприятие и подразделение → ответственный,
   куратор и срок подставились → заменить ответственного → «Передать». Письмо «Важно!» назначенным — в GreenMail.
3. Ответственный (`resp1@demo.local`): «Кабинет 2-й линии» — тикет выделен («Я ответственный»); переадресовать
   сменой подразделения; новый ответственный закрывает: способ ответа «письмо на бумаге», суть, скан.
4. Оператор: вкладка «На согласовании» → **«Вернуть на доработку»** («нет подписи на письме») → ответственный
   прикладывает документ и закрывает повторно → оператор **«Принять»** — тикет и обращение закрыты.
5. Супервизор: «Контроль 2-й линии» — все согласования; «Отчёты» → «2-я линия» — возврат и сроки. Ежедневные письма
   «осталось N дней / просрочено» проверяются автотестом с подменой времени.

## 5. Настройка без программирования

Администратор, без перезапуска: «Сценарии IVR» → изменить пункт меню → «Опубликовать» (идущие звонки доигрывают
прежнюю версию); «Шаблоны ответов» — новый шаблон `/код`; «Автоответы» — правило на ключевое слово; «Темы и поля» —
тема с обязательным полем; «Каналы» — новый Telegram-бот. Всё сразу работает у оператора и клиента.

## 6. Обновление без простоя

Во время звонков и чатов: `ops/build-images.sh v2 && MEDIA_TAG=v2 ops/release.sh v2` — поэтапная замена всех
прикладных сервисов и одного медиаузла; разговоры не обрываются, сообщения не теряются, у операторов — баннер
«Доступна новая версия», интерфейс обновляется сам вне звонка. Под нагрузкой (10 операторов, 30 вызовов, 100 чатов)
это подтверждает автотест `ops/zero-downtime-test` (регламент — [регламент-обновления.md](регламент-обновления.md)).

## 7. Отчёты

Супервизор: «Супервизор» — очереди, операторы, SL за сегодня с подсветкой по порогам («Настройки»). «Отчёты» —
обращения, SL и пропущенные (правила расчёта SL — «Настройки», раздел «Панель супервизора и отчёты»), ASA/AHT,
первый ответ, операторы, CSAT, 2-я линия, реестр просроченных → **«Скачать CSV»** (открывается в Excel).

## 8. Интеграции

1. Администратор: «Webhooks» → включить «Демо: анализатор». Оператор закрывает чат — внешняя система получает
   webhook и через API записывает результат анализа в поля и заметку обращения (видно в карточке).
2. «Подсказки: провайдеры» → включить «LLM (локальная модель, демо)» — у оператора кнопка «Черновик (ИИ)» даёт
   черновик ответа.

## 9. Права и важность

1. Два чата: один классифицировать предприятием «Юг», другой — «Север».
2. Супервизор `supervisor@demo.local` (область — «Север») не видит обращение «Юга» ни в списках, ни в поиске, ни в
   отчётах (фильтр по «Югу» — пусто). Обращение без предприятия и темы он тоже не видит, пока администратор не даст
   право «видит неклассифицированные обращения» («Сотрудники» → «Области видимости»).
3. Обращение по особо важной подтеме помечено автоматически и находится быстрым фильтром «Особо важные».

## 10. Отзывы с карт

Интеграция с Rocket Data (Ф13) на демо-стенде работает с моком API (описание API заказчика ожидается, В-32).

1. «Клиент пишет отзыв»: `curl -X POST http://127.0.0.1:8082/rocketdata/demo/__test/reviews -H 'content-type:
application/json' -d '{"location_id":"rd-azs-1","platform":"yandex","rating":1,"text":"Грубый кассир",
"author_name":"Иван"}'` — в течение 10 с отзыв появляется в очереди «Отзывы» у операторов: канал «Отзыв», ★☆☆☆☆,
   «срочное».
2. Оператор берёт обращение: над перепиской — площадка, оценка, объект «АЗС №1», автор, ссылка на отзыв; предприятие
   «Север» указано по объекту автоматически.
3. Ответ оператора (публичный, только текст) уходит в Rocket Data: у сообщения «✓ отправлено»; в моке —
   `GET http://127.0.0.1:8082/rocketdata/demo/__test/answers`. Дальше — как обычное обращение: тема, закрытие или
   передача на 2-ю линию.
4. Повторная загрузка отзыва дублей не создаёт; изменённый автором отзыв — новое сообщение того же обращения.
5. «Отчёты» → «Отзывы с карт: оценки и доля отвеченных» — по объектам, предприятиям, оценкам, площадкам, дням.
6. «Синхронизация объектов» → «Проверить (без изменений)» → «Синхронизировать сейчас»: из выгрузки мока добавляется
   «АЗС №7», демо-объекты переходят под синхронизацию; журнал запусков с перечнем изменений. В «Объектах» у
   синхронизируемых — источник «синхронизация», их название и предприятие вручную не меняются.

## Дополнительно (Ф12)

- **Вход с кодом**: «Профиль» → «Включить вход с кодом» → QR-код в приложении-аутентификаторе → вход с кодом;
  «Настройки» → обязательно для администраторов.
- **Персональные данные**: реестр согласий с версией текста; обезличивание клиента по заявлению.
- **Резервная копия**: `ops/backup.sh` во время работы → `ops/restore.sh --verify <каталог>`.
