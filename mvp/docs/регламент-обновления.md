# Регламент обновления контакт-центра без остановки обработки обращений

Главное требование заказчика: обновление не прерывает работу (M-UPD-01..06, 02-архитектура, раздел 6).
Во время обновления не обрывается ни один установленный разговор, не теряется ни одно сообщение, операторы
не выходят из системы; переподключение WebSocket — до 5 с, пауза в IVR — до 3 с. Компоненты, которым нужно
окно, перечислены ниже (класс C); окно — не более 60 с и без обрыва идущих разговоров.

Документ — для администратора, выполняющего выпуск, и для разработчика, готовящего релиз.

## 1. Классы компонентов и процедуры

| Компонент                                                              | Класс           | Процедура                                                                  | Эффект для пользователей                                                                                                                                                                                        |
| ---------------------------------------------------------------------- | --------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| api, worker, router, realtime, коннекторы, call-control, web (статика) | A — незаметно   | `ops/release.sh <тег>` (поэтапная замена экземпляров, `ops/rollout.sh`)    | Нет. WebSocket переподключается ≤ 5 с и догружает пропущенное; в IVR возможна пауза ≤ 3 с (фраза повторяется)                                                                                                   |
| NATS (кластер ×3)                                                      | A — незаметно   | `ops/update-media.sh nats-1 nats-2 nats-3` — по одному, lame duck mode     | Нет: клиенты переходят на другие узлы, потоки JetStream (R3) работают на двух узлах                                                                                                                             |
| Asterisk ×2                                                            | B — осушение    | `MEDIA_TAG=<тег> ops/update-media.sh` (или `MEDIA_TAG` у `ops/release.sh`) | Нет. Новые вызовы идут на другой узел, идущие доживают; обновление занимает время осушения (обычно минуты, максимум `MAX_DRAIN`)                                                                                |
| coturn ×2                                                              | B — осушение    | `ops/update-media.sh coturn-1 coturn-2`                                    | Нет. Экземпляр исключается из ICE-серверов, которые api выдаёт перед каждым вызовом; ждём окончания его TURN-сессий                                                                                             |
| Kamailio (1 экз.)                                                      | C — окно ≤ 60 с | `KAMAILIO_TAG=<тег> ops/update-media.sh kamailio` в окно низкой нагрузки   | Разговоры продолжаются и корректно завершаются (проверено автотестом). Около 7 с не принимаются новые вызовы, софтфоны переподключают WSS и перерегистрируются; удержание/перевод в эти секунды могут не пройти |
| Traefik (1 экз.)                                                       | C — окно ≤ 60 с | `docker compose up -d --no-deps --force-recreate traefik`                  | Разговоры и SIP-регистрации не затрагиваются (SIP/WSS и медиа идут мимо Traefik). WebSocket переподключаются, запросы повторяются клиентом; Telegram повторяет webhook сам                                      |
| PostgreSQL (минорная версия)                                           | C — секунды     | `docker compose up -d --no-deps --force-recreate postgres`                 | Разговоры не затрагиваются; входящие сообщения ждут в JetStream; сервисы повторяют запросы. Мажорная версия — через логическую репликацию, отдельное окно                                                       |
| SeaweedFS (S3, 1 экз.)                                                 | C — секунды     | `docker compose up -d --no-deps --force-recreate s3`                       | Записи разговоров выгружаются с повторами; загрузка вложений клиентом повторяется                                                                                                                               |
| Конфигурация (IVR, очереди, шаблоны, каналы, настройки, фиче-флаги)    | —               | Администрирование в интерфейсе                                             | Применяется без перезапуска (`config.changed`); начатые сессии IVR/бота доигрывают свою версию                                                                                                                  |

**Нельзя** выполнять общий `docker compose up -d` на работающем стеке после обновления файлов развёртывания:
compose пересоздаст одновременно все экземпляры, у которых изменились образ или параметры (в том числе все три
узла NATS или оба узла Asterisk). Каждый компонент обновляется своей командой из таблицы.

## 2. Выпуск релиза прикладных сервисов

### 2.1 Подготовка (разработчик)

1. PR зелёный в CI: проверки кода, линтер миграций, **совместимость контрактов** с предыдущим релизом, e2e,
   проверки под нагрузкой, автотест `ops/zero-downtime-test` (раздел 5).
2. Правила совместимости версий N и N+1 (они работают одновременно во время замены):
   - **миграции** — только `NNNN_expand_*.sql`: новые таблицы и столбцы (nullable или с DEFAULT), новые индексы;
     удаление и переименование — только `NNNN_contract_*.sql` **в следующем релизе** с пометкой
     `-- contract-of: NNNN` (какие expand-миграции завершает; линтер проверяет, что они уже выпущены).
     Индекс на большой таблице — `CREATE INDEX CONCURRENTLY IF NOT EXISTS` в файле с директивой
     `-- cc:no-transaction` (операторы выполняются по одному вне транзакции, файл должен быть повторяемым).
     Выпущенные миграции не изменяются (линтер сверяет с базовой ревизией);
   - **контракты** (`packages/contracts`: события, команды шины; OpenAPI публичного API) — только аддитивно: новые
     необязательные поля, новые типы и операции. Проверка: `pnpm compat:check --base <предыдущий релиз>`.
     Новые значения перечислений — предупреждение: старые потребители должны обрабатывать неизвестное значение;
     несовместимое изменение — новый тип события `….v2` и период двойной публикации; осознанное исключение —
     запись в `ops/compat/allow.json` с причиной;
   - **поведение** — новая функциональность, которую старые экземпляры не понимают, включается фиче-флагом после
     обновления всех экземпляров (`FEATURE_FLAGS` у `ops/release.sh`).
3. Сборка образов с тегом релиза: `ops/build-images.sh <тег>` (в закрытом контуре — из офлайн-комплекта,
   `ops/mirror/`). Образ web переносит в себя ресурсы работающей (предыдущей) версии — вкладки старой версии не
   получают 404 при подгрузке модулей. Если сборка идёт не на сервере со стеком — `PREV_WEB_IMAGE=cc/web:<пред.тег>`.
4. Git-тег релиза `release-<тег>` — база для проверки совместимости следующего релиза.

### 2.2 Выпуск (администратор)

```bash
cd mvp
ops/release.sh v12                                  # прикладные сервисы
FEATURE_FLAGS=reports.new_widget ops/release.sh v12 # с включением фиче-флагов после обновления
MEDIA_TAG=v12 ops/release.sh v12                    # вместе с медиа (Asterisk осушением)
```

Шаги `ops/release.sh`:

1. **Предпроверки**: есть образы всех сервисов с этим тегом; все экземпляры стека здоровы; линтер миграций и
   совместимость контрактов с `COMPAT_BASE` (по умолчанию — последний тег `release-*`). На сервере без git —
   `SKIP_COMPAT=1` (проверка уже выполнена в CI).
2. **Миграции expand** образом новой версии, старые экземпляры продолжают работать. Каждая операция ждёт
   блокировку не дольше `MIGRATION_LOCK_TIMEOUT_MS` (5000) и повторяется — миграция не выстраивает очередь
   запросов работающих сервисов за собой.
3. **Поэтапная замена** в порядке: коннекторы → worker → router → realtime → api → call-control → web. Для
   каждого сервиса поднимаются новые экземпляры рядом со старыми, после их готовности старые корректно
   останавливаются (readiness → 503, пауза, завершение текущих запросов и задач, закрытие соединений с кодом
   1012). Активный call-control узла передаёт управление резервному, сценарии IVR продолжаются с сохранённого
   шага. При ошибке выпуск останавливается: работающие экземпляры не трогаются, отчёт подсказывает откат.
4. **`app.version`**: открытые вкладки операторов показывают «Доступна новая версия интерфейса» и обновляются
   сами, когда нет звонка и неотправленного ответа (флаг `web.auto_reload`, M-OP-11); во время звонка кнопка
   «Обновить» недоступна, страница не перезагружается.
5. **Фиче-флаги** из `FEATURE_FLAGS`.
6. **Медиа** (если задан `MEDIA_TAG`; узлы — `MEDIA_NODES`).
7. **Журнал выпусков** (`release_log`, «Администрирование → Настройки» / `GET /api/v1/admin/releases`) и файл
   отчёта `out/releases/release-<тег>-<время>.json` (длительность каждого шага). Тег записывается в
   `infra/compose/.env` (`API_TAG`), чтобы последующие команды compose не вернули старые образы.

### 2.3 Откат

```bash
ops/release.sh --rollback v11
```

Повторная поэтапная замена на образы предыдущего релиза, без миграций: схема после expand совместима с N-1.
Фиче-флаги, включённые выпуском, при откате выключите заранее (Администрирование или
`docker compose run --rm --no-deps migrate node dist/cli/release-ops.js flags disable <ключи>`).

### 2.4 Миграции contract

Только в следующем релизе после того, как все экземпляры работают на версии, не использующей удаляемое. Тот же
`ops/release.sh`: contract-миграция выполняется на шаге 2 — к этому моменту старый код удаляемое уже не читает.

## 3. Медиа: осушение узлов (класс B)

```bash
MEDIA_TAG=v12 ops/update-media.sh                    # asterisk-1, затем asterisk-2
ops/update-media.sh coturn-1 coturn-2                # TURN-серверы
MAX_DRAIN=3600 ops/update-media.sh asterisk-2        # дольше ждать окончания разговоров
```

- Asterisk: Kamailio переводит узел в «disabled» — новые вызовы идут на другой узел; скрипт ждёт 0 каналов
  на узле, пересоздаёт его, проверяет готовность и возвращает в работу. Звонки операторам из осушаемого узла
  продолжают поступать.
- coturn: экземпляр вносится в `telephony.turn_disabled` (его больше не выдают в ICE-серверах перед вызовом);
  скрипт ждёт 0 TURN-сессий по метрике `turn_total_allocations`, пересоздаёт, возвращает в список. Вручную —
  «Настройки» → `telephony.turn_disabled` или `release-ops.js turn disable coturn-1`.
- Если за `MAX_DRAIN` (по умолчанию 1800 с) разговоры не закончились — **разговоры не обрываются**: в терминале
  скрипт спрашивает, ждать ли ещё, вернуть узел в работу без обновления или выйти, оставив узел выключенным
  (повторный запуск продолжит). Без терминала — `DRAIN_DECISION=wait|skip|exit` (по умолчанию выход, код 2).
- Отчёт: `out/releases/media-<время>.json` — по каждому узлу число сессий в начале, время осушения и обновления.

## 4. Окна (класс C)

Выполняются в период низкой нагрузки, по одному компоненту.

**Kamailio** — `KAMAILIO_TAG=<тег> ops/update-media.sh kamailio`. Окно ≈ 7 с (время старта контейнера):
новые вызовы и регистрации в эти секунды не принимаются, софтфоны переподключают WSS с задержкой 2–10 с и
перерегистрируются. Идущие разговоры продолжаются (медиа идёт мимо Kamailio) и корректно завершаются в обе
стороны: в Record-Route — имя (`SIP_ADVERTISE`), а не IP контейнера, а запросы внутри диалога к браузеру
находят текущее соединение софтфона по GRUU (регистрация с `+sip.instance`). На сервере с внешним транком
`SIP_ADVERTISE` — адрес, по которому транк достигает Kamailio. Проверка: `node ops/test/kamailio-restart.mjs`.

**Traefik**, **PostgreSQL (минорная)**, **SeaweedFS** — пересоздание одной командой из таблицы раздела 1; сервисы
повторяют запросы, сообщения ждут в JetStream. После — проверить `docker compose ps` (все healthy).

**Этого релиза (Ф11) касается**: изменились параметры coturn (метрики) и Kamailio (`SIP_ADVERTISE`, обработка
GRUU) — после `ops/release.sh` выполнить `ops/update-media.sh coturn-1 coturn-2`, затем в окно —
`ops/update-media.sh kamailio`.

## 5. Автотест «обновление под нагрузкой»

```bash
ops/build-images.sh v1 && <стек v1 с SEED_DEMO=true, COMPOSE_PROFILES=test>
EXTRA_MIGRATIONS_DIR=ops/zero-downtime-test/probe SKIP_MEDIA=1 ops/build-images.sh v2
MEDIA_TAG=v2 node ops/zero-downtime-test/run.mjs v2
```

Нагрузка (M-NFR-05): 10 операторов в браузерах (Playwright, софтфоны зарегистрированы), 30 одновременных
вызовов (SIPp → Kamailio → Asterisk, клиенты в очереди с музыкой), 100 одновременных чатов (20 виджет + 80
Telegram через мок). Во время нагрузки — `ops/release.sh v2` (тестовая миграция на «горячей» таблице
сообщений, замена всех прикладных сервисов) и осушение Asterisk ×2 и coturn ×2.

Критерии (02, 6.8): 0 оборванных разговоров (SIPp и журнал вызовов: все завершены клиентом), 0 потерянных и
0 дублированных сообщений (сверка отправленного с сохранённым в БД), 0 разлогиненных операторов (вкладки в
системе, софтфоны зарегистрированы), p99 доставки сообщения клиента в канал оператора во время обновления < 5 с. Отчёт —
`out/zero-downtime-report.json`. В CI автотест выпускает версию PR поверх версии `main` (реальный переход N → N+1).

## 6. Чек-лист выпуска

- [ ] CI PR зелёный (включая совместимость контрактов и автотест под нагрузкой).
- [ ] Образы собраны с тегом релиза; офлайн-комплект обновлён (если сервер без интернета).
- [ ] `docker compose ps` — все healthy; нет незавершённого выпуска в журнале.
- [ ] `ops/release.sh <тег>` — код 0; отчёт сохранён.
- [ ] Медиа, если менялись: `ops/update-media.sh …`; Kamailio и другие компоненты класса C — в окно.
- [ ] Фиче-флаги новой функциональности включены (после обновления всех экземпляров).
- [ ] Git-тег `release-<тег>` поставлен.
- [ ] Contract-миграции, отложенные с прошлого релиза, — в этом выпуске (если есть).
