# Журнал фаз MVP

## Ф4. Коннекторы Telegram и email, фреймворк каналов — выполнена (28.09.2026)

**Сделано**

- Миграция `0005`: у `channel` — состояние подключения, которое пишет коннектор (`status`/`status_detail`/
  `status_at`: подключён/ошибка/выключен); таблица `channel_log` — журнал обмена канала (приём, отправка,
  служебные события; без содержимого сообщений — ПДн; хранится 30 дней); у `message` — статус доставки во
  внешний канал (`delivery_status`: pending → sent | failed, `delivery_error`); у `conversation` —
  `channel_meta` (для email: тема, Message-ID последнего письма клиента, References).
- **Контракт коннектора** (`packages/contracts/src/channels.ts`): входящее — прежний `InboundMessage` в поток
  `CC_INBOUND` (Ф2); исходящее — `OutboundMessage` (`cc.outbound.<канал>`), статус доставки — `DeliveryStatus`
  (`cc.delivery.<канал>`), оба — в новом потоке JetStream `CC_OUTBOUND` (R3); схемы настроек канала
  `TelegramChannelConfigSchema`/`EmailChannelConfigSchema` (zod) — по ним api проверяет форму админки, а
  коннектор — запись из БД.
- **Исходящие** (`packages/domain`): ответ оператора в канал Telegram/email в той же транзакции, что и само
  сообщение, получает `delivery_status = pending` и команду в outbox (`enqueueCommand`, идемпотентный ключ —
  id сообщения) → OutboxRelay → `CC_OUTBOUND` → коннектор → `DeliveryStatus` → **worker** (новый
  `DeliveryProcessor`, durable-потребитель) → `applyDeliveryStatus` (идемпотентно: доставленное не
  откатывается запоздавшим/повторным статусом) → событие `conversation.message_status` → оператор видит
  «отправляется… / ✓ отправлено / ⚠ не доставлено: причина». Внутренние заметки и служебные сообщения во
  внешний канал не уходят; нет адреса клиента в этом канале — сразу «не доставлено».
- **`packages/connector-kit`** — основа коннекторов: реестр экземпляров канала (`ChannelRegistry`: активные
  каналы своего типа из БД, расшифровка секретов, проверка схемой, перечитка по `config.changed` и страховочно
  раз в 30 с — добавление/изменение/выключение канала без перезапуска; некорректная конфигурация — статус
  «ошибка» у канала, а не падение коннектора); доставка исходящих (`OutboundWorker`: общий durable-потребитель
  на все экземпляры, повторы с экспоненциальной паузой до `OUTBOUND_MAX_ATTEMPTS`, `PermanentError` — сразу
  «не доставлено», защита от повторной отправки — отметка в NATS KV `cc_outbound_sent` после успешной
  отправки); `publishInbound`; сохранение вложений в S3 (запрещённые расширения отбрасываются, как в Ф2);
  журнал и статус канала.
- **`packages/service-kit`**: `KvLease` — аренда в NATS KV (CAS по ревизии, TTL 45 с, освобождение при
  корректной остановке); `sealSecret`/`openSecret` — шифрование секретов каналов в БД (AES-256-GCM, ключ из
  `SECRETS_KEY`); поток `OUTBOUND_STREAM`; пинги NATS в журнал — на уровне debug.
- **connector-telegram** (новый сервис, 2 экземпляра): каждый бот — экземпляр канала. Режим **опрос**
  (long polling, по умолчанию; ведёт владелец аренды `tg.<id канала>`, смещение — в NATS KV `cc_tg_offsets`)
  или **webhook** (`POST /tg/<id канала>` через Traefik, принимают оба экземпляра, проверка
  `X-Telegram-Bot-Api-Secret-Token` — секрет генерируется api автоматически; `setWebhook` делает владелец
  аренды). Личные чаты: текст, фото (самое крупное), документы с подписью; `/start` пропускается.
  Обновление подтверждается Telegram (200 OK / сдвиг смещения) только после записи в `CC_INBOUND`.
  Ответы: текст и документы; 400/403 от Bot API (бот заблокирован, чат не найден) — без повторов.
- **connector-email** (новый сервис, 2 экземпляра): каждый ящик — экземпляр канала; приём по IMAP (IDLE +
  страховочная проверка раз в 15 с) ведёт владелец аренды `mail.<id канала>`, последний UID — в NATS KV
  `cc_mail_state` (при первом подключении берутся только непрочитанные, история ящика не импортируется);
  письмо помечается прочитанным после записи в `CC_INBOUND`. Разбор — mailparser: HTML → текст, отсечение
  цитаты предыдущей переписки («… написал(а):», «On … wrote:», хвост «> …»), вложения (кроме встроенных
  картинок), автоответы/рассылки (`Auto-Submitted`, `Precedence`, `X-Autoreply`) не создают обращений (иначе
  автоответчики зацикливаются с ответами операторов), письма от собственного адреса ящика пропускаются.
  **Цепочки**: ответ клиента по `In-Reply-To`/`References` попадает в то обращение, к письмам которого
  относится (даже с другого адреса), пока оно не закрыто; ответ оператора уходит по SMTP с темой `Re: <тема
первого письма>`, `In-Reply-To`/`References` и детерминированным `Message-ID` (`<id сообщения@домен ящика>`),
  который после доставки становится `external_id` сообщения — на него ссылаются следующие письма клиента.
- **api**: справочник каналов проверяет настройки по типу канала (веб-чат/приложение — как в Ф2, Telegram,
  email), секреты (`bot_token`, `webhook_secret`, `imap_password`, `smtp_password`) шифруются при записи и
  маскируются (`********`) в ответах и **в журнале аудита**; пришедшая обратно маска — «не менять».
  `GET /api/v1/channels/:id/log` — состояние и журнал обмена канала (право `admin.directories`).
- **web**: «Каналы» — формы для Telegram-бота (токен, режим, адрес Bot API) и почтового ящика (IMAP/SMTP), поля
  зависят от типа канала; колонка «Подключение» и окно «Журнал» канала; в рабочем месте оператора — статус
  доставки ответа. Исправлено попутно: изменение канала «Чат в приложении» через форму затирало `app_secret`
  (форма не содержала этого поля и отправляла config целиком).
- **Моки** (профиль compose `test`, в поставку не входят): `apps/mock-telegram` — мок Bot API
  (getUpdates/webhook с повторами, sendMessage/sendDocument, файлы) и тестовые методы «клиент пишет боту» /
  «что отправил бот»; GreenMail (SMTP 3025, IMAP 3143, без авторизации).
- `infra/compose`: `connector-telegram` ×2 (сервис Traefik — только порт и `/readyz` в метках, маршрут `/tg/`
  — в `infra/traefik/dynamic.yml`), `connector-email` ×2, `SECRETS_KEY`/`PUBLIC_BASE_URL`; `ops/build-images.sh`
  собирает коннекторы по умолчанию. CI: профиль `test`, e2e Ф4, новый шаг
  `ops/test/connectors-under-rollout.mjs`.

**Решения и находки**

- **Коннекторы обращаются к БД** (отступление от схемы 02, где коннектор — только NATS): реестр каналов
  читается из таблицы `channel`, коннектор сам пишет статус/журнал канала и метаданные вложений (`attachment`,
  как api в Ф2). Альтернатива — отдавать реестр через api и писать журнал событиями — давала бы ещё один
  контракт и зависимость коннектора от доступности api без выигрыша для обновления без остановки (схема БД
  меняется только expand). Сообщения и обращения коннекторы по-прежнему не трогают — это делает только
  worker/api через `packages/domain`.
- **Свой тонкий клиент Telegram Bot API вместо grammY** (отступление от 02, раздел «Технологии»): нужны 7
  методов, а владение циклом long polling (аренда, смещение в KV, отмена при остановке) и webhook-обработчиком
  на общем http-сервере сервиса у grammY пришлось бы обходить. Меньше зависимостей для офлайн-комплекта.
- **Режим бота задаётся явно**, а не «webhook с автоматическим фолбэком на опрос»: в закрытом контуре
  входящего доступа из интернета обычно нет, а при webhook адрес должен быть публичным https — такой выбор
  делает администратор. По умолчанию — опрос.
- **Защита от повторной отправки ответа** — отметка в NATS KV после успешной отправки + уникальный
  `Nats-Msg-Id` статуса. Окно дубля остаётся только при аварийном падении процесса между отправкой во внешний
  канал и отметкой (у Telegram и SMTP нет ключа идемпотентности); при корректной остановке текущая отправка
  завершается и подтверждается — проверено тестом обновления. Таймауты SMTP (15/15/30 с) меньше `ack_wait`
  потока (60 с), иначе зависшее соединение приводило бы к повторной доставке команды другому экземпляру.
- **Порядок исходящих между экземплярами** не гарантируется строго: два ответа оператора подряд в один чат
  могут уйти в обратном порядке, если их заберут разные экземпляры коннектора (в тесте обновления не
  наблюдалось; для email порядок не важен, для Telegram — редкая перестановка соседних сообщений).
- **Статус «Подключён» в режиме опроса** ставился только после первого long-poll (до 20 с без сообщений) —
  найдено e2e; теперь сразу после успешной проверки токена.
- **Двойная лицензия `@zone-eu/mailsplit`** (зависимость mailparser): `MIT OR EUPL-1.1+` — используется на
  условиях MIT, добавлена в список допустимых в `ops/licenses/check.mjs`.
- `PUBLIC_BASE_URL=''` из compose ломал запуск (пустая строка — не URL): пустое значение трактуется как
  «не задано».

**Известные ограничения**

- Размер входящих вложений коннекторами не ограничивается (у Telegram Bot API — не больше 20 МБ на файл,
  у почты — лимит почтового сервера); письмо целиком читается в память. Для MVP приемлемо; лимит и пометку
  «вложение слишком большое» — при необходимости.
- Telegram: только личные чаты; стикеры, голосовые, видео, геолокация не принимаются (пропускаются без
  создания сообщения). Исходящие — текст и файлы как документы (без альбомов/форматирования).
- Email: ответы — только текстом (`text/plain`), без HTML-шаблона и подписи; тема ответа — от первого письма
  обращения. Удаление писем из ящика после приёма не делается (только флаг «прочитано»).
- Смена `SECRETS_KEY` требует повторного ввода секретов каналов (статус канала — «ошибка: не удалось
  расшифровать»); ротация ключа с перешифрованием — отдельная задача.
- Повторная отправка «не доставленного» ответа из интерфейса оператора не сделана — оператор пишет ответ заново.

(`connectors-under-rollout.mjs`).

## Ф3. Маршрутизация (ACD), статусы операторов, супервизор — выполнена (28.09.2026)

**Сделано**

- Миграция `0004`: у `queue` — стратегия (`least_recent`/`least_load`), резервная группа для перелива
  (`overflow_queue_id`/`overflow_after_s`), таймаут принятия оператором (`offer_timeout_s`), длительность
  постобработки (`wrap_up_s`); у `conversation` — эффективный приоритет, момент постановки в очередь
  (`queued_at`), признак уже начисленной эскалации, дата отложенного перезвона (`callback_at`); новые таблицы
  `agent_status`/`agent_status_log` (статус оператора и его журнал), `routing_offer` (предложения обращений
  операторам: принято/отклонено/просрочено), `routing_rule` (маршрутизация текста по каналу/ключевому
  слову/regex, M-RT-07), `segment_priority` (приоритет по сегменту клиента, M-RT-08).
- **pg-boss** (`packages/service-kit/src/jobs.ts`) — первая очередь фоновых задач в проекте: таймаут принятия
  оператором создаётся и обрабатывается самим router. Остальные таймеры (перелив, эскалация, автовозврат из
  постобработки, отложенный перезвон) — периодический опрос router по хранимым в БД дедлайнам, а не задачи
  pg-boss: решение и почему — см. «Решения и находки».
- **router** (новый сервис, 2 экземпляра, без входящего HTTP от пользователей): на каждом тике — перелив
  просроченных по ожиданию обращений в резервную группу, эскалация приоритета по времени ожидания,
  автовозврат оператора из «Постобработка» в «Готов», возврат отложенных обращений в очередь, затем попытка
  назначить операторов очередным обращениям. Кандидаты — операторы очереди (`user_queue`) со статусом «Готов»
  и свободной ёмкостью; навык, привязанный к теме (`skill.topic_id`), — мягкий приоритет при выборе, а не
  жёсткий фильтр (иначе обращение может зависнуть без подходящего специалиста); стратегия очереди —
  «дольше всех свободен» или «наименьшая загрузка» (`RoutingStrategy`, unit-тесты). Конкурентная безопасность:
  обращение и статус выбранного оператора блокируются `FOR UPDATE` (SKIP LOCKED — на самом обращении) в одной
  транзакции — так ни обращение не уходит двум операторам, ни ёмкость оператора не превышается при гонке двух
  экземпляров router. Не подключается к NATS: события пишет через тот же outbox, что и остальные сервисы, —
  уже работающие экземпляры worker публикуют их в JetStream.
- **api**: `POST /api/v1/conversations/:id/accept` и `/decline` (оператор принимает или отклоняет предложение
  router; отказ исключает оператора из повторных предложений по этому обращению); `take` — теперь рядом с
  автоматическим распределением, а не вместо него (ручной перехват из очереди, в том числе для супервизора);
  `close` — при результате «Отложено / перезвонить» требует дату и время, сохраняет их в `callback_at`
  (router возвращает обращение в очередь по наступлении срока) и переводит оператора в «Постобработка» на
  `wrap_up_s` очереди; `transfer` в очередь — новая постановка в очередь (сброс `queued_at`/приоритета/
  эскалации). `packages/domain`: `ingestInbound` применяет правило маршрутизации текста и приоритет сегмента
  клиента при создании обращения (M-RT-01/07/08); общий `setAgentStatus` (api и router) ведёт
  `agent_status`/`agent_status_log`. Новые контроллеры: `agent-status` (`GET/POST /api/v1/agent-status`) и
  `supervisor` (`GET /api/v1/supervisor/overview` — очереди и операторы для панели реального времени).
- **web**: переключатель статуса оператора (Готов/Перерыв с причиной/Офлайн; «Постобработка» — только
  индикатор с обратным отсчётом) в рабочем месте оператора; предложенные обращения (`status = offered`) — с
  кнопками «Принять»/«Отклонить» в списке и в карточке; закрытие с результатом «Отложено / перезвонить» — поле
  даты и времени; новая страница «Супервизор» (очереди — ожидают/дольше всех ждёт/порог эскалации; операторы —
  статус/причина/сколько в статусе/активные чаты), опрос раз в 4 с; справочники «Очереди» (новые поля
  стратегии/перелива/таймаутов) дополнены вкладками «Правила маршрутизации» и «Приоритет сегментов»; настройка
  «Надбавка приоритета при эскалации».
- `infra/compose`: сервис `router` (2 экземпляра, без Traefik — как worker); `ops/build-images.sh` собирает его
  по умолчанию. `ops/test/route-under-rollout.mjs` — новый автотест: обращения (часть уже предложена
  оператору, часть ещё ждёт) переживают поэтапное обновление router без потерь.

**Решения и находки**

- **Не все таймеры — через pg-boss, хотя pg-boss введён именно в этой фазе.** Таймаут принятия
  оператором заведён через pg-boss (`router.offer-timeout`): он создаётся и потребляется самим router, без
  межсервисных зависимостей. У перелива, эскалации, автовозврата из постобработки и отложенного перезвона
  дедлайн уже хранится в столбце (`queued_at`+`overflow_after_s`/`max_wait_s`, `wrap_up_until`, `callback_at`);
  их обрабатывает периодический опрос router (раз в `ROUTER_POLL_INTERVAL_MS`, по умолчанию 300 мс) —
  состояние переживает перезапуск/замену экземпляра точно так же, как задача pg-boss, но без необходимости
  заводить pg-boss-клиент ещё и в api/worker только ради планирования этих задач при постановке в очередь.
  Это отступление от буквального прочтения 02-архитектуры (6.2 п.6: «таймауты… перелив… — задачи pg-boss»),
  оставляющее тот же инвариант (дедлайн — данные, не память процесса); при появлении второго потребителя
  pg-boss (Ф8: ежедневная рассылка по срокам тикетов) стоит пересмотреть в пользу единообразия.
- **Ёмкость оператора — гонка при конкурентных экземплярах router.** Проверка «есть ли ещё место у
  оператора» по прочитанному вне блокировки счётчику пропускает конкурентное превышение (нашёл интеграционный
  тест на 5 параллельных тиков: у одного оператора набралось 6 при лимите 5). Исправлено: перед назначением
  строка `agent_status` выбранного оператора блокируется `FOR UPDATE`, счётчик активных обращений
  пересчитывается уже под блокировкой.
- **Навык по теме — мягкий приоритет, а не фильтр.** Если у темы обращения есть привязанный навык
  (`skill.topic_id`), но ни у кого из готовых операторов очереди нет соответствующей записи в `user_skill`,
  жёсткий фильтр оставил бы обращение без кандидатов вовсе. Навык влияет только на ранжирование внутри
  стратегии (как тай-брейк), не на состав кандидатов — состав определяет членство в очереди (`user_queue`).
- **«Взять» из очереди не заменено автоматическим распределением, а дополняет его** (в плане Ф2 это было
  временным решением до Ф3). И то и другое работает на одной и той же атомарной проверке
  `status = 'queued'`, поэтому не может привести к двойному назначению: кто первый — ручной перехват
  оператором/супервизором или очередной тик router — тот и получает обращение.
- **Лимит частоты клиентского API в нагрузочном тесте.** Пока разбирался нагрузочный автотест
  `route-under-rollout.mjs`: клиентский API создаёт не больше 10 сессий в минуту с одного адреса (M-CH-03,
  уже было в Ф2) — обычная нагрузка теста должна заводить сессии заранее и не чаще этого лимита, иначе часть
  просто получает 429.
- Найдена и исправлена скрытая гонка в интеграционных тестах api и router: `pg.Pool`, созданный в
  `it/setup.ts`, без обработчика `'error'` иногда аварийно завершал процесс Vitest при `DROP DATABASE …
WITH (FORCE)` в `cleanup()` (сервер обрывает ещё закрывающиеся простаивающие соединения) — заметно только
  при параллельном запуске нескольких пакетов интеграционных тестов. Добавлен `pool.on('error', () => {})` в
  обоих `it/setup.ts`.
- **Статус оператора при закрытии и ручном «Взять» (найдено при ревью).** Первая версия переводила в
  «Постобработка» любого, кто закрыл обращение, — в том числе оператора на перерыве и супервизора, закрывшего
  чужое; через `wrap_up_s` router делал их «Готов», и они начинали получать обращения. А «Взять» у оператора без
  записи статуса создавало её сразу со статусом «Готов». Теперь постобработка — только для своего обращения и
  только из «Готов»/«Постобработка», а «Взять» лишь отмечает `last_assigned_at`. Покрыто интеграционным тестом api.
- **Служебные уведомления ACD — внутренние заметки.** «Оператор не принял вовремя», «перелив в резервную
  группу», «наступило время перезвона» пишутся как `note` (клиент их не видит); клиенту уходят только
  «Оператор … подключился к диалогу» и «Мы свяжемся с вами …» (время — Europe/Minsk).
- Squawk: `adding-foreign-key-constraint` и `require-concurrent-index-creation` добавлены в исключения CI —
  по той же причине, что и уже исключённые `prefer-robust-stmts`/`require-timeout-settings`: раннер миграций
  (`packages/db/src/migrate.ts`) выполняет файл миграции одной транзакцией, а `CREATE INDEX CONCURRENTLY` и
  раздельные `NOT VALID`/`VALIDATE` для внешнего ключа требуют выполнения вне транзакции/в нескольких
  транзакциях. При масштабе MVP (локальный/демонстрационный стенд) кратковременная блокировка записи в
  expand-миграции приемлема.

**Известные ограничения**

- Ёмкость операторов (`operator.max_chats`) и статус влияют только на текстовые каналы (`channel_kind <>
'voice'`) — голосовая ёмкость и связанные приоритеты появятся в Ф5.
- Панель супервизора — опрос раз в несколько секунд, а не push через WebSocket (M-REP-02 отмечена [УПР] в
  требованиях); полноценная витрина реального времени и пороги/подсветка — доработка Ф10.
- Вкладка «Перезвонить» как отдельный список задач (упомянута в плане Ф2 для Ф6/Ф8) не заведена: отложенное
  обращение по наступлении срока возвращается в ту же очередь и просто появляется в «Мои»/«Очередь» — этого
  достаточно для M-CARD-05 в MVP.
- Пропущенное предложение (таймаут) не меняет статус оператора: отошедший от рабочего места оператор
  остаётся «Готов» и продолжает получать предложения по очереди с другими (каждое — задержка `offer_timeout_s`
  для клиента). Обычная практика ACD — после N пропусков подряд переводить в «Не готов»; нужно решение
  заказчика (записать в 04 при следующей фазе).
- Если все подходящие операторы отказались от обращения, router больше его не предлагает — оно остаётся во
  вкладке «Очередь» до ручного «Взять» (оператором или супервизором).
- Правила маршрутизации текста проверяются только по телу первого сообщения обращения (создание); смена
  темы/канала обращения задним числом их не пересчитывает.

в рабочем месте оператора) и «Обновление без остановки» (`route-under-rollout.mjs`).

**Решения и отступления от плана**

- S3-хранилище — **SeaweedFS** (Apache 2.0) вместо MinIO (В-36): риски смены лицензии/политики сборок MinIO.
- Вместо внешнего плагина docker-rollout — собственный `ops/rollout.sh` (меньше внешних зависимостей).
- **Traefik 3.6+ обязателен** для Docker Engine 29+: Traefik 3.5 обращается к Docker API 1.24 и получает отказ.
- Версии зафиксированы на проверенных линиях (TypeScript 5.9, NestJS 11, zod 3, Vitest 3), а не на только что
  вышедших мажорных (TypeScript 7, NestJS 12) — обновление отдельной задачей.
- Метрики NATS в Prometheus не собираются (нужен prometheus-nats-exporter) — при развитии мониторинга.

**Известные ограничения**

- Сертификат HTTPS — самоподписанный сертификат Traefik; для сервера — свой сертификат или ACME.
- Задача CI `zero-downtime` скачивает образы из Docker Hub; при его лимитах — использовать зеркало/свой реестр.
- Kamailio/Asterisk/coturn — в Ф5; остальные сервисы (realtime, router, worker, коннекторы) — в своих фазах.
