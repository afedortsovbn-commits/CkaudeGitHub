# Журнал фаз MVP

## Ф13. Интеграции: Rocket Data (отзывы с карт) и синхронизация объектов — выполнена (30.09.2026)

Требования M-CH-10, M-ORG-06 (автоматическая синхронизация), отчёт по отзывам в M-REP-03; демо-сценарий 10.
**Описания API Rocket Data (В-32) и источника справочника объектов (В-42) от заказчика не получены** — по указанию
заказчика фаза выполнена по контрактам-заглушкам с решениями по умолчанию из 04:
[интеграции-rocketdata-и-объекты.md](интеграции-rocketdata-и-объекты.md). Зависящее от внешних форматов собрано в двух
адаптерах — при получении описаний меняются только они.

**Сделано**

- **Контракты** (`packages/contracts/src/reviews.ts`): настройки канала «Отзыв» `RocketDataChannelConfigSchema` (адрес и
  токен API, период опроса, глубина первой загрузки, «срочные — с оценкой не выше», пропуск уже отвеченных), сведения об
  отзыве `ReviewMetaSchema` (во входящем — `meta.review`, в обращении — `channel_meta.review`), названия площадок,
  настройки и строка выгрузки синхронизации объектов; `review` — в `CONNECTOR_CHANNELS` (ответ оператора уходит
  коннектору), `api_token` — в шифруемых секретах канала; отчёт `reviews` и разрезы `rating`, `platform` (аддитивно,
  исключение сверки — новый ключ каталога отчётов, `ops/compat/allow.json`).
- **connector-rocketdata** (новый сервис, 2 экземпляра, по образцу connector-telegram и `connector-kit`): каждый
  канал «Отзыв» — подключение к Rocket Data; опрос ведёт владелец аренды `rd.<канал>`, отметка «изменены начиная с» —
  в NATS KV `cc_rd_state` (сдвигается после записи страницы в `CC_INBOUND`, с запасом 5 мин); ключ сообщения — id
  отзыва + отпечаток оценки и текста (повторная загрузка — не дубль, изменённый отзыв — новое сообщение). Ответы —
  общий `OutboundWorker`: `POST …/answer` с `Idempotency-Key` = id сообщения (повтор не создаёт второй ответ);
  «отклонён площадкой», 4xx — без повторов; файлы и пустой ответ — «не доставлено». Выход к API — через прокси
  (`ROCKETDATA_PROXY` → `HTTPS_PROXY` + `NODE_USE_ENV_PROXY=1`, встроенная поддержка Node 22).
- **Отзыв → обращение** (`packages/domain/src/reviews.ts`, `ingestInbound`): клиент — автор отзыва (идентификатор —
  id отзыва: у площадок нет устойчивого id автора), поэтому у каждого отзыва своё обращение; объект — по
  `external_ids.rocketdata` точки, иначе по коду объекта → предприятие обращения (до события `conversation.created`:
  права и измерения отчётов); низкая оценка — «срочное»; точка не найдена — обращение без предприятия и служебная
  подсказка оператору; уже отвеченный на площадке неизвестный отзыв — не создаёт обращения. Изменённый отзыв —
  новое сообщение открытого обращения с актуальной оценкой. **Ответ публичный**: приветствия, «в очереди», ключевые
  слова, автозакрытие по молчанию и сообщение о передаче на 2-ю линию на отзывы не отправляются (кроме правил, где
  канал «Отзыв» выбран явно). Ответ оператора — команда `cc.outbound.review` (адрес — id отзыва) той же транзакцией.
- **Синхронизация объектов** (`packages/domain/src/objects-sync.ts`): разбор выгрузки JSON или CSV (колонки ручного
  импорта + `rocketdata`, `ext_<ключ>`, `is_active`), сверка по коду одной транзакцией — добавление, обновление,
  переход объектов, заведённых вручную/импортом, под синхронизацию (`source = sync`), деактивация исчезнувших и
  закрытых, повторная активация; строки с ошибками — «замечания», такие объекты не деактивируются; **защита от
  ошибочной выгрузки** (пустая или деактивация больше заданной доли, 30 %) — ошибка без изменений; журнал запусков
  `object_sync_run` (итоги, изменения поле «было → стало», замечания); один запуск за раз (advisory lock).
  Плановый запуск — worker (pg-boss раз в минуту: включено, наступило время по Минску, сегодня ещё не выполнено;
  после ошибки — повтор раз в час). api: `GET/PUT /api/v1/objects/sync/settings` (токен источника шифруется, не
  отдаётся, «маска — не менять»), `POST /api/v1/objects/sync/run[?dryRun=true]`, `GET …/runs`, `GET …/runs/:id`.
  Синхронизируемые поля (код, название, адрес, предприятие, внешние идентификаторы) и активность вручную не
  меняются — ни в карточке объекта, ни импортом CSV (400 с пояснением); общие «Настройки» и экспорт конфигурации
  настройку `objects.sync` не содержат.
- **Отчёт по отзывам** (`reports/reviews`): по объектам, предприятиям, оценкам, площадкам, дням — отзывов, средняя
  оценка, с оценкой 1–2, отвечено, доля отвеченных, среднее время до ответа, распределение оценок; изменённый отзыв
  считается один раз (последнее состояние), отвеченный — ответ доставлен в Rocket Data; период — по дате публикации;
  область видимости — `scopeFilter`; CSV.
- **web**: тип канала «Отзывы с карт (Rocket Data)» с формой, состоянием подключения и журналом; у оператора — канал
  «Отзыв» и звёзды в списке, над перепиской — карточка отзыва (площадка, оценка, автор, дата, объект, ссылка),
  подсказка «публичный ответ», файлы к ответу на отзыв недоступны, у сообщений — оценка редакции и «отзыв изменён
  автором»; страница «Синхронизация объектов» (настройки, «Проверить (без изменений)», «Синхронизировать сейчас»,
  журнал запусков с подробностями); в «Объектах» — источник и идентификатор точки Rocket Data; разрезы отчёта.
- **Моки** (`mock-selfservice`): API Rocket Data с независимыми учётными записями (`/rocketdata/<акк>/…`: демо-канал —
  `demo`, проверки — свои), управление отзывами и просмотр ответов; выгрузка объектов JSON/CSV с подменой.
- **Демо-данные**: канал «Отзывы с карт (Rocket Data, демо)» (опрос раз в 10 с), очередь «Отзывы» с операторами,
  точки Rocket Data у демо-объектов, источник синхронизации (выключена, запуск вручную). Отзывы в моке появляются

- Миграция `0015_expand_reviews.sql` (только expand): `object_sync_run`, `service_object.synced_at`, настройка

- Инфраструктура: `connector-rocketdata` ×2 в compose, `ops/build-images.sh`, `release.sh` (`START_SERVICES` — запуск
  нового сервиса выпуском), `restore.sh`, `demo.sh`, CI (сборка, `ops/test/reviews-under-rollout.mjs`; в автотесте

**Решения и находки**

- **Клиент — автор отзыва, у каждого отзыва своё обращение.** Площадки не дают устойчивого идентификатора автора, а
  ответ адресуется конкретному отзыву; объединять отзывы «по имени» — ошибочно склеивать разных людей.
- **Ключ сообщения — отпечаток содержимого**, а не `updated_at`: у отзыва меняется `updated_at` и после нашего ответа
  (ответ публикуется), но новым сообщением это становиться не должно.
- **Мок Rocket Data — многоаккаунтный**: любой канал к одному адресу забирал бы все отзывы мока, и отзывы проверок
  попадали бы в демо-очередь с операторами (router предлагал бы их в следующих проверках).
- **Автоответы на отзывы — только явно**: правило «для всех каналов» иначе опубликовало бы приветствие на карте.
- **Время синхронизации — pg-boss раз в минуту + журнал**, как у рассылки 2-й линии: время меняется в интерфейсе без
  перезапуска, запуск не повторяется при замене экземпляра worker.
- **Найдено в CI: блокировка «головы очереди» в router.** `assignQueued` брал первые `ROUTER_BATCH_SIZE` (20)
  ожидающих обращений по всей системе; очередь без готовых операторов с хвостом больше пакета (отзывы проверки
  обновления, в эксплуатации — первая загрузка отзывов за 7 дней) занимала весь пакет, и чаты и звонки других очередей
  не распределялись (`route-under-rollout.mjs`: 8 из 8 обращений остались в очереди). Теперь пакет — голова каждой
  очереди (до 20 на очередь); интеграционный тест router воспроизводит случай.
- **Найдено проверкой обновления: справочник каналов api не принимал тип `review`** — канал «Отзыв» нельзя было
  создать в интерфейсе (демо-канал создаётся сидом, интеграционный тест тоже шёл через сид). Исправлено, создание
  через справочник добавлено в интеграционный тест.
- **Прокси — встроенный в Node 22** (`NODE_USE_ENV_PROXY`), без зависимости undici/агента.
- **Найдено автотестом `zero-downtime` в CI (выход операторов при выпуске, не связано с отзывами)**: в части прогонов
  2–7 из 10 операторов оказывались «не в системе». Диагностика автотеста (ошибки страниц и запросов, скриншоты —
  артефакт `zero-downtime-report`, `out/zdt-operators/`) показала: `POST /auth/refresh` обрывался браузером
  (`ERR_NETWORK_CHANGED` — при пересоздании контейнеров Docker меняет сеть хоста), сервер же успевал сменить
  refresh-токен; браузер оставался со старым, следующая попытка получала 401 — и выход. Исправление: сервер ещё
  120 с после ротации принимает предыдущий токен (`auth_session.prev_refresh_hash`/`rotated_at`, миграция `0016`,
  выход отзывает и его), клиент при сбое сети или 5xx повторяет обновление сессии с паузой (4 повтора) вместо выхода.
- Найдено при e2e: после перезапуска Docker-демона Kamailio остаётся «unhealthy» (слушал прежний адрес интерфейса),
  а `migrate` может не дождаться S3 — стек поднимается повторным `up` и пересозданием Kamailio (к Ф13 не относится).

**Известные ограничения**

- Обмен с Rocket Data и формат выгрузки объектов — **предположение** до получения описаний (В-32, В-42): проверено на
  моках, не на реальных системах. Статус публикации ответа (`pending` → `published`/`rejected` после модерации)
  после отправки не отслеживается — «отправлено» означает «принято Rocket Data».
- Источник объектов — только HTTP GET; выгрузка файлом по расписанию (SFTP, общая папка) — после В-42.
- Новый сервис при выпуске поверх Ф12 запускается `START_SERVICES=connector-rocketdata ops/release.sh <тег>` (или
  `ops/rollout.sh connector-rocketdata`).

**Как проверить** — [сценарий демонстрации](сценарий-демонстрации.md), раздел 10; `node ops/test/reviews-under-rollout.mjs <тег>`.

## Ф12b. Закрытие пробелов приёмки — выполнена (30.09.2026)

Требования со статусом «частично» после Ф12: M-OP-02, M-TEL-01, M-CARD-01, M-CARD-06, M-OP-05 и M-TKT-11
(консультация), M-NFR-08. Архитектура — 02, 4.2, 5, 8.1; миграция только expand (`0014_expand_gaps.sql`). Консультативный
перевод уложился в фазу — Ф12c не понадобилась. В [отчёте о соответствии](соответствие-требованиям.md) пунктов
«частично» больше нет.

**Сделано**

- **M-OP-02 — вкладки «Удержание» и «Постобработка»** (второй ряд вкладок рабочего места, в подписи — число
  обращений; обновление по событиям realtime и раз в 30 с). Строятся по признакам, без новых статусов обращения
  (`GET /conversations?tab=hold|wrapup`): «Удержание» — мои обращения, чей звонок в разговоре на удержании
  (`call.on_hold`); «Постобработка» — мои открытые обращения, где разговор закончен: у звонка все вызовы завершены
  (разговор был), у чата последним написал оператор и клиент молчит дольше `operator.wrapup_chat_idle_s` («Настройки»,
  300 с по умолчанию) — ответ клиента возвращает чат из вкладки.
- **M-TEL-01 — несколько SIP-транков с приоритетом и резервом**: `TRUNKS="хост:порт;приоритет,…"` (1 — основной; без
  приоритета — по порядку), `TRUNK_HOST` остаётся для совместимости (`TRUNK_HOST;1`). entrypoint Kamailio сортирует
  транки по приоритету в список; `route[TO_TRUNK]` отправляет вызов в первый, `failure_route[TRUNK_FAILOVER]` — в
  следующий при отказе (5xx) или молчании (408 без предварительных ответов); адрес, который не разрешается (DNS), —
  пропускается сразу. «Занято» (486), отбой абонента и 408 после звонка — ответ абонента, в другой транк не
  повторяются. Если `TRUNK_ALLOW` задан, к нему добавляются адреса всех транков (разрешаются при старте).
- **M-CARD-01 — ручное слияние дублей клиентов**: «Объединить с…» в карточке клиента (поиск по имени, телефону,
  email, идентификатору в канале; выбор основного) → `POST /contacts/:id/merge {duplicateId}`: идентификаторы, обращения,
  согласия и вложения переносятся к основному, пустые поля основного дополняются, дубль — `merged_into_id`,
  `merged_at`, `merged_by`, в поиске не находится; ранее присоединённые к дублю — сразу к основному (цепочек нет).
  Право `contacts.merge` (администратор, супервизор), аудит `contact.merge`. Обращения сохраняют id — отчёты и тикеты не
  меняются. Сессия виджета дубля продолжает работать: api (`/client/*`), worker (приём сообщения) и realtime
  (при подключении и в периодической сверке) подставляют основного клиента.
- **M-CARD-06 — обязательный тег при закрытии** — опция очереди «Обязательный тег при закрытии» (`queue.require_tag`,
  справочник «Очереди»; экспорт/импорт конфигурации переносит её автоматически). Закрытие и передача на 2-ю линию без
  тега — 400 `tag_required`; в карточке — «Теги \*» с пояснением, кнопки «Завершить» и «Передать на 2-ю линию»
  недоступны до выбора тега.
- **M-OP-05 / M-TKT-11 — консультативный перевод**: в софтфоне «Консультация» (адресат — как у перевода: оператор;
  очередь или подразделение с очередью — свободный оператор очереди в «Готов» без звонка; подразделение с внешним

**Решения и находки**

- **Найдено и исправлено: переход между узлами Asterisk в dispatcher Kamailio не работал** (с Ф5a). `ds_next_dst()` в
  `failure_route[MEDIA_FAILOVER]` требует флага `flags=2` модуля dispatcher («failover support disabled» в журнале),
  поэтому при отказе выбранного узла вызов не уходил на второй. Флаг включён.
- **Транки — не через dispatcher**: в режиме проб `ds_probing_mode=0` флаг «проба» снимается после первого ответа (узлы
  Asterisk остались бы без постоянных проб), а в режиме 1 пробы шли бы и к транку оператора связи, который может не
  отвечать на OPTIONS, — и транк отключался бы по ошибке. Поэтому dispatcher — только для узлов, а транки
  перебираются в сценарии Kamailio по списку от entrypoint (`$(var(list){s.select,N,|})`).
- **Вкладки — по признакам, а не статусам** (как в задании): статусы обращения `hold`/`wrap_up` не вводились — не
  нужны новые переходы, события и правки отчётов. «Закончен ли чат», система знает только по молчанию клиента —
  отсюда порог в «Настройках».
- **Консультация с очередью** — звонок свободному оператору очереди («Готов», без звонка), а не постановка в очередь:
  консультация — разговор «здесь и сейчас»; нет свободного — сообщение «переведите без консультации».
- **Слияние и живые сессии**: токен виджета содержит id клиента, поэтому основной клиент подставляется при каждом
  запросе (`merged_into_id`), а realtime сверяет подключённых клиентов раз в 30 с — открытый чат дубля не теряет
  ответы.
- **Строки — кодмодом по синтаксическому дереву** (одноразовый, в репозиторий не входит): текст JSX переносится по
  правилам JSX (обрезка по строкам, пробелы по краям сохраняются в значении), шаблоны с подстановками — функции;
  затенявшие ресурсы локальные переменные `t` переименованы. `as const` у ресурсов не используется — литеральные типы
  мешали параметрам по умолчанию и `useState`.
- Встроенный сценарий SIPp `uas` не возвращает Record-Route в 200 OK — запросы внутри диалога шли бы мимо Kamailio;
  в тесте резервного транка — свой сценарий ответа (как у настоящего транка).

**Известные ограничения**

- Транк МТС не подключён — ждём параметры (В-06); проверено имитаторами транка (SIPp).
- Консультация с очередью не учитывает навыки и приоритеты router; предложение router этому оператору во время
  консультации не блокируется (софтфон занят — предложение уйдёт следующему).
- Слияние необратимо; «разъединить» — нет (не требовалось).
- Ключи ресурсов — транслитерация (читаемы, но не английские); второй язык интерфейса — добавлением объекта рядом с
  `ru` в `lib/i18n.ts`.
- Выпуск Ф12b поверх Ф12: новый образ Kamailio (`TRUNKS`, `flags=2`) — окном класса C (`ops/update-media.sh kamailio`);
  до этого исходящие работают через прежний `TRUNK_HOST`.

**Как проверить** — `node ops/test/trunk-failover.mjs`, `pnpm i18n:check`, e2e `phase12b.spec.ts`; руководства
оператора и администратора (вкладки, консультация, слияние, обязательный тег).

**Решения и находки**

- **Найдено и исправлено: web после `docker compose stop` + `start` навсегда отвечал 503.** Отметка осушения
  `/tmp/draining` оставалась в файловой системе контейнера, и `/healthz` после запуска считал экземпляр
  останавливающимся. Проявилось на полном восстановлении из копии; теперь entrypoint удаляет отметку при старте.
- **Найдено: Traefik без файла сертификата ломает TLS целиком** (ссылка на отсутствующий `defaultCertificate`), поэтому
  сертификат подключается отдельным файлом конфигурации (`TRAEFIK_TLS`), а по умолчанию подключён файл только с
  минимальной версией TLS. Пустой `tls: {}` Traefik считает ошибкой.
- **Право на неклассифицированные — в предикате, а не в каждом запросе**: условие `(enterprise IS NULL AND темы нет)`
  добавляется `scopeFilter` только если у строки есть оба измерения; все 20+ мест применения получили его без правок.
- **Журнал событий содержит тексты сообщений** — обезличивание без их стирания было бы неполным. Журнал остаётся
  неизменяемым для всех, кроме процедуры обезличивания (`SET LOCAL cc.pd_erase` в её транзакции); удаление событий
  запрещено всегда, журнал аудита — неизменяем без исключений.
- **Строки таблиц для проверки копии — из самого дампа** (блоки COPY), а не отдельным запросом: копия снимается на
  работающей системе, и отдельный подсчёт разошёлся бы с дампом.
- **Срок хранения — в api, а не в worker**: доступ к S3 уже есть у api; задача pg-boss выполняется одним экземпляром.
- В e2e демо-сценария 3 звонок — последним шагом: в статусе «Готов» router предлагает оператору и накопившиеся в
  очереди чаты предыдущих тестов, и лимит одновременных чатов заполняется предложениями.

**Известные ограничения**

- Пункты «частично» из [отчёта о соответствии](соответствие-требованиям.md): отдельные вкладки «Удержание» и
  «Постобработка», несколько транков с приоритетом (и параметры транка МТС, В-06), ручное слияние дублей клиентов,
  обязательный тег при закрытии по очереди, консультативный перевод (в т.ч. прямой на подразделение), вынос всех
  строк интерфейса в ресурсы локализации.
- 2FA — только TOTP (без резервных кодов); SSO/AD — позже (В-12). Обязательность — для прав `admin.*` (В-53).
- Маскирование — в журналах прикладных сервисов; журналы Asterisk/Kamailio содержат номера (служебные, в контуре).
- Обезличивание не меняет ответы операторов и тексты тикетов 2-й линии (могут содержать ПДн); переписка и журнал
  событий хранятся бессрочно (В-54).
- Резервное копирование — полное (без PITR и инкрементов); объекты, созданные после копии, при восстановлении
  остаются в хранилище (не мешают).
- Выпуск Ф12 поверх Ф11: новый образ Kamailio (`TRUNK_ALLOW`) — окном класса C (`ops/update-media.sh kamailio`);
  Traefik (каталог конфигурации) — пересоздать один раз (`docker compose up -d traefik`, окно ~ секунды); до этого
  прежний Traefik работает со старой конфигурацией.

**Решения и находки**

- **Найдено и исправлено: принятый оператором входящий звонок обрывался через 32 с** (с Ф5). JsSIP регистрируется
  с `+sip.instance`, получает GRUU и указывает его Contact'ом в диалоге (`sip:op-…@cc.local;gr=…`); Kamailio
  внутри диалога пытался разрешить `cc.local` как хост и отбрасывал ACK, BYE и re-INVITE к браузеру. Итог: JsSIP
  без ACK завершал вызов по Timer H (32 с), BYE клиента до оператора не доходил. Прежние e2e разговаривали меньше
  32 с. Теперь GRUU разрешается `lookup("location")` — запрос идёт в текущее WSS-соединение софтфона; тот же
  механизм переживает перезапуск Kamailio (после перерегистрации — новое соединение). Тест
  `kamailio-restart.mjs` держит разговор 40 с: до исправления сценарий A падал, после — BYE клиента доходит до
  браузера за ~0,3 с.
- **Record-Route по имени** (`SIP_ADVERTISE`): при пересоздании контейнера Kamailio (обновление образа) IP может
  смениться, а он был в Record-Route идущих диалогов.
- **Найдено автотестом: после осушения узел Asterisk мог не принимать вызовы.** Kamailio кэширует DNS (TTL Docker
  DNS — 600 с); `dispatcher.reload` после пересоздания контейнера брал старый IP, пробы OPTIONS уходили в никуда,
  узел считался неактивным — а скрипт уже осушал второй узел, и новые вызовы получали 503 (42 из 192 в прогоне).
  Прежняя проверка `calls-under-update.mjs media` проходила, когда контейнер получал прежний IP. Теперь Kamailio
  без DNS-кэша, а `update-media.sh` переходит к следующему узлу, только когда Kamailio трижды подряд подтвердил
  обновлённый узел активным по пробам (иначе стоп, второй узел остаётся в работе).
- **При соединении с оператором Asterisk шлёт клиенту re-INVITE** (новый номер и медиа) — прежний сценарий SIPp
  считал это обрывом; сценарии «разговор» (`talkScenario`) отвечают на re-INVITE, UPDATE — ключ `-aa`.
- **Обработка входящих — параллельно по клиентам** (`INBOUND_CONCURRENCY`, 8 на экземпляр worker; следующая пачка из потока — не дожидаясь завершения предыдущей): под нагрузкой
  100 чатов последовательная обработка (~100 мс на сообщение при конкуренции за CPU) давала хвост `CC_INBOUND` до
  60 сообщений и p99 > 5 с ещё до выпуска. Сообщения одного клиента по-прежнему строго по очереди (ключ — канал и
  отправитель); два экземпляра worker и раньше делили потребителя, поэтому гарантии (порядок по `receivedAt`,
  дедупликация по ключу в БД) не ослаблены.
- **Проверки здоровья Docker под нагрузкой**: у образов была проверка раз в 2 с с `--retries=1`. Каждая проверка —
  отдельный процесс в контейнере (`runc`): два десятка контейнеров давали заметную долю загрузки CPU, а одна
  проверка, не уложившаяся в таймаут на загруженном хосте, делала экземпляр «unhealthy» — `rollout.sh` считал это
  отказом нового экземпляра, `release.sh` — нездоровым стеком. Теперь при старте — раз в секунду
  (`--start-interval`, новый экземпляр включается так же быстро), затем раз в 10 с, 3 неудачи подряд; запросы с
  останавливаемого экземпляра по-прежнему снимает проверка Traefik (`/readyz` раз в секунду). `rollout.sh` ждёт
  готовности до `HEALTH_TIMEOUT` и при отказе печатает хвост журнала нового экземпляра; предпроверка `release.sh`
  ждёт восстановления до 60 с.
- **Совместимость контрактов — из исходников ревизии, а не из хранимого снимка**: снимок строится TypeScript API
  по файлам любой git-ревизии (zod-типы выводятся компилятором, OpenAPI — транспиляцией `openapi.ts`), поэтому не
  нужно помнить об обновлении файла-снимка, а база — любой тег или ветка.
- **k6 заменён генератором нагрузки на Node** (как в прежних проверках `ops/test`): без отдельного бинарника в
  офлайн-комплекте, та же роль — сообщения виджета и Telegram с замером доставки.
- **100 чатов = 20 виджета + 80 Telegram**: создание сессий виджета ограничено (10 в минуту с адреса на экземпляр
  api — защита от злоупотреблений), а смесь каналов ближе к реальности.
- **В CI N — базовая ветка, N+1 — PR**: автотест проверяет реальный переход между версиями (миграции, события,
  контракты этого PR поверх работающей прошлой версии), а не две сборки одного кода.

**Известные ограничения**

- Kamailio, Traefik, PostgreSQL, SeaweedFS — по одному экземпляру (класс C, окно); путь развития — 02, 6.5.
- В автотесте операторы в статусе «Офлайн» (в системе, софтфоны зарегистрированы): вызовы ждут в очереди с
  музыкой, чаты — в очереди. Разговоры с оператором при смене call-control и осушении узла проверяют

  разовый всплеск при одновременном появлении 100 новых чатов в критерий не входит (выпуск начинается в
  установившемся режиме).
- Узел NATS в lame duck mode уходит до 2 мин (длительность по умолчанию); менять параметры узлов NATS обычным
  `docker compose up` нельзя — compose пересоздаст все три сразу (см. регламент).
- Мажорное обновление PostgreSQL (логическая репликация) не автоматизировано.
- **Выпуск самой Ф11 поверх Ф10**: пока работают прежние worker (последовательная обработка), под высокой нагрузкой
  хвост входящих копится — в CI (N = `main` целиком, 17 сообщ./с) p99 во время выпуска 18 с при 0 потерь; после
  замены worker задержка сразу падает (p50 ~0,1 с). На реальной нагрузке (сообщение клиента раз в 20–60 с) это
  незаметно; при высокой — начинать выпуск в спокойное время. В CI стек N поднимается с worker и Kamailio версии PR,
  пока базовая ветка не содержит их исправлений (условие в `.github/workflows/mvp.yml` само перестаёт срабатывать).
- **Автотест в CI — с сообщением клиента раз в ~15 с** (`MSG_EVERY_S=15`, ≈7 сообщ./с на 100 чатов): на раннере
  GitHub (4 vCPU на весь стек, 10 Chromium и 30 разговоров) при 6 с хвост входящих копился и p50 превышал 5 с ещё до
  начала выпуска — это предел раннера, а не выпуска (выпуск при этом шёл без потерь, дублей, обрывов и разлогиненных).
  Нагрузка 6 с (17 сообщ./с) проверяется локальным прогоном (таблица выше).

  эпизодов worker'ом по потоку `CC_EVENTS` и партиционирование `event` по месяцу (02, разд. 5).
- **Измерения — на конец периода**: обращение, классифицированное позже, попадает в отчёт со своей итоговой темой и
  предприятием; эпизоды ожидания относятся к очереди, в которой завершились (после перелива — к резервной).
- **Каждая постановка в очередь — отдельный эпизод** (в т.ч. после перевода): так считают SL большинство ACD;

- **Реестр просроченных — по таблице `ticket`**, а не по журналу: это текущее состояние (кто сейчас ответственный),

- **Найдено попутно:** страница «Настройки» отправляла все ключи `system_setting`, включая служебную отметку дня
  рассылки (Ф8) и `recording.retention_days`, которых нет среди разрешённых, — сохранение отвергалось сервером.
  Теперь отправляются только изменённые значения.
- **Неиспользуемый параметр запроса — ошибка PostgreSQL** («could not determine data type of parameter»): параметры

**Решения и находки**

- **Публичный API — отдельное пространство `/api/v1/ext/*`**, а не те же пути, что у рабочего места (в 02 для Bot
  Gateway был указан `/api/v1/conversations/{id}/messages`): ключ — не сотрудник (нет `app_user`, свои права и
  проверки вроде «обращение ведёт другой оператор» к нему неприменимы), отдельное описание OpenAPI и
  независимая эволюция. 02, разд. 7 поправлен.
- **Webhooks — из потока событий, а не из outbox**: раскладка по подпискам — отдельный durable-потребитель
  `CC_EVENTS` в worker, прикладные транзакции не знают о подписках; ход бота, наоборот, ставится в очередь той же
  транзакцией, что и сообщение клиента (ход не теряется и не повторяется).
- **Пробная доставка вместо повторов каждой строки**: упавший получатель не засыпается запросами по каждой
  накопившейся доставке; после восстановления очередь уходит сразу. Порядок доставки не гарантируется, получатель
  отбрасывает повторы по `id` (доставка «хотя бы один раз», как в документации).
- **Демо-ключи известны моку** (задаются `DEMO_*_API_KEY`): мок работает без настройки; на рабочем стенде демо-сид
  не выполняется.
- Пункт меню «Внешние боты» переименован в «Внешний бот (Bot Gateway)»: e2e Ф7 ищет пункт «Боты» по подстроке.
- **Найдена и исправлена ошибка запуска стека (CI, в т.ч. `main` после слияния #11):** кластер NATS отвечает на
  `/healthz` раньше, чем выбран мета-лидер JetStream; первые запросы JetStream API получали `TIMEOUT`, worker,
  коннекторы или realtime падали при старте, и `docker compose up --wait` считал их unhealthy. Теперь
  `connectNats` ждёт готовности JetStream (до 120 с), а создание потоков, потребителей и KV повторяется при
  временной недоступности кластера (`retryJs` в `service-kit`; ошибки конфигурации не повторяются).
- Новые открытые вопросы — В-49 (ограничение адресов получателей webhooks), В-50 (состав экспорта конфигурации).

**Известные ограничения**

- Порядок доставки webhooks не гарантируется; получатель должен быть идемпотентным (дубль возможен, только если
  экземпляр worker аварийно остановлен между ответом получателя и записью результата).
- Внешний бот получает текст и вложения клиента, но отвечает только текстом и кнопками (без файлов).
- Экспорт не переносит оргструктуру, сотрудников, каналы, ключи API и подписки (В-50), удаление при импорте не
  выполняется (записи только создаются и обновляются).
- Реализации анализаторов (транскрибация, резюме, тональность) — [ПОЗЖЕ] (M-AI-03); демо-анализатор — ключевые слова.

**Как проверить** — `mvp/README.md`, раздел «Публичный API, webhooks, внешние боты, экспорт конфигурации (Ф9)».

**Решения и находки**

- **Сообщение клиента по обращению на 2-й линии больше не создаёт новое обращение** (Ф2 создавала): требование
  M-TKT-03 — «добавляется в обращение и видно в тикете». Письма email по цепочке ведут себя так же.
- **Рассылка — «проверка раз в минуту», а не cron на 08:00**: время рассылки — настройка из админки; pg-boss
  `schedule` раз в минуту и отметка дня в `system_setting` дают применение без перезапуска и догоняющую рассылку,
  если worker был остановлен в 08:00. Письма сначала пишутся в `notification` (быстро, одной транзакцией), затем
  отправляются — поэтому перезапуск в любой момент не даёт ни дублей, ни пропусков.
- **Ссылка в письме подставляется при отправке** (`{{link}}` → `PUBLIC_BASE_URL/tickets/:id`): адрес системы — забота
  worker, а не домена.
- **Голосовые обращения пока не передаются на 2-ю линию** — вариант с записью разговора в кабинете по плану в Ф12.
- Постобработка оператора после передачи — как после закрытия (M-RT-06).
- Документы тикета — те же вложения S3 с привязкой к тикету; скачивание — через тикет (проверка видимости тикета).
- **Автоперевод «В работе» — только при открытии страницы тикета назначенным**, а не при фоновом обновлении:
  e2e показал, что открытая у ответственного страница сама «брала в работу» возвращённый тикет по событию realtime.
- e2e: e2e Ф4–Ф7 в этой сессии не прогонялись (стек поднят без телефонии и моков); их затрагивает только изменение
  `ingestInbound` (сообщение в обращение на 2-й линии) и общее соединение realtime — прогонит CI.

- **Проверка фазы после реализации** (повторный разбор кода) нашла и исправила: уведомление «требует
  переназначения» уходило всем супервизорам, а не только в области тикета; лишённый права входа создатель или
  заместитель считался согласующим; письма, стоявшие в очереди, уходили уволенному; при увольнении одного из
  ответственных не менялась версия тикета; «особо важное» переносилось из автоматической отметки обращения по
  другой теме, а автоматическую отметку можно было снять вручную; колокольчик не сообщал о взятии в работу,
  переадресации (остальным участникам) и снятии с тикета; отчёт `reassignment-report` не учитывал область
  видимости; несуществующая дата срока давала 500; админка не показывала предупреждение об открытых тикетах при
  отключении (сервер его возвращал); нет фильтра «Особо важные» во вкладках 2-й линии оператора; ежедневные письма,
  не ушедшие за сутки (SMTP недоступен), теперь не отправляются устаревшими. На каждое — интеграционный тест или
  проверка в e2e (всплывающее уведомление по realtime).
- Кураторы при увольнении единственного ответственного становятся ответственными тикета — В-48 в 04, подтверждено
  заказчиком 29.09.
- **Найдена и исправлена ошибка телефонии (Ф5), проявившаяся на e2e Ф6 в CI после e2e Ф8:** каждая загрузка
  страницы оператора — новая SIP-регистрация, старые живут до `register_expires` (300 с). Kamailio рассылает
  входящий не более чем на 12 регистраций (`max_branches`), а новые контакты шли в конец списка — после частых
  перезагрузок живой софтфон оказывался за пределом и не получал звонок (e2e Ф8 добавлял `operator1` несколько
  загрузок страницы перед Ф5/Ф6 — ровно на границе). Исправлено: `usrloc desc_time_order=1` (новые контакты
  первыми, отбрасываются старые) и снятие регистрации софтфона при закрытии/перезагрузке страницы (`pagehide`).
- e2e Ф8 закрывает контексты браузера сотрудников после каждого теста: в CI незакрытый контекст `operator1`
  с зарегистрированным софтфоном перехватывал звонок e2e Ф6 (та же ловушка, что описана в Ф7).

**Известные ограничения**

- Уведомления в интерфейсе — только по тикетам (обращения 1-й линии — прежние всплывающие уведомления рабочего места).
- Отчёты по 2-й линии (просрочки, возвраты, «ожидает согласования», прямые переводы) — Ф10; данные для них уже в
  `ticket`, `ticket_transition` и журнале `event`.
- Ответ ответным письмом из почты прямо в тикет, автоэскалация при просрочке — [ПОЗЖЕ] (M-TKT-13).

**Решения и находки**

- **Подсказки считает api по запросу панели, а не worker с доставкой через realtime** (отступление от 02, 2.2/4.1):
  провайдеры нужны оператору, открывшему обращение, — запрос из панели с проверкой области видимости проще и не
  грузит LLM на каждое сообщение каждого обращения; секреты провайдеров уже живут в api (как у интеграционных
  операций). Панель перечитывает подсказки только при новом сообщении клиента (свой ключ запроса, не задетый общей
  перечиткой по событиям realtime).
- **Состояние бота — в `conversation.bot_state`, а таймер шага — дедлайн в БД** (как IVR в Ф6 и router в Ф3): шаг
  бота и переход в очередь меняются одной транзакцией с обращением; pg-boss не понадобился.
- **Кнопки — текстом**: и в виджете, и в Telegram (клавиатура ответа), и в email нажатие — это обычное сообщение
  клиента с текстом кнопки; исполнитель сопоставляет текст/номер. Не нужны callback-запросы Telegram и отдельный
  контракт «нажатие кнопки».
- **Канал с ботом — отдельный в демо**: назначение бота прежнему `demo-webchat` сломало бы проверки Ф2–Ф4 и
  нагрузочные автотесты (первое сообщение уходило бы боту, а не в очередь).
- **Облачные LLM запрещены по умолчанию на уровне api** (В-05): адрес провайдера вне контура (не localhost, не
  частная сеть, не имя без домена / `.local`/`.internal`) сохраняется только с явным флагом.
- **e2e: контексты браузера сотрудников закрываются в конце теста.** Незакрытый контекст администратора из e2e Ф7
  оставлял зарегистрированный софтфон, и вызов прослушивания супервизором (Ф5) уходил на эту регистрацию —
  тест прослушивания падал при запуске после Ф7. Повторные прогоны e2e на одном стеке копят очередь брошенных
  обращений (router предлагает их первыми) — полный прогон делать на свежем стеке, как в CI.
- Панель подсказок не показывается в карточке звонка — подсказки относятся к текстовым ответам.
- Имена переменных сценария и шаблоны `{{…}}` допускают кириллицу (в заметке «Бот собрал» — понятные оператору
  подписи «Телефон», «Тема»).

**Известные ограничения**

- Оценка чата — только виджет и чат в приложении (в Telegram/email после закрытия запрос оценки не отправляется).
- Бот не ждёт ответа клиента по таймеру (нет выхода «клиент молчит»): молчание обрабатывает правило
  автозакрытия. Генеративный бот (LLM в роли бота) — [ПОЗЖЕ] (M-AUTO-06); LLM используется только для
  подсказок/черновика.
- Встроенный провайдер ищет по словам последних сообщений (без морфологических синонимов и RAG — позже,
  M-AI-04); ключевые слова статьи — способ подсказать поиску разговорные формы.
- Правила «приветствие», «в очереди», «нерабочее время» срабатывают один раз за обращение; ключевые слова — только
  пока обращение ждёт оператора (не мешают диалогу с оператором).
- Кнопки в Telegram — клавиатура ответа (не inline-кнопки под сообщением).

**Как проверить** — `mvp/README.md`, раздел «Автоответы, боты, подсказки (Ф7)»: демо-чат
`/widget/demo.html?key=demo-webchat-bot`, «Боты», «Подсказки: провайдеры».

## Ф6. flow-engine, конструктор и исполнение IVR, интеграционные операции — выполнена (29.09.2026)

Требования M-IVR-01..07, M-TEL-07 (очередь, сообщения в ожидании), M-TEL-08/09, M-INT-03, M-CARD-07.

**Сделано**

  ввода), **пошаговый исполнитель** с сериализуемым состоянием: `startFlow` / `resumeFlow(событие)` /
  `replayFlow` (повтор текущего шага после переключения) → действие для исполнителя канала (проиграть, ждать
  цифру, HTTP, очередь, голосовое сообщение, перевод, отбой) и эффекты (оценка). Узлы M-IVR-02: «Проиграть
  сообщение», «Объявления о сбоях», «Меню (DTMF)» с повтором, таймаутом, фразой о неверном вводе и цифрой возврата

**Решения и находки**

- **Состояние IVR — в PostgreSQL (`call.ivr_state`, `ivr_wake_at`), а не в NATS KV** (отступление от 02, 6.3):
  состояние вызова call-control хранит в БД с Ф5a, и переход «сценарий → очередь» должен меняться одной
  транзакцией с обращением (router видит очередь по БД). Свойство то же — состояние сохраняется после каждого
  шага и переживает смену экземпляра; таймеры шага — дедлайны в БД (как у router), а не `setTimeout`.
- **Фразы Asterisk получает по HTTP от call-control** (`res_http_media_cache`): узлы Asterisk не нужно
  синхронизировать при загрузке файла, конфигурация узлов неизменна (02, 6.4). Нашлось: модулю нужен каталог
  кэша (`astcachedir`), без него — «Failed to create temporary storage» и мгновенный конец проигрывания.
- **Формат файлов приводит браузер** (Web Audio: декодирование + передискретизация в 8 кГц моно) — на сервере
  не нужен ffmpeg/sox (офлайн-комплект), Asterisk играет файл без перекодирования.
- **Интеграционные операции — по NATS request/reply к api**, а не по HTTP: не нужны служебные токены между
  сервисами, запрос обслуживает любой живой экземпляр api, при его замене начатые запросы завершаются.
- **DTMF**: из браузера — RFC 4733 (RTCDTMFSender, telephone-event с Opus) принимается Asterisk; из SIPp — SIP INFO
  (`application/dtmf-relay`) принимается независимо от `dtmf_mode`. Цифры во время фраз «Проиграть сообщение» не
  учитываются, во время фразы меню — прерывают её.
- **Номер привязывается к сценарию** (`flow.dids`), номер — у голосового канала; без сценария звонок идёт сразу в
  очередь канала, как в Ф5. Демо-IVR — на 2000, чтобы проверки Ф5 на 1000 не зависели от сценария.
- **Расширение CHECK состояния вызова** (`'ivr'`): PostgreSQL не умеет расширять CHECK без пересоздания, а линтер
  expand-миграций запрещал `DROP CONSTRAINT`. Добавлено исключение: `DROP CONSTRAINT IF EXISTS x` допустим, если в
  том же файле `x` создаётся заново как CHECK (набор значений только расширяется, прежняя версия совместима).
- **Задача «перезвонить» и ёмкость голоса** — найдено e2e: 12 задач из проверки переключения предлагались
  оператору по очереди, и пока задача была предложена, он не получал живые звонки (голос «занят»). Задача без
  живого вызова теперь голос не занимает.
- Тестовый прогон в редакторе выполняет тот же `flow-engine` (исходники пакета подключены в web псевдонимом
  Vite), поэтому поведение прогона и реального звонка совпадает.

**Известные ограничения**

- Синтеза и распознавания речи нет (M-IVR-08, В-15): только записанные фразы; демо-фразы синтезированы и звучат
  «роботом». Узлы ботов для текстовых каналов — Ф7 (исполнитель уже общий).
- Сообщения в очереди и «долгое ожидание» действуют до первого ответа оператора; после перевода оператором в
  очередь клиент слышит только музыку. Номер позиции в очереди не озвучивается ([УПР]).
- Во время запроса во внешнюю систему клиент слышит тишину (обычно доли секунды; таймаут операции ≤ 30 с).
- Узел «Перевод на номер» проверен только логикой (нужен SIP-транк; при недоступности — выход «не удалось»).
- Если клиент молчал при записи голосового сообщения, создаётся задача «заказал обратный звонок» (запись пустая).
- В редакторе нет отмены действий и копирования узлов; одновременное редактирование одного сценария двумя
  администраторами — «последний сохранивший побеждает» (публикация — атомарна).
- Журнал интеграционных операций хранит только исход (без тел) — разбор ответа внешней системы делается
  кнопкой «Проверить» в админке.

**Как проверить** — `mvp/README.md`, раздел «IVR (Ф6)»: демо-звонок на 2000 со страницы `/demo-call`, конструктор
«Сценарии IVR», `ivr-under-switch.mjs`.

## Ф5b. Софтфон: аудиоустройства, гарнитуры, качество связи — выполнена (29.09.2026)

Вторая часть фазы Ф5 (первая — Ф5a ниже). Требования M-OP-05/06/07, M-NFR-02.

**Сделано** (`apps/web`)

- **Аудиоустройства** (`lib/audio-devices.ts`, M-OP-06): раздельный выбор микрофона, динамика разговора и
  устройства для звонка-рингтона; выбор хранится по deviceId **и названию** (у Bluetooth-гарнитуры deviceId
  может меняться между подключениями); настройки обработки звука — подавление эха, шумоподавление,
  автоусиление (по умолчанию включены). Вывод звука — `setSinkId` (Chrome, Яндекс Браузер, Edge).
- **Горячее подключение/отключение**: по событию `devicechange` используемое устройство, если пропало
  (разрядился Bluetooth), заменяется доступным — в идущем разговоре микрофон меняется без разрыва звонка
  (`RTCRtpSender.replaceTrack`, состояние «микрофон выключен» сохраняется), динамик — `setSinkId`; сотрудник
  получает уведомление. Когда предпочтённое устройство возвращается — софтфон снова использует его и сообщает об этом.
- **Окно «Настройки звука и гарнитуры»** (кнопка «Звук» рядом с индикатором телефона): выбор устройств, тест
  микрофона (индикатор уровня), «Проверить динамик», «Проверить звонок» (на выбранных устройствах), обработка
  звука, подключение гарнитуры с кнопками, подсказка по горячим клавишам и особенностям Bluetooth.
- **Кнопки гарнитуры — WebHID** (`lib/headset.ts`, M-OP-07): стандартная HID Telephony usage page — Hook Switch
  (поднять — ответить, положить — завершить/отклонить), Phone Mute (переключить микрофон); индикаторы LED
  page — Ring (звонит), Off-Hook (разговор), Mute. Поля ищутся по дескриптору устройства (WebHID
  `collections`), без таблиц конкретных моделей — так работают проводные Jabra и другие гарнитуры со
  стандартной страницей. Разрешение на устройство сотрудник даёт один раз («Подключить гарнитуру»), дальше
  гарнитура подключается сама. Общий интерфейс `HeadsetControl` — точка для адаптеров производителей.
- **Горячие клавиши** (без WebHID или без кнопок): Ctrl+Alt+A — ответить, Ctrl+Alt+H — завершить/отклонить,
  Ctrl+Alt+M — микрофон.
- **Качество связи**: раз в 2 с статистика WebRTC (задержка, джиттер, потери за интервал) → «Связь: хорошая /
  удовлетворительная / плохая» в панели звонка, значения — во всплывающей подсказке (пороги ITU-T G.114/G.107).
- **Восстановление связи**: при обрыве медиа (смена сети оператора) — через 3 с ICE restart (re-INVITE) без
  разрыва звонка, индикация «Связь прервалась — восстанавливаем…» (best effort, 02-архитектура 8.1);
  сигнализация (WSS + регистрация) восстанавливается JsSIP автоматически; при возврате во «замороженную»
  фоновую вкладку (`visibilitychange`/`resume`) регистрация проверяется и возобновляется.
- **Рингтон** — отдельный звук на выбранном «устройстве звонка» (например, динамик компьютера, пока гарнитура
  на столе), плюс системное уведомление браузера.
- **Интеграция со статусом**: переключение в «Готов» при неподключённом телефоне — предупреждение «звонки
  поступать не будут, чаты — будут».

- Firefox и Safari официально не поддерживаются (M-NFR-02): в них нет WebHID и выбора динамика.

## Ф5a. Телефония: медиа, call-control, базовый софтфон — выполнена (28.09.2026)

Фаза Ф5 разделена, как допускает план: **5a** (эта часть) — инфраструктура телефонии, call-control, голос в
маршрутизации, базовый софтфон, запись, прослушивание, обновление медиа без обрывов; **5b** (следующая) — модуль
аудиоустройств (выбор микрофона/динамика/рингтона, горячая замена гарнитуры), кнопки гарнитур через WebHID
(Jabra), индикация качества, чек-лист ручной проверки с реальными гарнитурами.

**Сделано**

- **Медиа и периметр** (`infra/`):
  - `infra/asterisk` — образ узла Asterisk 22.10 LTS на основе `andrius/asterisk:22` (собран из исходников,
    Debian 13) с нашими шаблонами конфигурации: два типа PJSIP-endpoint — браузерный (`webrtc`: DTLS-SRTP, ICE,
    Opus/G.711) и транковый (`trunk`: RTP, G.711 A-law/µ-law), выбор по заголовку `X-Leg: webrtc`, который
    ставит только Kamailio; ARI (приложение `cc`); свой диапазон RTP у каждого узла; музыка на удержании —
    собственная мелодия (`moh/gen-moh.mjs`, без сторонних лицензий). Диалплан не содержит логики: всё — в
    call-control; пока приложение `cc` не зарегистрировано (переключение call-control), вызов не сбрасывается —
    `Stasis()` повторяется до 15 с.
  - `infra/kamailio` — Kamailio 6.0 из официальных RPM проекта (образ `kamailio/kamailio-store`) на AlmaLinux 9,
    сборка без обращения к репозиториям. WSS на отдельном порту 8443 в обход Traefik (самоподписанный
    сертификат генерируется при первом запуске, на сервере монтируется свой), регистрация операторов
    короткоживущими учётными данными (`auth_ephemeral`, схема TURN REST API), dispatcher узлов Asterisk
    (круговой выбор, перебор при отказе, осушение — состояние `disabled`), NAT-обработка WebSocket-клиентов
    (`set_contact_alias`/`handle_ruri_alias`), все потоки через Kamailio: транк → узел, узел → оператор (WSS),
    узел → транк (`TRUNK_HOST`).
  - coturn ×2 (TURN REST API, общий секрет); api выдаёт TURN-учётные данные перед каждым вызовом.
  - compose: `kamailio`, `asterisk-1`, `asterisk-2`, `coturn-1/2`, `call-control` ×2; профиль `test` —
    `trunk-sim` (SIPp UAS, имитация транка для исходящих). `ops/build-images.sh` собирает `cc/asterisk` и
    `cc/kamailio` (тег `MEDIA_TAG`, по умолчанию `dev`).
- **Миграция `0006`**: `call` (вызов: узел, состояние queued/dialing/talking/external/ended, каналы и мост ARI —
  для сверки после переключения), `call_event` (стадии для журнала вызовов, M-TEL-05), `call_recording`
  (запись и очередь её выгрузки), настройка `recording.retention_days` = 180 (В-11).
- **call-control** (новый сервис, 2 экземпляра, ARI-клиент своей реализации на fetch + WebSocket Node 22):
  на каждый узел Asterisk — активный экземпляр (аренда `media.<узел>` в NATS KV, TTL 4 с, продление раз в
  секунду) и резервный. Вызов: StasisStart → ответ, клиент по АОН, обращение голосового канала в очереди
  (номер DID → канал → очередь, правила маршрутизации проверяются по номеру) → музыка → router предлагает
  оператору → call-control звонит в его софтфон (заголовки `X-CC-Conversation`/`X-CC-Call`) → оператор отвечает
  → мост, запись → отбой → журнал. Все операции узла выполняются последовательно (без гонок событий ARI, команд
  api и тика). Состояние — в БД: новый активный выполняет **сверку** с фактическими каналами Asterisk
  (завершившиеся закрывает, отвеченные за время разрыва соединяет, новые вызовы в Stasis без записи — обрабатывает).
  - **Исходящий вызов** (M-TEL-06): софтфон оператора звонит на номер (из карточки — с привязкой к обращению);
    номер нормализуется к E.164 (`normalizePhone`: «80 29 …», «29 …», «+375 …»), вызов уходит в транк через
    Kamailio, оператор слышит гудки, после ответа — мост и запись.
  - **Удержание** (M-TEL-07): на сервере — клиент выводится из моста и слышит музыку, оператор остаётся.
  - **Слепой перевод** (M-OP-05): оператору (звонок сразу предлагается ему), в очередь (новая постановка) и
    **прямой перевод на подразделение предприятия** (M-TKT-11): его очередь или внешний номер через транк;
    фиксируется событием вызова `transfer_*` с предприятием и подразделением (для отчёта «прямые переводы» Ф8/Ф10),
    сообщением в обращении; при неответе подразделения звонок возвращается в очередь.
  - **Прослушивание супервизором** (M-TEL-10): snoop-канал клиента → софтфон супервизора (ответ автоматический),
    действие пишется в журнал аудита.
  - **Запись** (M-TEL-04): snoop-канал клиента в обе стороны пишется в файл на узле (аналог MixMonitor) —
    непрерывно через удержания и переводы; после завершения call-control выгружает её в S3-хранилище (очередь
    выгрузки в БД, повторы) и удаляет с узла; событие `recording_ready`.
  - Брошенный до ответа оператора звонок закрывает обращение как «Пропущенный звонок».
  - Команды от api — NATS request/reply `cc.callctl.<узел>`: отвечает только активный экземпляр узла; во время
    переключения api отвечает 503 «повторите через несколько секунд».
- **router**: ёмкость голоса — один звонок (идущий/звонящий или предложенный голосовой), чаты голос не
  блокируют и не расходуют; интеграционный тест.
- **api**: `GET /telephony/softphone` (SIP-учётные данные на `SIP_CREDENTIALS_TTL_H` часов, адрес WSS, ICE),
  `GET /telephony/ice` (перед каждым вызовом), `POST /telephony/demo-caller` (публичный, только
  `DEMO_CALLER_ENABLED`, ограничение частоты), `GET /conversations/:id/calls` (журнал вызовов: ожидание,

**Решения и находки**

- **Kamailio — из официальных RPM на AlmaLinux 9**: готового образа Kamailio 6 в доступных реестрах нет
  (`kamailio/kamailio-ci` — только 5.5 2021 года), репозитории пакетов из среды сборки закрыты; RPM проекта
  лежат в образе `kamailio/kamailio-store` и ставятся без сети. RPM собраны с OpenSSL 3.2, в базе 3.5 —
  проверка версии снята (`tls_force_run`, ABI 3.x совместим).
- **Kamailio слушает адрес интерфейса, а не 0.0.0.0** (`listen=udp:eth0:5060`): иначе в Record-Route попадал
  `0.0.0.0` и запросы внутри диалога (ACK, BYE) терялись. Эвристику NAT «частный адрес в Contact» не
  используем — внутри контура все адреса частные.
- **Регистрации — в памяти Kamailio**, а не в БД (отступление от 02, 6.5): учётные данные короткоживущие, а
  браузер после переподключения WSS регистрируется заново. SIP Outbound (RFC 5626) не включён: запросы внутри
  диалога к браузеру находят WebSocket по alias в Contact; поведение при перезапуске Kamailio — Ф11.
- **Запись — snoop-каналом клиента, а не записью моста**: запись моста обрывалась, когда клиент выходил из
  моста (удержание, перевод) — найдено e2e (запись 1 с при разговоре 10 с).
- **ARI**: после ухода канала из Stasis приложению приходит `StasisEnd`, а `ChannelDestroyed` — нет; отбой
  определяется по обоим событиям (найдено на первом вызове SIPp).
- **Тайм-аут RTP 30 с у браузерного endpoint**: закрытая вкладка демо-абонента иначе оставляла «вечный» вызов
  в очереди. У транкового endpoint тайм-аута нет (SIPp в тестах не шлёт RTP).
- **Удержание и перевод — на сервере** (call-control), а не SIP re-INVITE браузера: клиент гарантированно
  слышит музыку, запись и журнал вызова непрерывны, одинаково для исходящих и входящих.
- **Opus**: модуль `codec_opus` в базовом образе собран из исходников (GPL), не бинарный модуль Digium —
  допустим по M-NFR-10; браузер ↔ Asterisk — Opus, Asterisk ↔ транк — G.711 A-law.
- `ds_is_from_list` Kamailio сравнивает IP: у пересозданного контейнера Asterisk IP может смениться — поэтому
  `update-media.sh` выполняет `dispatcher.reload` до возврата узла в работу.
- router: в голосовой ветке запроса неиспользуемый параметр `$2` ломал подготовку запроса PostgreSQL
  («could not determine data type») — найдено e2e, добавлен интеграционный тест голоса.

**Известные ограничения**

- Аудиоустройства, кнопки гарнитур, качество связи — выполнены в Ф5b (раздел выше).
- Консультативный перевод ([УПР]) не сделан — только слепой. Позиция в очереди не озвучивается (есть музыка).
- IVR, приветствие, CSAT после разговора, голосовая почта и заказ обратного звонка — Ф6.
- SIP-транк МТС не подключён (ждём параметры, В-06): исходящие проверяются имитацией транка; входящие — с
  демо-страницы и SIPp. Подключение — переменные `TRUNK_HOST`, при необходимости правила Kamailio.
- Для удалённых операторов за NAT нужно задать внешний адрес медиа (`MEDIA_EXTERNAL_ADDRESS`), опубликовать
  RTP-диапазоны узлов и порты TURN (`TURN_URLS`); на демо-стенде в одной сети браузер соединяется с Asterisk
  напрямую.
- Удаление записей по сроку хранения (`recording.retention_days`) — задача Ф12 (настройка уже есть).
- Kamailio принимает входящие INVITE на 5060/udp от любого адреса (как от транка); на сервере порт должен быть
  открыт только для адресов оператора связи (межсетевой экран) — список разрешённых адресов в Kamailio — Ф12.
  Звонок наружу (в транк) может начать только аутентифицированный оператор (WSS); демо-абонент и транк лишь
  звонят в КЦ.
- Прослушивание — эфемерное состояние активного call-control: при его переключении прослушивание
  прерывается (разговор — нет), супервизор включает его снова.

«Обновление без остановки» (`update-media.sh`, `calls-under-update.mjs`).

**Сделано**

- Миграция `0005`: у `channel` — состояние подключения, которое пишет коннектор (`status`/`status_detail`/
  `status_at`: подключён/ошибка/выключен); таблица `channel_log` — журнал обмена канала (приём, отправка,
  служебные события; без содержимого сообщений — ПДн; хранится 30 дней); у `message` — статус доставки во
  внешний канал (`delivery_status`: pending → sent | failed, `delivery_error`); у `conversation` —
  `channel_meta` (для email: тема, Message-ID последнего письма клиента, References).
- **Контракт коннектора** (`packages/contracts/src/channels.ts`): входящее — прежний `InboundMessage` в поток
  `CC_INBOUND` (Ф2); исходящее — `OutboundMessage` (`cc.outbound.<канал>`), статус доставки — `DeliveryStatus`
  (`cc.delivery.<канал>`), оба — в новом потоке JetStream `CC_OUTBOUND` (R3); схемы настроек канала
  `TelegramChannelConfigSchema`/`EmailChannelConfigSchema` (zod) — по ним api проверяет форму админки, а
  коннектор — запись из БД.
- **Исходящие** (`packages/domain`): ответ оператора в канал Telegram/email в той же транзакции, что и само
  сообщение, получает `delivery_status = pending` и команду в outbox (`enqueueCommand`, идемпотентный ключ —
  id сообщения) → OutboxRelay → `CC_OUTBOUND` → коннектор → `DeliveryStatus` → **worker** (новый
  `DeliveryProcessor`, durable-потребитель) → `applyDeliveryStatus` (идемпотентно: доставленное не
  откатывается запоздавшим/повторным статусом) → событие `conversation.message_status` → оператор видит
  «отправляется… / ✓ отправлено / ⚠ не доставлено: причина». Внутренние заметки и служебные сообщения во
  внешний канал не уходят; нет адреса клиента в этом канале — сразу «не доставлено».
- **`packages/connector-kit`** — основа коннекторов: реестр экземпляров канала (`ChannelRegistry`: активные
  каналы своего типа из БД, расшифровка секретов, проверка схемой, перечитка по `config.changed` и страховочно
  раз в 30 с — добавление/изменение/выключение канала без перезапуска; некорректная конфигурация — статус
  «ошибка» у канала, а не падение коннектора); доставка исходящих (`OutboundWorker`: общий durable-потребитель
  на все экземпляры, повторы с экспоненциальной паузой до `OUTBOUND_MAX_ATTEMPTS`, `PermanentError` — сразу
  «не доставлено», защита от повторной отправки — отметка в NATS KV `cc_outbound_sent` после успешной
  отправки); `publishInbound`; сохранение вложений в S3 (запрещённые расширения отбрасываются, как в Ф2);
  журнал и статус канала.
- **`packages/service-kit`**: `KvLease` — аренда в NATS KV (CAS по ревизии, TTL 45 с, освобождение при
  корректной остановке); `sealSecret`/`openSecret` — шифрование секретов каналов в БД (AES-256-GCM, ключ из
  `SECRETS_KEY`); поток `OUTBOUND_STREAM`; пинги NATS в журнал — на уровне debug.
- **connector-telegram** (новый сервис, 2 экземпляра): каждый бот — экземпляр канала. Режим **опрос**
  (long polling, по умолчанию; ведёт владелец аренды `tg.<id канала>`, смещение — в NATS KV `cc_tg_offsets`)
  или **webhook** (`POST /tg/<id канала>` через Traefik, принимают оба экземпляра, проверка
  `X-Telegram-Bot-Api-Secret-Token` — секрет генерируется api автоматически; `setWebhook` делает владелец
  аренды). Личные чаты: текст, фото (самое крупное), документы с подписью; `/start` пропускается.
  Обновление подтверждается Telegram (200 OK / сдвиг смещения) только после записи в `CC_INBOUND`.
  Ответы: текст и документы; 400/403 от Bot API (бот заблокирован, чат не найден) — без повторов.
- **connector-email** (новый сервис, 2 экземпляра): каждый ящик — экземпляр канала; приём по IMAP (IDLE +
  страховочная проверка раз в 15 с) ведёт владелец аренды `mail.<id канала>`, последний UID — в NATS KV

- **Свой тонкий клиент Telegram Bot API вместо grammY** (отступление от 02, раздел «Технологии»): нужны 7
  методов, а владение циклом long polling (аренда, смещение в KV, отмена при остановке) и webhook-обработчиком
  на общем http-сервере сервиса у grammY пришлось бы обходить. Меньше зависимостей для офлайн-комплекта.
- **Режим бота задаётся явно**, а не «webhook с автоматическим фолбэком на опрос»: в закрытом контуре
  входящего доступа из интернета обычно нет, а при webhook адрес должен быть публичным https — такой выбор
  делает администратор. По умолчанию — опрос.
- **Защита от повторной отправки ответа** — отметка в NATS KV после успешной отправки + уникальный
  `Nats-Msg-Id` статуса. Окно дубля остаётся только при аварийном падении процесса между отправкой во внешний
  канал и отметкой (у Telegram и SMTP нет ключа идемпотентности); при корректной остановке текущая отправка
  завершается и подтверждается — проверено тестом обновления. Таймауты SMTP (15/15/30 с) меньше `ack_wait`
  потока (60 с), иначе зависшее соединение приводило бы к повторной доставке команды другому экземпляру.
- **Порядок исходящих между экземплярами** не гарантируется строго: два ответа оператора подряд в один чат
  могут уйти в обратном порядке, если их заберут разные экземпляры коннектора (в тесте обновления не
  наблюдалось; для email порядок не важен, для Telegram — редкая перестановка соседних сообщений).
- **Статус «Подключён» в режиме опроса** ставился только после первого long-poll (до 20 с без сообщений) —
  найдено e2e; теперь сразу после успешной проверки токена.
- **Двойная лицензия `@zone-eu/mailsplit`** (зависимость mailparser): `MIT OR EUPL-1.1+` — используется на
  условиях MIT, добавлена в список допустимых в `ops/licenses/check.mjs`.
- `PUBLIC_BASE_URL=''` из compose ломал запуск (пустая строка — не URL): пустое значение трактуется как
  «не задано».

**Известные ограничения**

- Размер входящих вложений коннекторами не ограничивается (у Telegram Bot API — не больше 20 МБ на файл,
  у почты — лимит почтового сервера); письмо целиком читается в память. Для MVP приемлемо; лимит и пометку
  «вложение слишком большое» — при необходимости.
- Telegram: только личные чаты; стикеры, голосовые, видео, геолокация не принимаются (пропускаются без
  создания сообщения). Исходящие — текст и файлы как документы (без альбомов/форматирования).
- Email: ответы — только текстом (`text/plain`), без HTML-шаблона и подписи; тема ответа — от первого письма
  обращения. Удаление писем из ящика после приёма не делается (только флаг «прочитано»).
- Смена `SECRETS_KEY` требует повторного ввода секретов каналов (статус канала — «ошибка: не удалось
  расшифровать»); ротация ключа с перешифрованием — отдельная задача.
- Повторная отправка «не доставленного» ответа из интерфейса оператора не сделана — оператор пишет ответ заново.

**Решения и находки**

- **Не все таймеры — через pg-boss, хотя pg-boss введён именно в этой фазе.** Таймаут принятия
  оператором заведён через pg-boss (`router.offer-timeout`): он создаётся и потребляется самим router, без
  межсервисных зависимостей. У перелива, эскалации, автовозврата из постобработки и отложенного перезвона
  дедлайн уже хранится в столбце (`queued_at`+`overflow_after_s`/`max_wait_s`, `wrap_up_until`, `callback_at`);
  их обрабатывает периодический опрос router (раз в `ROUTER_POLL_INTERVAL_MS`, по умолчанию 300 мс) —
  состояние переживает перезапуск/замену экземпляра точно так же, как задача pg-boss, но без необходимости
  заводить pg-boss-клиент ещё и в api/worker только ради планирования этих задач при постановке в очередь.
  Это отступление от буквального прочтения 02-архитектуры (6.2 п.6: «таймауты… перелив… — задачи pg-boss»),
  оставляющее тот же инвариант (дедлайн — данные, не память процесса); при появлении второго потребителя
  pg-boss (Ф8: ежедневная рассылка по срокам тикетов) стоит пересмотреть в пользу единообразия.
- **Ёмкость оператора — гонка при конкурентных экземплярах router.** Проверка «есть ли ещё место у
  оператора» по прочитанному вне блокировки счётчику пропускает конкурентное превышение (нашёл интеграционный
  тест на 5 параллельных тиков: у одного оператора набралось 6 при лимите 5). Исправлено: перед назначением
  строка `agent_status` выбранного оператора блокируется `FOR UPDATE`, счётчик активных обращений
  пересчитывается уже под блокировкой.
- **Навык по теме — мягкий приоритет, а не фильтр.** Если у темы обращения есть привязанный навык
  (`skill.topic_id`), но ни у кого из готовых операторов очереди нет соответствующей записи в `user_skill`,
  жёсткий фильтр оставил бы обращение без кандидатов вовсе. Навык влияет только на ранжирование внутри
  стратегии (как тай-брейк), не на состав кандидатов — состав определяет членство в очереди (`user_queue`).
- **«Взять» из очереди не заменено автоматическим распределением, а дополняет его** (в плане Ф2 это было
  временным решением до Ф3). И то и другое работает на одной и той же атомарной проверке
  `status = 'queued'`, поэтому не может привести к двойному назначению: кто первый — ручной перехват
  оператором/супервизором или очередной тик router — тот и получает обращение.
- **Лимит частоты клиентского API в нагрузочном тесте.** Пока разбирался нагрузочный автотест
  `route-under-rollout.mjs`: клиентский API создаёт не больше 10 сессий в минуту с одного адреса (M-CH-03,
  уже было в Ф2) — обычная нагрузка теста должна заводить сессии заранее и не чаще этого лимита, иначе часть
  просто получает 429.
- Найдена и исправлена скрытая гонка в интеграционных тестах api и router: `pg.Pool`, созданный в
  `it/setup.ts`, без обработчика `'error'` иногда аварийно завершал процесс Vitest при `DROP DATABASE …
WITH (FORCE)` в `cleanup()` (сервер обрывает ещё закрывающиеся простаивающие соединения) — заметно только
  при параллельном запуске нескольких пакетов интеграционных тестов. Добавлен `pool.on('error', () => {})` в
  обоих `it/setup.ts`.
- **Статус оператора при закрытии и ручном «Взять» (найдено при ревью).** Первая версия переводила в
  «Постобработка» любого, кто закрыл обращение, — в том числе оператора на перерыве и супервизора, закрывшего
  чужое; через `wrap_up_s` router делал их «Готов», и они начинали получать обращения. А «Взять» у оператора без
  записи статуса создавало её сразу со статусом «Готов». Теперь постобработка — только для своего обращения и
  только из «Готов»/«Постобработка», а «Взять» лишь отмечает `last_assigned_at`. Покрыто интеграционным тестом api.
- **Служебные уведомления ACD — внутренние заметки.** «Оператор не принял вовремя», «перелив в резервную
  группу», «наступило время перезвона» пишутся как `note` (клиент их не видит); клиенту уходят только
  «Оператор … подключился к диалогу» и «Мы свяжемся с вами …» (время — Europe/Minsk).
- Squawk: `adding-foreign-key-constraint` и `require-concurrent-index-creation` добавлены в исключения CI —
  по той же причине, что и уже исключённые `prefer-robust-stmts`/`require-timeout-settings`: раннер миграций
  (`packages/db/src/migrate.ts`) выполняет файл миграции одной транзакцией, а `CREATE INDEX CONCURRENTLY` и
  раздельные `NOT VALID`/`VALIDATE` для внешнего ключа требуют выполнения вне транзакции/в нескольких
  транзакциях. При масштабе MVP (локальный/демонстрационный стенд) кратковременная блокировка записи в
  expand-миграции приемлема.

**Известные ограничения**

- Ёмкость операторов (`operator.max_chats`) и статус влияют только на текстовые каналы (`channel_kind <>
'voice'`) — голосовая ёмкость и связанные приоритеты появятся в Ф5.
- Панель супервизора — опрос раз в несколько секунд, а не push через WebSocket (M-REP-02 отмечена [УПР] в
  требованиях); полноценная витрина реального времени и пороги/подсветка — доработка Ф10.
- Вкладка «Перезвонить» как отдельный список задач (упомянута в плане Ф2 для Ф6/Ф8) не заведена: отложенное
  обращение по наступлении срока возвращается в ту же очередь и просто появляется в «Мои»/«Очередь» — этого
  достаточно для M-CARD-05 в MVP.
- Пропущенное предложение (таймаут) не меняет статус оператора: отошедший от рабочего места оператор
  остаётся «Готов» и продолжает получать предложения по очереди с другими (каждое — задержка `offer_timeout_s`
  для клиента). Обычная практика ACD — после N пропусков подряд переводить в «Не готов»; нужно решение
  заказчика (записать в 04 при следующей фазе).
- Если все подходящие операторы отказались от обращения, router больше его не предлагает — оно остаётся во
  вкладке «Очередь» до ручного «Взять» (оператором или супервизором).
- Правила маршрутизации текста проверяются только по телу первого сообщения обращения (создание); смена
  темы/канала обращения задним числом их не пересчитывает.

- **worker** (новый сервис): поток `CC_INBOUND` → клиент по идентификатору → открытое обращение или новое в очереди
  канала → сообщение. Подтверждение только после записи в БД; повторная доставка не создаёт дублей; сообщения
  одного клиента обрабатываются последовательно (advisory lock).
- **realtime** (новый сервис): WebSocket операторов и клиентов; события — из `CC_EVENTS`; оператору — по правам и
  области видимости, клиенту — только его диалоги и никогда внутренние заметки; «печатает…» в обе стороны;
  проверка отзыва сессии; при остановке — код 1012 и переподключение к другому экземпляру.
- **Клиентский API** (`/api/v1/client`, он же «коннектор» веб-чата): настройки виджета, сессия с согласием на
  обработку ПДн (версия текста, IP), разрешённые сайты (CORS), ограничение частоты, сообщения с идемпотентным
  `clientMessageId` (ответ клиенту — после записи в JetStream R3), вложения; чат в приложении с подписью
  пользователя приложения (HMAC).
- **Операторский API**: вкладки «Мои / Очередь / Все открытые / Закрытые», «Взять» (с лимитом одновременных чатов),
  ответы, внутренние заметки, вложения, классификация (тема → автоматически «особо важное», предприятие,
  подразделение, объект, поля темы, теги, срочность), передача оператору или в очередь, закрытие с результатом
  (тема и обязательные «при закрытии» поля проверяются), карточка клиента и кросс-канальная история. Области
  видимости применяются к обращениям (прямой доступ к чужому — 404).
- **Виджет** (`apps/widget`, Preact, 22 КБ, Shadow DOM): встраивание одним `<script>`, согласие, вложения,
  повторная отправка без дублей, переподключение с догрузкой, «печатает…»; `/widget/demo.html` и
  `/widget/mobile.html` для WebView приложения.
- **Веб**: рабочее место оператора (3 панели, realtime, уведомления звуком/в заголовке/системные), раздел «Каналы».

**Решения и находки**

- Клиентский API выступает коннектором веб-чата: публикует во входящий поток, а не пишет в БД напрямую — единый путь
  для всех каналов (Ф4 добавит Telegram и email по тому же контракту).
- Порядок показа сообщений — по времени приёма системой (`sent_at`), синхронизация — по нему же: при параллельной
  обработке двумя экземплярами worker порядок не нарушается.
- `text/plain` принимается как байты (не строка): иначе загрузка текстовых файлов ломалась (найдено e2e-тестом).
- Результаты «Передать на 2-ю линию» и «Отложено / перезвонить» пока отклоняются с пояснением: передача — Ф8,
  отложенные обращения с напоминанием — Ф3 (нужны таймеры pg-boss).

**Известные ограничения**

- Распределение — ручное («Взять»); автоматическое — Ф3. Ограничение частоты сообщений — в памяти экземпляра.
- Антивирусная проверка вложений — позже (FS-SEC-03); опасные расширения отклоняются.

**Решения и находки**

- **Маршруты Traefik перенесены из меток контейнеров в файл `infra/traefik/dynamic.yml`.** При поэтапном обновлении
  старые и новые контейнеры работают одновременно; если метки маршрутов у них различаются, Traefik считает это
  конфликтом и снимает маршрут (получили сотни ответов 404). Теперь метки описывают только сервис (порт, проверку
  готовности), а маршруты и повторы не зависят от версии контейнера.
- Статика (nginx) останавливается так же корректно, как api: `/healthz` → 503, пауза, плавное завершение с лимитом.
- `jose` 5 (поддержка CommonJS), argon2 — `hash-wasm` (без нативных модулей: одинаково на любой платформе и в офлайн-сборке).
- Роль и ответственность разделены: роль — «что умеет», строка матрицы — «за что отвечает» (02-архитектура, 5.1).
- По умолчанию новый сотрудник видит «всё» (В-34); ограничение — областями.
