# Контакт-центр — MVP

Омниканальный контакт-центр: телефония и IVR, текстовые каналы, единое рабочее место оператора,
вторая линия с согласованием, обновления без остановки обработки обращений.

Требования, архитектура и план — в [`../Контакт-центр/planning/`](../Контакт-центр/planning/).
Журнал выполненных фаз — [`docs/PROGRESS.md`](docs/PROGRESS.md). Руководства: [развёртывание](docs/руководство-развёртывания.md),
[администратор](docs/руководство-администратора.md), [оператор](docs/руководство-оператора.md),
[регламент обновления](docs/регламент-обновления.md), [сценарий демонстрации](docs/сценарий-демонстрации.md),
[соответствие требованиям](docs/соответствие-требованиям.md).

## Быстрый старт

Нужны: Node.js 22, pnpm 10, Docker с Compose (Docker Engine 29+ требует Traefik 3.6+, он и используется).
Демо-стенд одной командой — `ops/demo.sh up` (сборка образов, демо-данные, заглушки внешних систем; сценарий показа —
[docs/сценарий-демонстрации.md](docs/сценарий-демонстрации.md)). Рабочий сервер — по
[руководству по развёртыванию](docs/руководство-развёртывания.md).

```bash
cd mvp
ops/build-images.sh dev                                   # сборка кода и образов cc/api:dev, cc/web:dev
SEED_DEMO=true BOOTSTRAP_ADMIN_PASSWORD='Admin12345!' \
  docker compose -f infra/compose/docker-compose.yml up -d --wait
# интерфейс: https://localhost  (самоподписанный сертификат)
# демо-сайт с виджетом чата: https://localhost/widget/demo.html
docker compose -f infra/compose/docker-compose.yml --profile observability up -d   # Prometheus :9090, Grafana :3001
```

Учётные записи демо-стенда (`SEED_DEMO=true`, пароль `Demo12345!`, задаётся `DEMO_PASSWORD`):

| Вход                                                                                  | Роль                                             |
| ------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `admin@cc.local` / `BOOTSTRAP_ADMIN_PASSWORD`                                         | Администратор                                    |
| `supervisor@demo.local`                                                               | Супервизор, область — только предприятие «Север» |
| `operator1@demo.local` … `operator3@demo.local`                                       | Операторы                                        |
| `resp1@demo.local` … `resp4@demo.local`, `curator1@demo.local`, `curator2@demo.local` | Ответственные и кураторы 2-й линии               |

На сервере обязательно задайте в `infra/compose/.env` свои `JWT_SECRET`, `POSTGRES_PASSWORD`, `BOOTSTRAP_ADMIN_PASSWORD`
и `SECRETS_KEY` (ключ шифрования токенов ботов и паролей почты в БД, не короче 16 символов; при его смене секреты
каналов нужно ввести заново). Для Telegram-ботов в режиме webhook — `PUBLIC_BASE_URL` (внешний https-адрес КЦ,
Telegram будет присылать сообщения на `<адрес>/tg/<id канала>`); режим опроса (по умолчанию) входящего доступа из
интернета не требует, нужен только исходящий доступ к `api.telegram.org` (или локальный Bot API-сервер).

Каналы Telegram и email добавляются в «Администрирование → Каналы» и начинают работать без перезапуска; там же —
состояние подключения и журнал обмена канала. Проверить Telegram и почту на стенде без интернета:

```bash
APPS="mock-telegram" ops/build-images.sh dev
export COMPOSE_PROFILES=test PUBLIC_BASE_URL=https://traefik
docker compose -f infra/compose/docker-compose.yml up -d --wait
# мок Telegram: адрес Bot API в настройке бота — http://mock-telegram:3000; «клиент пишет боту»:
curl -X POST http://127.0.0.1:8081/__test/<токен>/message -H 'content-type: application/json' \
  -d '{"chatId": 1001, "text": "Здравствуйте", "firstName": "Иван"}'
# GreenMail: IMAP mail:3143, SMTP mail:3025 без TLS, пароль любой; снаружи — 127.0.0.1:3143/3025
```

## Телефония (Ф5)

Звонки идут через Kamailio (SIP-периметр) на два узла Asterisk; логикой вызовов управляет `call-control`.
Софтфон оператора (JsSIP) встроен в интерфейс и регистрируется сам после входа — нужны HTTPS и разрешение на
микрофон. Проверить без SIP-транка:

- демо-страница **https://localhost/demo-call** — «клиент звонит в КЦ» из браузера на номер 1000 (голосовой
  канал «Телефон (демо)»); оператор в статусе «Готов» получает звонок в софтфон;
- генератор вызовов SIPp: `docker run --rm --network cc -v $PWD/ops/test/sipp:/s ctaloi/sipp -sf /s/uac-call.xml kamailio:5060 -s 1000 -m 1 -d 30000`.

Порты сервера: **8443/tcp** — WSS Kamailio для браузеров (в обход Traefik; на сервере смонтируйте сертификат
домена в том `sipcerts`: `cert.pem`, `key.pem`; с самоподписанным сертификатом браузер один раз должен открыть
https://<адрес>:8443 и принять его), **5060/udp** — SIP-транк, 3478/3479 — TURN. Переменные (`infra/compose/.env`):

| Переменная                                  | Назначение                                                                                           |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `SIP_SECRET`, `ARI_PASSWORD`, `TURN_SECRET` | Секреты SIP-учётных данных операторов (общий api и Kamailio), ARI узлов Asterisk, TURN — задать свои |
| `SIP_DOMAIN`                                | SIP-домен (по умолчанию `cc.local`)                                                                  |
| `TRUNK_HOST`                                | Адрес SIP-транка оператора связи для исходящих (`host:port`); пусто — исходящие наружу недоступны    |
| `MEDIA_EXTERNAL_ADDRESS`, `TURN_URLS`       | Для удалённых операторов за NAT: внешний адрес медиа узлов и адреса TURN (`turn:<адрес>:3478,…`)     |

Номера, на которые звонят клиенты (DID), задаются у голосового канала в «Администрирование → Каналы».

Звук и гарнитура — кнопка **«Звук»** в софтфоне: выбор микрофона, динамика разговора и устройства для звонка,
индикатор уровня микрофона, тест динамика/звонка, обработка звука (эхо, шум, АРУ). Выбор сохраняется в браузере;
при отключении гарнитуры звонок продолжается на устройстве по умолчанию, при возврате — снова на гарнитуре.
Кнопки проводных гарнитур (Jabra и др. со стандартной HID Telephony page) — через WebHID: «Подключить гарнитуру»
в том же окне (один раз). Горячие клавиши: **Ctrl+Alt+A** — ответить, **Ctrl+Alt+H** — завершить,
**Ctrl+Alt+M** — микрофон. Во время разговора показывается качество связи; при сбое сети — ICE restart.
Чек-лист ручной проверки гарнитур — `docs/PROGRESS.md`, раздел Ф5b.

## IVR (Ф6)

Сценарии настраиваются в **«Администрирование → Сценарии IVR»** без программирования: узлы (фраза, меню,
расписание, условие, очередь, голосовое сообщение, запрос во внешнюю систему, озвучивание числа, перевод, оценка,
завершение) соединяются мышью; «Тестовый прогон» проходит сценарий в браузере; «Опубликовать» — атомарно, идущие
звонки доигрывают свою версию; «Версии» — откат. Сценарий отвечает на номера (DID), указанные в его свойствах.

- Фразы — «Аудиобиблиотека» (любой аудиофайл переводится в формат телефонии в браузере; там же — фрагменты
  чисел для озвучивания сумм); «Объявления о сбоях» включает и выключает супервизор без правки сценария.
- «Интеграции» — HTTP-операции внешних систем (URL-шаблон, авторизация, маппинг ответа в переменные, таймаут,
  значения при ошибке); используются в IVR и в карточке клиента («Данные из внешних систем»).
- Демо-стенд (`SEED_DEMO=true`, профиль `demo` или `test` для мока самообслуживания): со страницы
  **https://localhost/demo-call** позвонить на номер **2000** — демо-сценарий «сеть АЗС»: объявление, меню
  («1» — бонусы → «1» — баланс, «2» — топливные карты, «0» — оператор, «\*» — назад), после разговора — оценка
  1–5; номер 1000 — сразу в очередь.

```bash
APPS="mock-selfservice" ops/build-images.sh dev
COMPOSE_PROFILES=demo SEED_DEMO=true BOOTSTRAP_ADMIN_PASSWORD='Admin12345!' \
  docker compose -f infra/compose/docker-compose.yml up -d --wait
```

## Автоответы, боты, подсказки (Ф7)

- **«Шаблоны ответов»** — общие (администратор) и личные (любой оператор), по темам и каналам, с переменными
  `{{client.name}}`, `{{operator.name}}`, `{{conversation.topic}}`; в поле ответа — `/код` и Enter.
- **«База знаний»** — рубрики и статьи (полнотекстовый поиск PostgreSQL по-русски, темы, ключевые слова).
- **«Автоответы»** — приветствие, «вы в очереди», нерабочее время по расписанию, ответ на ключевые слова,
  автозакрытие при молчании клиента; по каналам; действуют сразу после сохранения.
- **«Боты»** — текстовые сценарии на том же конструкторе, что IVR: сообщение, меню кнопками, сбор поля (телефон,
  email, число — с проверкой и записью в карточку), запрос во внешнюю систему, условия, расписание, перевод на
  оператора (очередь, тема, приоритет), завершение; тестовый прогон в виде чата. Бот назначается каналу в «Каналах».
- **Панель подсказок** в рабочем месте оператора: шаблоны и статьи БЗ по последним сообщениям клиента и теме,
  ответы ИИ-провайдеров; «Вставить» — одним кликом; «Черновик (ИИ)» — черновик от LLM.
- **«Подсказки: провайдеры»** — встроенный (всегда), LLM по OpenAI-совместимому API (локальный vLLM/Ollama;
  адреса вне контура запрещены без явного разрешения), внешний провайдер по контракту Assist API
  (`packages/contracts/src/assist.ts`); «Проверить связь»; включение/выключение — без перезапуска.
- Демо: **https://localhost/widget/demo.html?key=demo-webchat-bot** — чат с ботом (кнопки → телефон → баланс из мока
  → оператор); провайдер «LLM (локальная модель, демо)» (мок в `mock-selfservice`) выключен — включить в
  «Подсказки: провайдеры». После закрытия чата оператором виджет предлагает оценку 1–5.

## Вторая линия (Ф8)

- Оператор: результат обработки **«Передать на 2-ю линию»** → форма: предприятие и подразделение, тема, суть;
  ответственные, кураторы и срок подставляются по матрице (можно заменить людей и срок); без ответственного тикет
  не сохраняется. Клиенту в текстовых каналах уходит автосообщение (настройка в «Настройках»). Вкладки
  **«На согласовании»** (принять / вернуть на доработку; заместитель на период отсутствия) и **«Переданные»**.
- **«Кабинет 2-й линии»** (`/tickets`, роль «Ответственный / куратор»): быстрые фильтры, сроки цветом, выделение
  «я ответственный», предпросмотр и полный переход в обращение (переписка, документы, история); закрытие со
  способом ответа, сутью и документами, переадресация (пересчёт по матрице или ручной выбор). Система ответ клиенту
  не отправляет.
- **«Контроль 2-й линии»** (супервизор, администратор): все согласования в области, «требуют переназначения»,
  «Применить матрицу к открытым тикетам», заместители. Режим согласования («создатель» / «только супервизор») и
  время ежедневной рассылки — в «Настройках», действуют без перезапуска.
- Письма «Важно!» (`Importance: High`, `X-Priority: 1`) — при назначении, переадресации, возврате; ежедневно в 08:00
  (включая выходные) — «осталось N дней» / «просрочено на N дней». SMTP заказчика — переменные compose
  `TICKET_SMTP_HOST`, `TICKET_SMTP_PORT`, `TICKET_SMTP_SECURE`, `TICKET_SMTP_USER`, `TICKET_SMTP_PASSWORD`,
  `TICKET_SMTP_FROM`; ссылки в письмах — `PUBLIC_BASE_URL`. Для проверки с GreenMail (профиль `test`):
  `TICKET_SMTP_HOST=mail TICKET_SMTP_PORT=3025`, письма видны по IMAP `127.0.0.1:3143` (логин — адрес получателя).
- Демо: `operator1@demo.local` передаёт обращение из чата `/widget/demo.html`, `resp1@demo.local` …
  `resp4@demo.local`, `curator1@demo.local` — ответственные и кураторы, `supervisor@demo.local` — согласования
  «Севера».

## Публичный API, webhooks, внешние боты, экспорт конфигурации (Ф9)

- **«Ключи API»** — выпуск ключа (`cck_…`, показывается один раз) с правами `conversations.read`,
  `conversations.write`, `bot.reply`, `inbound` и областью видимости (предприятия); отзыв действует за секунды.
  Вызовы — `Authorization: Bearer cck_…` к `/api/v1/ext/*`; описание — **«Документация API»** (`/api-docs`) и
  `GET /api/v1/openapi.json` (OpenAPI 3.1, с webhooks и проверкой подписи).
- **«Webhooks»** — подписки на события (`conversation.closed`, `message.created`, `recording.ready`, `ticket.*` …,
  фильтр по каналам), подпись `X-CC-Signature: sha256=HMAC(секрет, "<X-CC-Timestamp>.<тело>")`, кнопка «Тест»,
  журнал доставки, «Повторить сейчас». Упавший получатель не влияет на операторов: события копятся, повторы — с
  растущей задержкой одной пробной доставкой (`WEBHOOK_MAX_BACKOFF_S`, по умолчанию 300 с), после восстановления
  очередь уходит сразу; доставка ждёт до `WEBHOOK_MAX_AGE_H` (72 ч).
- **Внешний канал** — канал типа «Внешняя система (API)» + ключ с правом `inbound`: `POST /api/v1/ext/inbound`
  превращает сообщение сторонней системы (форма сайта, CRM) в обращение; ответы операторов — webhook
  `message.created` с фильтром по этому каналу.
- **«Внешний бот (Bot Gateway)»** — бот внешней системы назначается каналу («Каналы» → «Внешний бот»): получает
  `conversation.bot_turn` на каждое сообщение клиента, отвечает `POST …/ext/conversations/:id/messages` (с
  кнопками) и `…/handoff`; не ответил за заданное время — диалог уходит оператору.
- **Анализ завершённых обращений** — подписка на `conversation.closed`/`recording.ready`, результат —
  `PATCH /api/v1/ext/conversations/:id` (поля, теги, заметка); оператор видит заметку и блок «Данные внешних систем».
- **«Экспорт и импорт»** — JSON-файл конфигурации (темы и поля, очереди, навыки, расписания, справочники, правила,
  IVR и боты с версиями и аудиофразами, интеграции без секретов, шаблоны, база знаний, настройки); импорт —
  сначала проверка с отчётом, затем применение одной транзакцией, без перезапуска.
- Демо-стенд (`SEED_DEMO=true`, профиль `test`/`demo`): подписка «Демо: анализатор» (выключена — включите в
  «Webhooks», закройте чат и увидите результат анализа в карточке), чат с внешним эхо-ботом
  `/widget/demo.html?key=demo-webchat-extbot`, канал «Форма сайта (API, демо)» с ключом
  `cck_demo_form_key_change_me_0123456789abcd` (демо-ключи задаются `DEMO_*_API_KEY` у сервиса migrate и мока).
  Мок (`127.0.0.1:8082`): `GET /hooks/<имя>` — что пришло, `POST /control {"down":true}` — «получатель упал».

## Отчёты и панель супервизора (Ф10)

- **«Супервизор»** (право `supervisor.monitor`) — панель реального времени: сводка (ожидают, дольше всех ждёт,
  операторы по статусам, отвечено/пропущено сегодня, активные обращения по статусам), очереди (ожидают, особо
  важные в очереди, предложено/в работе, **SL за сегодня**), операторы (статус, сколько в статусе, чаты, звонок,
  «Прослушать»). Подсветка — по порогам «Настройки → Панель супервизора и отчёты» (`supervisor.thresholds`),
  применяются без перезапуска. Обращения — в области видимости супервизора. Опрос раз в 4 с.
- **«Отчёты»** (право `reports.view` — администратор и супервизор): обращения по каналам/темам/результатам, SL и
  пропущенные, ASA/AHT, первый ответ в чатах, загрузка и статусы операторов, CSAT, 2-я линия по предприятиям и
  подразделениям (в срок, просрочка, возвраты, время решения, ожидание согласования, способы ответа, прямые
  переводы; разрез по ответственным и кураторам), реестр просроченных тикетов. Фильтры: период (даты по Минску),
  канал, очередь, предприятие, подразделение, тема/подтема, объект, оператор, ответственный/куратор, быстрый
  фильтр «Особо важные». «Скачать CSV» — `;`, UTF-8 с BOM, десятичная запятая (открывается в Excel); выгрузка
  пишется в аудит.
- API: `GET /api/v1/reports` (каталог), `GET /api/v1/reports/options` (значения фильтров),
  `GET /api/v1/reports/<вид>?from=ГГГГ-ММ-ДД&to=…&groupBy=…&format=csv`. Все отчёты, кроме реестра, считаются по
  журналу `event` (история статусов обращения, `agent.status_changed`, `ticket.*`); данные ограничены областью
  видимости (`scopeFilter`), ответственный/куратор видит свои тикеты.
- Параметры расчёта (Настройки): порог SL для голоса и текста (`report.sl_voice_s`, `report.sl_text_s`) и по очереди
  (`report.sl_queue_thresholds`), короткий сброс (`report.short_abandon_s`) и учитывать ли короткие сбросы
  (`report.sl_count_short_abandons`) и возвраты в IVR/бот (`report.sl_count_ivr_returns`) в знаменателе, перевод —
  новое поступление (`report.sl_transfer_new_arrival`), «первый ответ вовремя» (`report.first_response_s`).

## Обновление без остановки (Ф11)

Порядок и процедуры по классам компонентов — **[docs/регламент-обновления.md](docs/регламент-обновления.md)**.

```bash
ops/build-images.sh v2                              # образы релиза (web переносит ресурсы работающей версии)
ops/release.sh v2                                   # предпроверки → expand-миграции → поэтапная замена → app.version
FEATURE_FLAGS=a,b MEDIA_TAG=v2 ops/release.sh v2    # + фиче-флаги после обновления, + Asterisk осушением
ops/release.sh --rollback v1                        # откат на образы предыдущего релиза (без миграций)
ops/update-media.sh coturn-1 coturn-2               # TURN: вывод из ICE-серверов, ожидание сессий, обновление
ops/update-media.sh nats-1 nats-2 nats-3            # NATS по одному (lame duck mode)
KAMAILIO_TAG=v2 ops/update-media.sh kamailio        # класс C: окно ≈ 7 с, разговоры продолжаются
pnpm compat:check --base release-v1                 # совместимость событий и OpenAPI с прошлым релизом
pnpm migrations:lint --base release-v1              # expand/contract, неизменность выпущенных миграций
```

- Интерфейс оператора узнаёт о новой версии (`/version.json`, событие `app.version`) и показывает «Доступна
  новая версия»; обновляется сам, когда нет звонка и неотправленного ответа (флаг `web.auto_reload`), во время
  звонка кнопка «Обновить» недоступна (M-OP-11). Образ web хранит ресурсы текущей и предыдущей версии.
- «Настройки» → фиче-флаги и журнал выпусков (`GET /api/v1/admin/releases`, `/api/v1/admin/feature-flags`).
- Миграции ждут блокировку не дольше `MIGRATION_LOCK_TIMEOUT_MS` (5 с) и повторяются; индексы на больших
  таблицах — `CREATE INDEX CONCURRENTLY` в файле с `-- cc:no-transaction`; удаление — только contract-миграцией
  следующего релиза с пометкой `-- contract-of: NNNN`.

Проверки под нагрузкой (стек с `SEED_DEMO=true`, профиль `test`):

```bash
MEDIA_TAG=v2 node ops/zero-downtime-test/run.mjs v2 # 10 операторов, 30 вызовов, 100 чатов во время выпуска v2
node ops/test/kamailio-restart.mjs                  # разговор переживает перезапуск Kamailio, BYE в обе стороны
```

## Доводка и приёмка (Ф12)

- **Права**: «видит неклассифицированные обращения» (без предприятия и темы) — у роли («Сотрудники» → «Роли») или
  отметкой у сотрудника («Области видимости»), В-52. **SL**: все параметры расчёта — в «Настройках» (В-51).
- **Безопасность**: вход с кодом (TOTP) — «Профиль» (щелчок по имени в шапке); обязательность для администраторов —
  «Настройки» (`security.admin_2fa_required`); сброс — карточка сотрудника. Сертификат домена — `TRAEFIK_TLS`
  (`infra/traefik/tls-certs.yml`, файлы в `infra/traefik/certs/`), адреса SIP-транка — `TRUNK_ALLOW`.
- **ПДн**: «Персональные данные» — реестр согласий, версии текстов (текст канала меняется только с новой версией),
  обезличивание клиента; обезличивание уволенного сотрудника — карточка сотрудника; срок хранения записей —
  «Настройки» (`recording.retention_days`, удаление раз в час); ПДн в логах маскируются (`LOG_PII=1` — отключить на
  стенде). В логах — сквозной `correlationId` (`x-request-id`), он же `traceId` событий.
- **Резервное копирование**:

```bash
ops/backup.sh                                   # БД + S3 + .env на работающей системе → out/backups/<дата-время>
ops/restore.sh --verify out/backups/<каталог>   # проверка: временная БД и бакет, сверка строк и sha256
CONFIRM=yes ops/restore.sh out/backups/<каталог> # полное восстановление (сервисы останавливаются)
node ops/test/backup-restore.mjs                # автотест: копия во время переписки, проверка, восстановление
ops/demo.sh up | reset | check | down           # демо-стенд; check — все e2e с пометкой «демо-сценарий»
```

## Работа без интернета (M-NFR-10)

```bash
ops/mirror/export.sh offline-bundle        # все Docker-образы + все npm-пакеты по lockfile
# перенести репозиторий и offline-bundle/ на сервер без интернета:
ops/mirror/import.sh offline-bundle
```

Образы приложений собираются без скачивания чего-либо внутри Docker. Лицензии зависимостей
проверяются в CI (`pnpm licenses:check`), в продукт допускаются только свободные бессрочные лицензии.
