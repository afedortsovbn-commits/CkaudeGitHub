# Выжимка: «Архитектура общая.pdf» (ChannelBox — описание архитектуры и Sizing)

Источник: `Контакт-центр/Архитектура общая.pdf`, 85 стр. Версия документа 2.0, февраль 2026, аудитория DevOps.
Стр. 49–85 — дубликат стр. 9–48 (та же редакция, отличия только в вёрстке таблиц).

## 1. О чём документ

- Инфраструктурное описание **ChannelBox Self-hosted Edition** (текстовые каналы: веб-виджет, Telegram, WhatsApp) — состав контейнеров, сеть, потоки запросов, масштабирование, бэкапы, обновления, внешние зависимости, чек-лист DevOps.
- Большая часть объёма — сайзинг по 5 конфигурациям (Pilot/Start/Standard/Medium/Large). Функциональности продукта (UI оператора, маршрутизация, IVR) документ почти не касается.
- Телефонии/OCP/HelpDesk в документе нет — только текстовый контур.

## 2. Компоненты и назначение

Архитектура целиком построена на стеке **Supabase** (self-hosted): 13 Docker-контейнеров в одном `docker-compose.yml`.

| Компонент | Назначение |
|---|---|
| `db` — PostgreSQL 15 + pgvector, pg_cron, pg_net | единственная БД: диалоги, сообщения, логи, векторные индексы (HNSW/IVFFlat) для RAG, планировщик задач; на схеме «~80 таблиц» |
| `kong` — API Gateway | единая точка входа для API, маршрутизация по path: `/rest/v1/*`, `/auth/v1/*`, `/realtime/v1/*`, `/storage/v1/*`, `/functions/v1/*` |
| `auth` — GoTrue | аутентификация, JWT, OAuth; шлёт email (подтверждение, сброс пароля, уведомления операторам) через SMTP |
| `rest` — PostgREST | автогенерируемый CRUD REST API из схемы БД |
| `realtime` | WebSocket-подписки на изменения БД (Postgres CDC / PubSub) — доставка событий в UI оператора |
| `storage` — storage-api | файловое хранилище (S3-совместимое; бэкенд — local FS или MinIO) для вложений, аватаров, экспортов |
| `imgproxy` | ресайз/оптимизация изображений |
| `functions` — Deno Edge Runtime | **вся бизнес-логика**: 50+ функций — боты, приём webhook каналов, вызовы LLM, интеграции |
| `supavisor` | пул соединений к PostgreSQL (transaction mode) |
| `meta`, `studio` | метаданные БД и админ-панель БД (dev/debug; в prod отключать/ограничивать) |
| `vector` (timber.io) | сбор и маршрутизация логов stdout/stderr всех контейнеров |
| `frontend` | React SPA — операторская панель (статика за Nginx) |
| внешний **Nginx** | reverse proxy: TLS-терминация, WebSocket upgrade, security headers; внутри трафик по HTTP |

- Два домена: `app.*` → Frontend (SPA), `api.*` → Kong (все backend-сервисы). Наружу только 80/443 (+22 SSH); все сервисы — внутренняя Docker-сеть.
- Таблицы, упомянутые как «на диалог»: `conversations`, `messages`, `chat_history`, `conversation_tags`, `chat_ratings`, `dialog_sessions`, `sla_events`.
- Таблицы логов: `cron_job_logs`, `external_api_logs`, `event_webhook_logs`, `external_channel_logs`.

## 3. Потоки данных и взаимодействия

- Открытие панели оператора: Client → Nginx → Frontend (SPA).
- Список диалогов: Client → Nginx → Kong → REST (PostgREST) → Supavisor → PostgreSQL.
- Отправка сообщения оператором: Client → Nginx → Kong → Functions → Supavisor → PostgreSQL → **Realtime** → Client (UI обновляется по WebSocket из изменения в БД).
- Загрузка файла: Client → Nginx → Kong → Storage → S3/MinIO.
- Входящее из канала (webhook Telegram): Telegram → Nginx → Kong → Functions → Supavisor → PostgreSQL.
- AI-ответ бота: Functions → внешний LLM API → Functions → PostgreSQL.
- Фоновые задачи: pg_cron → pg_net → Kong → Functions (HTTP-вызов из БД).
- Исходящие HTTPS из `functions`: LLM API (OpenAI, Anthropic и др.), Telegram Bot API, WhatsApp Business API (через провайдера); из `auth` — SMTP.
- [прим.] Модель «БД как шина событий»: запись в Postgres → Realtime пушит изменения в браузер; бизнес-логика — stateless-функции.

## 4. Функциональность, релевантная MVP

- **Каналы**: браузер/веб-виджет, Telegram (Bot API, webhook), WhatsApp Business API; email — только как уведомления/подтверждения через SMTP (не как канал обращений — в документе не описано).
- **Жизненный цикл диалога**: создание → назначение → обработка оператором/ботом → постобработка → закрытие; в среднем ~11.5 сообщений на диалог.
- **Очереди**: упоминаются только в чек-листе («первичная настройка: создание админа, настройка очередей, каналов»); алгоритмы маршрутизации не описаны.
- **SLA, теги, оценки**: есть сущности `sla_events`, `conversation_tags`, `chat_ratings`.
- **Боты / LLM / RAG**: AI-боты и RAG через внешние LLM-API, векторный поиск — pgvector в той же БД (HNSW/IVFFlat; поэтому SSD обязателен, на HDD латентность RAG в 5–10× выше). GPU не нужен.
- **Рабочее место оператора**: React SPA в браузере, realtime через WebSocket; вложения/скриншоты/документы через Storage, превью через imgproxy.
- **Отчёты**: упомянут «экспорт отчётов» (файлы в S3). Аналитика не описана.
- **Интеграции/API**: авто-REST (PostgREST) поверх схемы, Edge Functions как точка расширения, исходящие webhooks (`event_webhook_logs`), логирование внешних вызовов (`external_api_logs`).
- **Auth**: JWT, OAuth, apikey для API; email-подтверждение и сброс пароля.
- **Отказоустойчивость / HA** (крупные конфигурации): LB (HAProxy / Nginx Plus / Cloud LB) перед ≥2 App-серверами; **sticky sessions для WebSocket (Realtime)**; DB streaming replication + автофейловер (pg_auto_failover или Patroni); общий MinIO на отдельном сервере. Уровни масштабирования: all-in-one → App+DB → App+DB+S3/Logs → кластер.
- **Бэкапы**: pg_dump ежедневно, pg_basebackup еженедельно, WAL archiving (PITR), синхронизация S3 (rclone / mc mirror). RPO/RTO: от 24 ч / 1–2 ч (без реплики) до ~минут / 5–15 мин (реплика + PITR + автофейловер).
- **Обновления** — **с простоем**: `docker compose down` → `pull` → миграции (Ansible, tag `database`) → `up -d`. Downtime: патч образов 1–3 мин, миграции БД 5–15 мин, major PostgreSQL 30–60 мин. Рекомендации: окно минимальной нагрузки; для многосерверных конфигураций — rolling update App-серверов по одному; хранить предыдущие теги образов для отката.
  - [прим.] Это расходится с требованием заказчика zero/near-zero downtime: у образца нет blue-green, обратно совместимых миграций, graceful drain WebSocket — это придётся проектировать самим.
- **Мониторинг** (рекомендации): node_exporter + Prometheus (CPU, RAM, disk I/O), `pg_stat_activity` (соединения), `pg_stat_replication` (лаг реплики), рестарты контейнеров (`docker events`), срок SSL (blackbox_exporter). Healthcheck-эндпоинты: `/auth/v1/health`, `/functions/v1/health-check`.
- **Логи**: Vector собирает stdout; ротация 7 / 30 / 90 дней (dev / prod / compliance).

## 5. Технологии и протоколы (из документа)

- Supabase (GoTrue, PostgREST, Realtime, storage-api, edge-runtime/Deno, Supavisor, postgres-meta, Studio), Kong, PostgreSQL 15 + pgvector + pg_cron + pg_net, MinIO (S3), imgproxy, Vector, React SPA, Nginx.
- Docker Engine 24+, Docker Compose v2.20+, Ansible (установка и миграции), Ubuntu 22.04 / RHEL 8+ / Debian 12+.
- HTTPS/TLS 1.2+ (рекоменд. 1.3), WebSocket, REST, JWT, OAuth, webhooks, SMTP (587/465), S3 API.
- HA: HAProxy / Nginx Plus, Patroni / pg_auto_failover, PostgreSQL streaming replication, WAL archiving/PITR.
- Мониторинг: Prometheus, node_exporter, blackbox_exporter; Let's Encrypt/Certbot.
- Внешние: OpenAI/Anthropic API, Telegram Bot API, WhatsApp Business API.

## 6. Отброшено как нерелевантное

- Сайзинг (5 конфигураций, vCPU/RAM/SSD/HDD, RPS, формулы объёма БД/S3/логов, размеры бэкапов), IP-адресация, DNS-записи, UFW-правила, варианты SSL-сертификатов, платформы виртуализации, примеры cron/certbot-команд, чек-лист установки.
