# OCP — архитектура (выжимка из «OCP — Архитектура и сайзинг Self-hosted Edition», v2.0, фев. 2026, 66 стр.)

Источник: `OCP_—_Архитектура_и_сайзинг.pdf`. Аудитория документа — DevOps. Функциональных описаний (IVR-редактор, ACD-алгоритмы, карточка клиента, подсказки) в документе почти нет — только состав компонентов, потоки, развёртывание.

**Отброшено (сайзинг/лицензии):** разд. 0 (карточки Pilot/Start/Standard/Medium/Large), 3 (потребление RAM), 4.4 (IP по конфигурациям), 6–7 (vCPU/RAM/диски, формулы хранения), 10 (объёмы бэкапов), 13.4 (пороги алертов), Прил. A, план развёртывания 1.4 (лицензии SBC/DQL) — кроме функциональных фактов, извлечённых ниже.

## 1. Общий подход
- Микросервисная архитектура; Docker-контейнеры + системные сервисы; управление `docker-compose.yml` + Ansible (playbook, `group_vars/all.yml`).
- Self-hosted; ОС Linux (Ubuntu 22.04 / RHEL 8+ / Debian 12+); виртуализация любая. GPU не нужен — **LLM-инференс через внешние API** (OpenAI, Anthropic и др.).
- Единица нагрузки — «диалог»: создание → назначение → обработка оператором/ботом → постобработка → закрытие (~11.5 сообщений).

## 2. Слои и компоненты
| Слой | Компонент | Роль |
|---|---|---|
| Телефония | **SBC** (контейнер; фактически Oktell — пути `/var/lib/oktell`, портал Oktell) | SIP-обработка, **IVR**, маршрутизация вызовов, **запись разговоров**, hunt-группы (очереди), CDR, скрипт-редактор, ролевые приложения |
| Бизнес-логика | **OCP Backend** (:9999) | диалоги, очереди, операторы, API; интеграции с каналами и LLM |
| | **OCP Proxy** (:8888) | проксирование запросов между компонентами |
| | **OCP File API** (:19999) | загрузка/скачивание файлов, работа с S3 |
| | **OCP Migrations** | миграции схемы БД (запуск при обновлении) |
| Фронтенд | **OCP Frontend** — React SPA (Vite), статика через Nginx | операторская панель |
| Софтфон | WebRTC-софтфон, отдельный домен `softphone.*` (CDN/статика) | звонки из браузера оператора |
| БД | **PostgreSQL** (в prod — системный сервис, не контейнер) | общая СУБД |
| Файлы | **MinIO** (S3-совместимое) | вложения, аватары, экспорт |
| Edge | **Nginx** | SSL termination, reverse proxy на все сервисы; внутри — HTTP |
| Отчётность | **Apache Superset** (:8088) | дашборды, встраиваются в OCP через **iframe** |
| Мониторинг | Grafana + Loki + Prometheus + Alloy | логи (JSON), метрики, алерты |
| Опционально | Screen Recorder; Video Streaming (×2 контейнера, RTSP-медиасервер); Data Store / Storage API (экспорт данных); ClickHouse Sync (аналитика); Data Manager (`data.*`); интеграционные сервисы (`api.*`) | |

- Внешние каналы: Telegram Bot API (webhook), WhatsApp Business API, SMTP/email; внешние интеграции вызываются из контейнера `functions` (упомянут в таблице зависимостей) [прим.: вероятно, общий с HelpDesk функциональный слой].
- Производственный календарь (production-calendar.ru) — для расписаний/рабочего времени.
- Таблицы на диалог: `conversations, messages, chat_history, conversation_tags, chat_ratings, dialog_sessions, sla_events` → есть теги, оценки (CSAT), сессии, SLA-события.

## 3. Телефония / SIP / WebRTC
- SIP 5060 UDP/TCP (транки к провайдерам); **5063 TCP — SIP over TLS / WSS** для WebRTC-софтфона.
- Мастер-домен SBC (`studio.*`) — корневой FQDN инсталляции; **клиентские поддомены** (мультитенантность: клиент/филиал/БЕ) хранят свои сценарии IVR, маршрутизацию, шаблоны автонастройки; лимиты наследуются по дереву доменов.
- **Wildcard-сертификат `*.мастер-домен` обязателен для WebRTC** (иначе браузер блокирует HTTPS/WSS).
- Сеть: прямая маршрутизация SBC ↔ провайдер без NAT (NAT только для авторизованных транков); минимальные задержки между компонентами.
- Типы очередей SBC: hunt-группы `sip` (устройства) и `user` (пользователи); сущности: IVR-сценарии, служебные сценарии, **сценарии чат-ботов**, router, bridge (мост для интеграций), ESB, submaster-домены; каналы «нажми и звони» (click-to-call); веб-сервисы public/subscr.
- Коды абонентских функций, правила маршрутизации настраиваются через API SBC (плейбук).
- Регистрация устройств проверяется через SIP OPTIONS.
- Кодеки, SRTP, STUN/TURN — **в документе не упомянуты** [прим.: потребуется отдельный источник].

## 4. Запись разговоров
- SBC пишет разговоры в локальный каталог (WAV); Nginx на SBC раздаёт их по HTTP (`sbc-storage.*`); OCP хранит ссылки и даёт прослушивание в веб-интерфейсе.
- В кластере записи хранятся только на одном сервере SBC (техническое ограничение); нужна ротация; в планах — микросервис поиска записей по кластеру.
- Опционально: запись экранов операторов (клиент на рабочем месте + контейнеры видео, хранение в S3).

## 5. Интеграция OCP ↔ SBC
- Через SBC API: токены `SBC_DATA_CHANNEL_TOKEN` (DataChannel) и `SBC_IVR_TOKEN` (IVR), сервисная учётка; синхронизация пользователей и лицензий SBC.
- Параметры очередей в OCP: `QUEUES_WORKLOAD_PERIOD` (период пересчёта загрузки очередей), `DELAY_LIC_DEVICES`.
- Состояния оператора/CTI-события — детально не описаны [прим.].

## 6. Типовые потоки
- Панель: Client → Nginx → Frontend (SPA); данные/сообщения: Client → Nginx → Backend → PostgreSQL; файлы: → File API → MinIO.
- **Входящий звонок:** SIP-провайдер → SBC → IVR → Очередь → Оператор (через OCP).
- **Исходящий:** OCP Backend → SBC → SIP-провайдер.
- Telegram: webhook → Nginx → Backend → PostgreSQL.
- **AI-ответ бота:** Backend → внешний LLM API → Backend → PostgreSQL (LLM для AI-ботов и RAG).
- Запись: Client → Nginx → sbc-storage → файл.
- Отчёт: Client → OCP (iframe) → Superset → PostgreSQL (read). Встраивание по сервисному токену, без повторной аутентификации.
- Авторизация AD: Backend → AD (LDAP 389 / LDAPS 636 / GC 3268); синхронизация групп/ролей, автосоздание пользователя при первом входе, fallback на локальную аутентификацию.
- Realtime к оператору — WebSocket (sticky sessions на LB).

## 7. Интеграции
- CRM-коннекторы SBC: 1С, AmoCRM, Битрикс24, Bpium, BPMSoft, Creatio.
- Каналы: Telegram, WhatsApp Business, email (SMTP обязателен: подтверждение email, сброс пароля, уведомления операторам).
- Экспорт данных: Storage API; аналитика: ClickHouse Sync; внешний API ключ `API_KEY`; health-endpoint `/api/health`.

## 8. Отказоустойчивость и масштабирование
- Уровни: L1 all-in-one → L2 App+DB → L3 App+DB+S3/Logs (+реплика) → L4 кластер: 2× App (Nginx+SBC+Backend/Proxy/FileAPI/Frontend) за LB.
- HA-компоненты: LB (HAProxy / Nginx Plus / Cloud LB); PostgreSQL streaming replication + автофейловер (pg_auto_failover / Patroni; альтернатива Consul+Patroni, PgBouncer); **sticky sessions для WebSocket (SBC WebRTC)**; MinIO вынесен отдельно.
- **SBC-кластер: 4 узла**, «урезанные» кластерные функции для совместимости с софтфоном, требует поддержки кластера SIP-провайдером.
- Бэкап: pg_dump / pg_basebackup / WAL-архивирование (PITR) / S3 sync (rclone, mc mirror). RPO/RTO: от 24 ч/1–2 ч (single) до ~0/5–15 мин (реплика + автофейловер).

## 9. Обновления
- Процедура: бэкап → `docker compose down` → `pull` → миграции (Ansible tag `database`) → `up -d` → проверка health.
- Downtime: патч образов 1–3 мин; мажорное с миграциями 5–15 мин (требует остановки); major PostgreSQL 30–60 мин.
- Рекомендации: окно минимальной нагрузки; на Medium/Large — rolling update App-серверов по одному; хранить теги прежних образов для отката.
- [прим.] **Zero-downtime не обеспечен**: миграции требуют остановки, SBC в all-in-one перезапускается вместе с приложением → активные звонки рвутся. Для нашего MVP нужны: обратно-совместимые (expand/contract) миграции, graceful drain SIP/WS-сессий, раздельный жизненный цикл медиа-слоя и бизнес-логики.

## 10. Выводы для MVP [прим.]
- Ориентир: SBC отдельно + оркестратор диалогов + SPA + S3 + PostgreSQL + встраиваемая BI. Слабые места: запись на одном узле SBC, нет zero-downtime, проприетарный SBC (Oktell), отчёты через iframe.
