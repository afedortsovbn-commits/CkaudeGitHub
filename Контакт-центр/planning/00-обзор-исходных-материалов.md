## 3. Главные выводы по материалам

1. **Материалы описывают образцы, а не наш продукт.** OCP (телефония/IVR/КЦ), ChannelBox (текстовые каналы) и HelpDesk (2-я линия) — три отдельных коммерческих продукта. Мы делаем **один** продукт с единой моделью обращения, объединяющий их функции.
2. **Функциональные требования** берутся в основном из ТЗ и формы соответствия; архитектурные PDF полезны как ориентир (состав компонентов, каналы, статусы диалога, API-подходы), но не как образец для копирования.
3. **Образцы не решают ключевую задачу заказчика — обновление без простоя.** И ChannelBox, и OCP описывают простой 1–3 мин при обновлении образов и 5–15 мин при миграциях БД; rolling update только для app-серверов. Это требование проектируется нами с нуля (см. 02-архитектура, разд. 6).
4. **Текстовые образцы (ChannelBox, HelpDesk) построены на Supabase** (PostgreSQL + PostgREST + Realtime + Deno Edge Functions). Мы этот стек сознательно не повторяем: бизнес-логика в десятках edge-функций и связка «изменение БД → Realtime» усложняют контролируемые обновления и версионирование контрактов. Берём полезные идеи: PostgreSQL как основа, pgvector для RAG, объектное хранилище, webhooks, коннекторы каналов, OpenAI-совместимые LLM, MCP для ИИ-агентов (позже).
5. **Процесса «согласование закрытия / возврат на доработку» нет ни в одном документе** — он задан только указаниями заказчика и проектируется нами (см. 01, разд. 3.8).

## 4. Разрешённые противоречия между источниками

| Противоречие | Источники | Решение для MVP |
|---|---|---|
| Операторы в офисе без VPN vs удалённые операторы через браузер | ТЗ vs указания заказчика | Удалённая работа через браузер (WebRTC + TURN), офис — частный случай |
| Десктоп-софтфон vs только браузер | Форма vs указания | Только браузер; внешний SIP-софтфон — после MVP как опция (стандартный SIP, M-OP-05) |
| Email и WebRTC не упомянуты в ТЗ | ТЗ vs указания/форма | Email и WebRTC входят в MVP |
| LLM/транскрибация/речевая аналитика on-premise как обязательные | ТЗ | В MVP — только точки расширения и адаптер к OpenAI-совместимому API (локальный vLLM или иной); сами модели — позже |
| Колонка «обязательно/желательно» в форме пустая | Форма | Приоритеты расставлены нами по указаниям заказчика; вынесено в открытые вопросы |
| Много мессенджеров (Telegram, Viber, WhatsApp, VK, MAX…) | ТЗ, форма | В MVP — Telegram + механизм коннекторов; остальные — позже |
| Интеграции с SAP CRM/ERP и CRM B2B | ТЗ | В MVP — универсальный интеграционный слой + мок-сервис «баланс/история»; реальные коннекторы — позже |

## 5. Контекст заказчика (справочно)

По ТЗ — КЦ сети ~570 АЗС и ~1000 ЭЗС в Беларуси: 24/7, ~15 000 входящих + 5 000 исходящих звонков и ~1 000 текстовых обращений в месяц, AHT ≈ 2,5 мин, ≥30 одновременных вызовов, рост до 50+ операторов; строго on-premise; ПДн по закону РБ № 99-З. Этот домен используется в MVP как **демо-данные** (темы: топливо, бонусная программа, ЭЗС, топливные карты B2B…), но продукт проектируется универсальным (см. 04, вопрос В-01).
