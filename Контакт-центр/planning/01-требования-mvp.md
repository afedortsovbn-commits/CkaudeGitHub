# 01. Требования к MVP

Источник приоритетов: **указания заказчика** (Промпт.docx) > ТЗ (REQ-*) > форма соответствия (FS-*) > архитектурные документы-образцы.
Идентификаторы требований MVP: `M-<ОБЛ>-NN`. В скобках — трассировка к выжимкам в `sources/`.
Метки: **[MVP]** — делаем полностью; **[УПР]** — делаем упрощённо (что именно упрощено — указано); **[ПОЗЖЕ]** — вне MVP, но архитектура оставляет место.
Предположения помечены `[П]` и ссылаются на вопросы из [04-открытые-вопросы.md](04-открытые-вопросы.md) (`В-NN`).

## 1. Цель MVP

Показать на локальном/собственном сервере, что работает **весь основной сквозной функционал** омниканального КЦ:
клиент обращается по телефону, через веб-чат, чат в приложении, Telegram или email → IVR/бот → маршрутизация → оператор в едином веб-интерфейсе с подсказками и автоответами → при необходимости передача на 2-ю линию → согласование закрытия или возврат на доработку → оценка клиента → базовые отчёты.
И отдельно продемонстрировать: **обновление компонентов без остановки приёма и обработки обращений.**

Не цель MVP: промышленная эксплуатация, реальные интеграции с SAP/CRM заказчика, речевая аналитика, собственные ИИ-модели, нагрузочное подтверждение 50+ операторов.

## 2. Роли пользователей

| Роль | Что делает |
|---|---|
| Клиент | Обращается по каналам, проходит IVR/бота, оценивает обслуживание |
| Оператор 1-й линии | Обрабатывает звонки и чаты (до N одновременно), заполняет карточку, передаёт на 2-ю линию (выбирая предприятие и подразделение), принимает или возвращает на доработку ответы 2-й линии |
| Ответственный специалист (2-я линия) | Сотрудник предприятия, назначенный по матрице ответственности на тему/подтему в подразделении; в своём кабинете отвечает клиенту, закрывает или переадресует тикеты |
| Куратор (2-я линия) | Контролирует тикеты своих тем и подразделений; получает те же уведомления; при необходимости действует как ответственный |
| Супервизор | Мониторинг очередей и операторов в реальном времени, ручное назначение, прослушивание (упрощ.) |
| Администратор / менеджер КЦ | Настраивает всё: IVR, очереди, навыки, предприятия, подразделения, темы и поля, матрицу ответственности, объекты, шаблоны, автоответы, боты, каналы, интеграции, сотрудников, роли и области видимости |
| Внешняя система | Работает через API/webhooks (чат-боты сайта/приложения, самообслуживание, CRM, ИИ) |

## 3. Функциональные требования

### 3.1 Каналы и единое обращение (CH)
- **M-CH-01 [MVP]** Единая модель «обращение» (conversation) для всех каналов; единая история клиента по всем каналам. (REQ-CH-01, FS-OMNI-01)
- **M-CH-02 [MVP]** Голос: входящие и исходящие вызовы (подробно в 3.3).
- **M-CH-03 [MVP]** Веб-чат на сайте — встраиваемый виджет (JS-сниппет): несколько виджетов с привязкой к очереди, белый список доменов, вложения с лимитом размера, ограничение частоты. (REQ-CH-04, FS-WGT-01)
- **M-CH-04 [MVP]** Чат в мобильном приложении — тот же протокол виджета: WebView-встраивание и открытый Client Chat API (REST + WebSocket) для нативной реализации; идентификация клиента по токену авторизованной сессии приложения. (FS-WGT-02, REQ-INT-04)
- **M-CH-05 [MVP]** Мессенджер: Telegram (бот API, webhook или long-polling). `[П]` первый мессенджер — Telegram (В-02). **[ПОЗЖЕ]** WhatsApp, Viber, VK, MAX и др. — как новые коннекторы. (REQ-CH-03, FS-OMNI-02/03)
- **M-CH-06 [MVP]** Email: несколько ящиков (IMAP для приёма, SMTP для отправки), привязка ящика к очереди, группировка писем в треды по заголовкам In-Reply-To/References, индикация состояния подключения. (FS-OMNI-04)
- **M-CH-07 [MVP]** Подключение нового канала или экземпляра канала без правки ядра и без остановки системы: канал = коннектор + запись конфигурации; статус канала и журнал обмена. (FS-OMNI-05)
- **M-CH-08 [УПР]** Исходящие: ответ в любом канале, где у клиента есть идентификатор; исходящий звонок в 1 клик. Массовые рассылки — **[ПОЗЖЕ]**. (REQ-CH-05)
- **M-CH-09 [УПР]** Внешний канал по API с ключом (приём сообщений сторонней системы как обращений, например формы сайта). (FS-OMNI-07)
- **M-CH-10 [УПР]** **Отзывы с карт через Rocket Data** — у заказчика есть договор с интегратором Rocket Data, API будет предоставлено. Отзывы и оценки по объектам из Google Карт и Яндекс Карт загружаются из Rocket Data как обращения канала «Отзыв»: текст, оценка, автор, дата, площадка, объект → предприятие (M-ORG-06). Дальше они обрабатываются как обычные обращения, включая вторую линию. **Ответ на отзыв пишется в нашей системе и уходит в Rocket Data по API**, далее — на площадку. Выход в интернет из контура нужен только к API Rocket Data. Реализуется **отдельным этапом** (Ф13) после получения описания API (В-32).

### 3.2 Рабочее место оператора (OP) — единый веб-интерфейс
- **M-OP-01 [MVP]** Браузерное SPA, русский язык; три панели: список обращений / лента диалога (чат или звонок) / карточка клиента и обращения. (REQ-UI-01, FS-OP-01)
- **M-OP-02 [MVP]** Список обращений с вкладками: «Мои», «Очередь», «У бота», «Удержание», «Постобработка», «На согласовании» (ответы 2-й линии по тикетам, созданным этим оператором, M-TKT-09), «Переданные» (мои тикеты на 2-й линии со статусами и сроками); быстрый фильтр «Особо важные»; время ожидания, сортировка, фильтры, отметка «Срочное». (FS-OP-02)
- **M-OP-03 [MVP]** Одновременная работа с несколькими чатами (лимит на оператора настраивается, по умолчанию 5) и одним голосовым вызовом; учёт голоса при раздаче чатов. (REQ-UI-02, FS-RT-02)
- **M-OP-04 [MVP]** Статусы оператора: «Готов», «Перерыв» (с причиной из справочника), «Постобработка», «Офлайн»; автосмена при звонке; таймер статуса. (FS-OP-05)
- **M-OP-05 [MVP]** Встроенный софтфон: ответ, отбой, удержание с музыкой, mute, DTMF, слепой перевод на оператора/очередь; консультативный перевод — **[УПР]** (желательно в MVP, допускается перенос). Индикация регистрации и качества соединения, автоматическое переподключение сигнализации; восстановление медиа при смене сети — best effort. Внешний SIP-софтфон вместо встроенного — **[ПОЗЖЕ]** (технически возможен через Kamailio, в MVP не тестируется). (REQ-TEL-10/11, FS-TEL-01/03)
- **M-OP-06 [MVP]** Гарнитуры проводные (USB/3,5 мм) и беспроводные (Bluetooth, DECT-базы): выбор микрофона, динамика и отдельного устройства для звонка-рингтона; сохранение выбора; горячее подключение/отключение устройства во время работы (в т.ч. автоматический переход на другое устройство при потере Bluetooth) с уведомлением; тест микрофона/динамика. (REQ-UI-08, FS-TEL-04)
- **M-OP-07 [MVP]** Любая гарнитура, которую видит ОС, работает как аудиоустройство (M-OP-06). Кнопки гарнитуры (ответ/отбой/mute, индикаторы) — через WebHID в Chromium-браузерах: основной ориентир — **проводные гарнитуры Jabra** (стандартная HID Telephony-страница, при необходимости — официальный JS SDK Jabra поверх WebHID); у других производителей кнопки работают, если гарнитура поддерживает стандартную HID Telephony-страницу. Если нет — управление из интерфейса и горячими клавишами. (В-07)
- **M-OP-08 [MVP]** Передача обращения другому оператору/в очередь с контекстом; внутренние заметки; поиск по обращениям и клиентам. (FS-OP-03)
- **M-OP-09 [MVP]** Уведомления: звук, мигание вкладки, системное уведомление браузера. (FS-OP-06)
- **M-OP-10 [MVP]** Панель подсказок: подходящие шаблоны ответов, статьи базы знаний, предложения от подключённых ИИ-провайдеров; вставка в ответ одним кликом (см. 3.6).
- **M-OP-11 [MVP]** Обновление интерфейса не прерывает работу: новая версия SPA подхватывается по кнопке «Обновить» (недоступна во время активного звонка) или автоматически, когда у оператора нет активного звонка и неотправленного черновика (см. 02, разд. 6.2).
- **M-OP-12 [ПОЗЖЕ]** Реакции/эмодзи, правка сообщений, тёмная тема, внутренний чат, PWA, TTS-озвучивание текста оператора (REQ-UI-06, FS-OP-08).

### 3.3 Телефония (TEL)
- **M-TEL-01 [MVP]** SIP (RFC 3261) — подключение SIP-транков операторов связи конфигурацией; несколько транков с приоритетом/резервом. **Провайдер — МТС (Беларусь)**; параметры транка заказчик предоставит в ближайшие дни. До их получения — демо-страница «Позвонить в КЦ» (WebRTC) и генератор вызовов SIPp (В-06). (REQ-TEL-01/03)
- **M-TEL-02 [MVP]** WebRTC для операторов (SIP over WSS, DTLS-SRTP), NAT-обход через STUN/TURN для удалённых операторов.
- **M-TEL-03 [MVP]** Кодеки: Opus (браузер), G.711 (транки); G.729 — **[ПОЗЖЕ]** по необходимости. (REQ-TEL-02)
- **M-TEL-04 [MVP]** Запись всех разговоров в объектное хранилище с привязкой к обращению; прослушивание в карточке с правами доступа. (REQ-QA-01, FS-TEL-07)
- **M-TEL-05 [MVP]** Журнал вызовов (CDR): стадии, длительности (ожидание, разговор, постобработка), результат, переводы, связь с обращением. (FS-TEL-05)
- **M-TEL-06 [MVP]** Исходящий вызов из карточки и ручной набор с нормализацией номера. (FS-TEL-02)
- **M-TEL-07 [MVP]** Музыка на удержании и в очереди; информирование о позиции в очереди — **[УПР]** (периодическое сообщение без точной позиции допустимо).
- **M-TEL-08 [УПР]** Нет свободных операторов / нерабочее время → голосовое сообщение клиента (запись) либо заказ обратного звонка; создаётся обращение-задача «перезвонить». (REQ-TEL-09, FS-TEL-06)
- **M-TEL-09 [MVP]** Автосообщение после разговора и CSAT-опрос по 5-балльной шкале через DTMF, оценка привязывается к обращению. Голосовой ответ — **[ПОЗЖЕ]**. (REQ-TEL-12/13)
- **M-TEL-10 [УПР]** Супервизор: прослушивание разговора; суфлирование и вмешательство — **[ПОЗЖЕ]** если не укладывается. (FS-QA-02)
- **M-TEL-11 [ПОЗЖЕ]** Кампании автообзвона, GSM-шлюзы/SIM-банки (подключаются как SIP-транк), запись экрана, транскрибация.

### 3.4 IVR (IVR) — «легко настраиваемая»
- **M-IVR-01 [MVP]** Визуальный конструктор сценариев в админке (граф из узлов со связями) без программирования. (REQ-ADM-01, FS-IVR-01)
- **M-IVR-02 [MVP]** Типы узлов MVP: «Проиграть сообщение», «Меню (DTMF)» с повтором/таймаутом/возвратом в предыдущее меню, «Проверка расписания», «Условие по переменной», «Поставить в очередь (тема/навык)», «Голосовое сообщение / заказ перезвона», «HTTP-запрос к внешней системе» (самообслуживание, напр. баланс) с сохранением ответа в переменные, «Проиграть значение переменной» (**[УПР]**: чтение чисел/сумм из заранее записанных фрагментов), «Перевод на номер», «CSAT-опрос», «Завершить». (REQ-TEL-07)
- **M-IVR-03 [MVP]** Многоуровневое меню (минимум 3 уровня тем), выход на оператора из любого уровня. (REQ-TEL-07)
- **M-IVR-04 [MVP]** Приветствия и сообщения: загрузка аудиофайлов; быстрое включение/выключение «информационного сообщения о сбое» менеджером без правки сценария (глобальные объявления с периодом действия). (REQ-TEL-05/06)
- **M-IVR-05 [MVP]** Расписания работы, праздничные дни, нерабочее время. (FS-IVR-02)
- **M-IVR-06 [MVP]** Версионирование сценариев: черновик → публикация; публикация атомарная, уже идущие вызовы доигрывают свою версию; откат на предыдущую версию; валидация графа перед публикацией.
- **M-IVR-07 [MVP]** Привязка сценария к номеру (DID) / точке входа.
- **M-IVR-08 [ПОЗЖЕ]** Голосовой ввод (ASR), синтез речи (TTS) on-premise. `[П]` в MVP только аудиофайлы (В-15).

### 3.5 Маршрутизация и очереди (RT) — едина для голоса и текста
- **M-RT-01 [MVP]** Очереди с параметрами: каналы, приоритет, лимиты, очередь по умолчанию для канала. (FS-RT-01)
- **M-RT-02 [MVP]** Навыки: оператору назначаются темы/навыки с уровнем; маршрутизация по теме из IVR/бота/правила. (REQ-RT-01, FS-RT-02)
- **M-RT-03 [MVP]** Стратегии: «дольше всех свободен» (least recent) и «наименьшая загрузка»; ёмкость оператора по типу канала. Round Robin/весовые — **[ПОЗЖЕ]** как дополнительные стратегии. (REQ-RT-02)
- **M-RT-04 [MVP]** Перелив: приоритетная группа → через таймаут резервная группа/общая очередь; эскалация по времени ожидания. (REQ-RT-03/04, FS-RT-03)
- **M-RT-05 [MVP]** Таймаут принятия оператором → возврат в очередь; ручное назначение супервизором. (FS-RT-03)
- **M-RT-06 [MVP]** Постобработка после обращения (настраиваемая длительность), затем автоматический «Готов». (FS-RT-04)
- **M-RT-07 [УПР]** Правила маршрутизации текста: канал/ключевые слова/регулярное выражение → очередь/приоритет/«срочное». (FS-RT-05)
- **M-RT-08 [УПР]** Приоритет по сегменту клиента (напр. B2B) внутри очереди. (REQ-RT-05)
- **M-RT-09 [ПОЗЖЕ]** Внешний маршрутизатор по API, SPQ/WFQ. (FS-RT-06)

### 3.6 Подсказки, автоответы, боты (AUTO) — всё настраивается
- **M-AUTO-01 [MVP]** Шаблоны ответов: личные/общие, по темам, с переменными (`{{client.name}}`), поиск, быстрый вызов по `/`. (REQ-AI-01, FS-AUTO-01)
- **M-AUTO-02 [MVP]** Автоответы по правилам: приветствие при первом сообщении, «вы в очереди», нерабочее время, ответ на ключевые слова; автозакрытие при молчании клиента с предупреждением. (FS-AUTO-01)
- **M-AUTO-03 [MVP]** Автоподсказки оператору (M-OP-10): встроенный провайдер — подбор шаблонов и статей базы знаний по тексту последних сообщений (полнотекстовый поиск PostgreSQL) и по теме обращения; дополнительные провайдеры подключаются через Assist API (3.10).
- **M-AUTO-04 [УПР]** Сценарный бот без кода для текстовых каналов (тот же движок графа, что и IVR): меню кнопками, сбор полей (форма до диалога), HTTP-запрос к внешней системе, перевод на оператора с историей. (REQ-AI-02/04, FS-AUTO-02)
- **M-AUTO-05 [MVP]** База знаний: статьи с рубриками (используется подсказками и позднее RAG).
- **M-AUTO-06 [ПОЗЖЕ]** Отложенные/повторные сообщения, генеративный бот по умолчанию.

### 3.7 Клиент, карточка обращения, темы (CARD)
- **M-CARD-01 [MVP]** Идентификация клиента по номеру телефона (АОН) / Telegram ID / email / токену приложения; объединение идентификаторов в одного клиента (ручное слияние дублей — **[УПР]**). (REQ-CRM-01, FS-TKT-03)
- **M-CARD-02 [MVP]** Автоподгрузка кросс-канальной истории при поступлении обращения. (REQ-CRM-02/04)
- **M-CARD-03 [MVP]** Классификатор тем до 3 уровней, редактируемый. (REQ-CRM-05)
- **M-CARD-04 [MVP]** Для каждой темы — набор настраиваемых полей карточки (тип, маска, список значений); обязательность полей задаётся отдельно для «закрытия» и для «передачи на 2-ю линию»; при закрытии 1-й линией достаточно темы, подтемы и контакта. (REQ-UI-03/04, REQ-ADM-03)
- **M-CARD-05 [MVP]** **Результат обработки** при сохранении обращения — из настраиваемого справочника, у каждого значения задан тип поведения. `[П]` Начальный набор (В-33):
  - «Решено на 1-й линии» — закрыть, CSAT;
  - «Передать на 2-ю линию» — форма выбора предприятия и подразделения, M-TKT-01;
  - «Не требует ответа» — спам, ошибочный звонок, благодарность; закрыть без CSAT;
  - «Отложено / перезвонить» — задача с датой и временем;
  - «Дубликат» — связать с существующим обращением и закрыть.

  (REQ-UI-05)
- **M-CARD-06 [MVP]** Теги (обязательный тег при закрытии — опция очереди).
- **M-CARD-08 [MVP]** В карточке обращения — предприятие, подразделение и объект (если применимо), отметка **«особо важное»**. Она ставится **автоматически**, если тема или подтема помечена особо важной (при смене темы автоматическая отметка пересчитывается). Оператор может поставить её вручную обращению или тикету по любой другой теме; ручная отметка сохраняется. Быстрый фильтр «Особо важные» — во всех списках и отчётах.
- **M-CARD-07 [УПР]** Панель внешних данных клиента: блок в карточке, заполняемый интеграционным коннектором (мок «CRM/бонусы/история заправок»). Реальные SAP/CRM — **[ПОЗЖЕ]**. (REQ-CRM-03)

### 3.8 Оргструктура, ответственность и вторая линия (ORG/TKT)
Процесс задан заказчиком (уточнение от 27.09.2026); в исходных документах его нет. Привязка «предприятие → подразделение → тема/подтема → сотрудник» — **сквозная**: она используется в правах доступа, маршрутизации тикетов, уведомлениях, интерфейсах, поиске и аналитике.

#### 3.8.1 Справочники и матрица ответственности (ORG)
- **M-ORG-01 [MVP]** Справочник «Предприятия»: название, код, активность, контакты по умолчанию.
- **M-ORG-02 [MVP]** Справочник «Подразделения» — **общий, не привязанный к предприятию**, и связь «подразделение на предприятии» (многие-ко-многим): одно подразделение добавляется сразу в несколько предприятий (мультивыбор). У связки свои атрибуты: активность, телефон/внутренний номер или очередь для прямого перевода звонка (M-TKT-11), email подразделения (необязательно).
- **M-ORG-03 [MVP]** Темы и подтемы (до 3 уровней) с отметкой **«особо важная»**. **Срок ответа второй линии:** глобальное значение по умолчанию — **15 календарных дней**; для отдельных тем и подтем можно задать свой срок по умолчанию (подтема наследует срок темы, если свой не задан). Оператор при передаче видит подставленный срок и может его изменить (M-TKT-01).
- **M-ORG-04 [MVP]** Единый справочник «Сотрудники» для всех ролей (операторы, ответственные, кураторы, супервизоры, администраторы): ФИО, **email** (обязателен для ответственных и кураторов), телефон, основное предприятие и подразделение. **У всех ответственных и кураторов обязательно есть вход в систему** — они закрывают тикеты в своём кабинете. Роли и права — атрибуты сотрудника, а не отдельные справочники.
- **M-ORG-05 [MVP]** **Матрица ответственности:** запись = предприятие × подразделение × тема или подтема × сотрудник × роль (**ответственный** / **куратор**). По одной комбинации может быть несколько ответственных и кураторов (обычно по одному). Привязка к теме действует на все её подтемы, пока для подтемы не задана своя, более точная. Матрица задаёт ответственных **по умолчанию**; оператор может изменить их для конкретного тикета (M-TKT-01). Нужны: массовое назначение (сотруднику сразу набор тем/предприятий), копирование назначений с одного предприятия на другое, отчёт «комбинации без ответственного».
- **M-ORG-06 [MVP]** Справочник «Объекты» (АЗС, ЭЗС и т.п.): предприятие, адрес, внешние идентификаторы, в том числе для площадок отзывов. **Источник — внешняя система заказчика, автоматическая синхронизация раз в день** (новые объекты добавляются, изменённые обновляются, исчезнувшие деактивируются; ручная правка синхронизируемых полей запрещена). Источник и формат интеграции уточняются (В-42). До подключения интеграции — импорт CSV. Используется для отзывов (M-CH-10) и обращений по конкретному объекту.
- **M-ORG-07 [MVP]** **Области видимости** для каждого сотрудника: администратор задаёт набор правил «предприятия × подразделения × темы» (каждое измерение — «все» или список). Правила определяют, какие обращения и тикеты сотрудник видит в списках, поиске, карточке клиента и отчётах. Роль задаёт набор действий. Ответственный или куратор всегда видит тикеты, на которые назначен, независимо от области. Для быстрой настройки — шаблоны областей. `[П]` Области действуют для всех ролей; операторам КЦ по умолчанию «всё» (В-34).
- **M-ORG-08 [MVP]** Изменения справочников, матрицы и областей — с историей в аудите. Удаление — это деактивация: история обращений и отчёты не ломаются.

#### 3.8.2 Вторая линия (TKT)
Уточнено заказчиком 27.09.2026: ответственный связывается с клиентом **вне системы** (городской телефон, электронная почта, официальное письмо и т.д.). Система не отправляет ответ клиенту, а фиксирует, как и что ответили, и контролирует срок и качество закрытия.

- **M-TKT-01 [MVP]** **Передача на 2-ю линию.** Если оператор не может закрыть обращение, он выбирает результат «Передать на 2-ю линию» (M-CARD-05), затем:
  - предприятие и подразделение; тема и подтема уже в карточке, их можно уточнить;
  - **ответственных и кураторов** — поля заполняются автоматически по матрице (M-ORG-05), но оператор может заменить или добавить людей для этого конкретного тикета;
  - **срок ответа** — подставляется по умолчанию (M-ORG-03), оператор может изменить.

  Проверяются обязательные поля «при передаче». **Без хотя бы одного ответственного тикет не сохраняется.** Передать можно только в активные связки «подразделение на предприятии» и по активным темам. Клиенту в текстовых каналах уходит настраиваемое автосообщение о передаче.
- **M-TKT-02 [MVP]** **Назначение и срок.** Тикет назначается всем выбранным ответственным и кураторам (M-TKT-01). Срок ответа хранится у тикета как дата. Признак «особо важное» переносится из обращения; оператор может выставить его вручную для тикета по любой теме (M-CARD-08).
- **M-TKT-03 [MVP]** **Статусы тикета:**
  - `Новый` (передан, ещё не открыт) → `В работе` → `На согласовании` (ответственный закрыл) → `Закрыт` (принят);
  - `На согласовании` → `На доработке` (возвращён с комментарием) → `В работе` → … до принятия.

  «Просрочен» — вычисляемый признак (с числом дней), а не статус. Все переходы, переадресации, изменения ответственных и срока, комментарии — в истории.
  - **Срок и «закрыто в срок»:**
    - срок истекает в конце дня (23:59, Europe/Minsk), дни календарные;
    - тикет «закрыт в срок», если последнее закрытие ответственным (то, после которого ответ приняли) произошло не позже срока;
    - время ожидания согласования в просрочку ответственного не засчитывается, оно учитывается отдельным показателем «ожидает согласования N дней»;
    - при переадресации и возврате на доработку срок не меняется.
  - **Несколько назначенных.** Действовать может любой назначенный ответственный или куратор. В работу тикет переводит первый открывший. Одновременные действия исключаются проверкой версии тикета: второй получает сообщение «тикет уже изменён». О возврате на доработку уведомляются все назначенные.
  - **Новые сообщения клиента** по обращению с открытым тикетом добавляются в обращение и видны в тикете, назначенным приходит уведомление в интерфейсе. В очередь 1-й линии такие сообщения не направляются.
- **M-TKT-04 [MVP]** **Email-уведомления с высоким приоритетом** (заголовки `Importance: High` / `X-Priority: 1`, «Важно!» в теме письма) ответственным и кураторам:
  - сразу при назначении, в том числе после переадресации или замены ответственного;
  - затем **ежедневно в 08:00, включая выходные**, отдельным письмом по каждому незакрытому тикету: «осталось N дней» или «просрочено на N дней»; время рассылки — настройка;
  - письма прекращаются, когда ответственный закрыл тикет (перевёл «На согласовании»), и возобновляются при возврате на доработку;
  - в письме: номер, тема/подтема, предприятие/подразделение, суть, контакты клиента, срок, ссылка в систему;
  - отправка через SMTP заказчика.
- **M-TKT-05 [MVP]** **Кабинет ответственного/куратора** — отдельный интерфейс, не такой, как у оператора (раздел того же веб-приложения):
  - список всех тикетов, где сотрудник ответственный или куратор, плюс видимые по его области;
  - понятные статусы, срок (осталось/просрочено, цветом), отметка «особо важное»;
  - тикеты, где сотрудник ответственный, **выделены**;
  - быстрые фильтры: «Я ответственный», «Я куратор», «Просроченные», «На доработке», «Особо важные»; фильтры по предприятию, подразделению, теме, статусу, сроку;
  - по клику — предпросмотр в части окна (суть, клиент и его контакты, срок, история) и полный переход в обращение: вся переписка, запись разговора, документы, история тикета.
- **M-TKT-06 [MVP]** **Переадресация** ответственным или куратором:
  - смена темы/подтемы, подразделения или предприятия — ответственные пересчитываются по матрице и их можно поправить вручную;
  - или выбор другого ответственного из списка (сотрудники с ролью «ответственный»).

  Комментарий обязателен `[П]`. Новые назначенные получают уведомление. `[П]` Переадресация в другое предприятие не ограничивается областью видимости переадресующего (В-40). Администратор может выполнить «применить матрицу к открытым тикетам» после изменения матрицы.
- **M-TKT-07 [MVP]** **Закрытие ответственным** после того, как он сам связался с клиентом. Обязательно указываются:
  - **способ ответа** — из справочника: «электронная почта», «мессенджер», «телефон», «письмо на бумаге», «не требует связи с клиентом»; справочник редактируемый;
  - **суть ответа** — текст;
  - **документы** — вложения, например скан официального письма.

  Затем тикет переходит в статус «На согласовании», согласующему приходит уведомление в интерфейсе и на email. Система ответ клиенту **не отправляет**.
- **M-TKT-08 [MVP]** **Согласование.** Согласующий проверяет, приложены ли нужные документы и понятно ли изложена суть ответа:
  - «Принять» → тикет `Закрыт`, обращение закрыто;
  - «Вернуть на доработку» → обязательный комментарий, возможны вложения, статус `На доработке`, ежедневные письма возобновляются, счётчик возвратов +1.

  Цикл повторяется до принятия. Пока тикет на согласовании, согласующему раз в день приходит напоминание.
- **M-TKT-09 [MVP]** **Кто согласует.** По умолчанию — оператор, создавший тикет (вкладка «На согласовании»); вместо него может согласовать его **заместитель** (назначает администратор или сам оператор на период отсутствия) или **супервизор**. **Супервизор видит все тикеты на согласовании** в пределах своей области (отдельный список). Правило «кто согласует» — настройка системы: «создатель тикета (+ заместитель и супервизор)» или «только супервизор». Переключить на второй вариант можно позже без доработки. Тикеты уволенного оператора на согласовании попадают супервизорам.
- **M-TKT-10 [MVP]** **Куратор** видит свои тикеты, получает уведомления и может делать всё, что ответственный: переадресовать, закрыть.
- **M-TKT-11 [MVP]** **Прямой перевод звонка** в срочном случае: во время разговора оператор переводит вызов на подразделение предприятия, слепо или с консультацией. Адресат задаётся в M-ORG-02: **внутренняя очередь** системы (например, техподдержка) **или внешний номер**. Перевод фиксируется в обращении событием с предприятием и подразделением и учитывается в отчёте по 2-й линии отдельной строкой («прямые переводы»).
- **M-TKT-12 [MVP]** Уведомления в интерфейсе (колокольчик, счётчики) обо всех событиях тикета для участников.
- **M-TKT-12a [MVP]** **Увольнение и деактивации.**
  - При деактивации сотрудника он исключается из назначений открытых тикетов и из рассылки.
  - Если у тикета не осталось активных ответственных, тикет пересчитывается по матрице. Если это не дало результата — назначается кураторам, а при их отсутствии попадает в отчёт «требуют переназначения» с уведомлением супервизорам.
  - При деактивации связки «подразделение на предприятии» или темы, по которым есть открытые тикеты, администратор получает предупреждение и список этих тикетов.
- **M-TKT-13 [ПОЗЖЕ]** Автоэскалация на куратора или руководителя при просрочке; ответ ответным письмом из почты прямо в тикет; уведомления в мессенджеры/SMS (В-38); клиентский портал; многоступенчатое согласование.

### 3.9 Аналитика (REP) — упрощённо
- **M-REP-01 [MVP]** Журнал событий обращений и вызовов (единый поток событий) — основа всех отчётов; хранится полностью, чтобы отчёты можно было доделать позже без переделки. (FS-LOG-03)
- **M-REP-02 [УПР]** Панель реального времени для супервизора: очереди (ожидают, макс. ожидание), операторы по статусам, активные обращения. (FS-REP-01)
- **M-REP-03 [УПР]** 7–9 табличных отчётов с выгрузкой CSV. Во всех — фильтры по периоду, каналу, **предприятию, подразделению, теме/подтеме, объекту**, оператору, ответственному/куратору и быстрый фильтр **«особо важные»**. Отчёты:
  - обращения по каналам, темам и результатам обработки;
  - SL и доля пропущенных;
  - ASA/AHT;
  - время первого ответа в чатах;
  - загрузка и статусы операторов;
  - CSAT;
  - **2-я линия по предприятиям и подразделениям:** поступило, закрыто в срок, просрочено (с числом дней), возвраты на доработку, среднее время решения, ожидание согласования, способы ответа, прямые переводы, в разрезе ответственных и кураторов;
  - **реестр просроченных тикетов**;
  - отзывы с карт по объектам.

  Данные в отчётах ограничены областью видимости пользователя (M-ORG-07). (REQ-REP-01..03, FS-REP-02)
- **M-REP-04 [ПОЗЖЕ]** Конструктор отчётов, BI (Superset/Metabase на реплике), рассылка отчётов, речевая аналитика. (REQ-REP-04, REQ-QA-02..06)

### 3.10 Точки расширения: ИИ и внешние системы (INT/AI)
- **M-INT-01 [MVP]** Публичный REST API (OpenAPI-описание, версия в пути `/api/v1`), ключи API с правами. (REQ-INT-04/06, FS-INT-01)
- **M-INT-02 [MVP]** Исходящие webhooks: подписка на типы событий, несколько получателей, подпись HMAC, повторы с экспоненциальной задержкой, журнал доставки, кнопка «тест»; сбой получателя не влияет на работу операторов. (REQ-INT-05, FS-INT-01)
- **M-INT-03 [MVP]** Интеграционные коннекторы (самообслуживание): в админке описывается HTTP-операция внешней системы (URL, метод, авторизация, маппинг входа/выхода, таймаут, фолбэк) и используется из IVR, бота и карточки клиента. Демонстрация: мок-сервис «баланс бонусного счёта / топливной карты». (Промпт; REQ-INT-01..03 — **[ПОЗЖЕ]** реальные SAP/CRM)
- **M-AI-01 [MVP]** Assist API — контракт подключения ИИ-провайдера подсказок/черновиков ответа: система отправляет контекст обращения, провайдер возвращает подсказки; таймаут, фолбэк на встроенный провайдер, выключатель без перезапуска. Встроенный адаптер к OpenAI-совместимому API (локальный vLLM/Ollama и т.п.) — **[УПР]**, выключен по умолчанию. `[П]` облачные LLM запрещены по умолчанию (В-05). (FS-AI-01/02, REQ-SEC-01)
- **M-AI-02 [MVP]** Bot Gateway — контракт подключения внешнего бота к текстовому каналу (обращение отдаётся боту, бот может ответить, запросить перевод на оператора). (FS-AI-03)
- **M-AI-03 [MVP]** Analysis hook — асинхронная обработка завершённых обращений внешним анализатором (подписка на событие `conversation.closed`/`recording.ready`, запись результата обратно через API в поля/теги). Реализация анализаторов (транскрибация, резюме, тональность, NLP-автозаполнение) — **[ПОЗЖЕ]**. (REQ-AI-05..08)
- **M-AI-04 [ПОЗЖЕ]** RAG по базе знаний (pgvector), MCP-сервер для ИИ-агентов, учёт расходов на ИИ. (REQ-AI-03, FS-AI-04/05)

### 3.11 Администрирование (ADM)
- **M-ADM-01 [MVP]** Сотрудники (M-ORG-04): создание, блокировка, увольнение (с обезличиванием — **[УПР]**; тикеты уволенного — по M-TKT-12a), роли, очереди, навыки, лимиты, основное предприятие и подразделение. (FS-ADM-01)
- **M-ADM-02 [MVP]** Права = **роль** (набор действий: оператор, ответственный/куратор, супервизор, администратор; у одного сотрудника может быть несколько ролей) + **область видимости** (M-ORG-07). Права задаются индивидуально каждому сотруднику, шаблоны ускоряют настройку. (FS-ADM-02)
- **M-ADM-03 [MVP]** Справочники: предприятия, подразделения (и их связи с предприятиями), темы/подтемы с полями, сроками и отметкой важности, объекты, матрица ответственности, результаты обработки, теги, причины перерывов, навыки, расписания. (FS-ADM-03)
- **M-ADM-04 [MVP]** Все настройки (каналы, очереди, IVR, шаблоны, правила, интеграции) применяются «на лету» без перезапуска компонентов.
- **M-ADM-05 [MVP]** Экспорт/импорт конфигурации (JSON) — для переноса между стендами и отсутствия vendor lock-in. (REQ-INT-06)

## 4. Нефункциональные требования

### 4.1 Обновления без остановки (ключевое требование заказчика) — M-UPD
- **M-UPD-01 [MVP]** Обновление любого прикладного сервиса (API, realtime-шлюз, маршрутизатор, коннекторы, обработчики, веб-интерфейс, call-control) выполняется поэтапно без остановки приёма и обработки обращений: не теряются сообщения, не обрываются установленные звонки, операторы не выходят из системы (допускается автоматическое переподключение WebSocket ≤ 5 с без потери состояния).
- **M-UPD-02 [MVP]** Обновление медиасервера (Asterisk) — через «осушение» узла: новые вызовы идут на другой узел, текущие разговоры доживают на старом; ни один установленный разговор не обрывается.
- **M-UPD-03 [MVP]** Миграции БД — только обратно совместимые (expand/contract), чтобы старая и новая версии работали одновременно.
- **M-UPD-04 [MVP]** Компоненты, которые не могут обновляться без эффекта для пользователей, перечислены явно с описанием эффекта и процедуры (02, разд. 6.5); для них — плановое окно и эффект ≤ 60 с (подтверждено заказчиком, В-09).
- **M-UPD-05 [MVP]** Изменения конфигурации (IVR, очереди, шаблоны, каналы) — вообще не требуют перезапуска.
- **M-UPD-06 [MVP]** Автоматизированная проверка: сценарий «обновление под нагрузкой» (идущие звонки и чаты во время поэтапного обновления) входит в приёмку MVP.

### 4.2 Прочие
- **M-NFR-01 [MVP]** Развёртывание на своём сервере/локально одной командой (Docker Compose); только открытое ПО; без обращения к публичным облакам (кроме самих внешних каналов — Telegram, API Rocket Data для отзывов (В-32) — и облачной LLM, только с явного разрешения администратора, В-05). (REQ-SEC-01, FS-ARCH-03)
- **M-NFR-02 [MVP]** Браузеры: **Google Chrome, Яндекс Браузер, Microsoft Edge** (последние версии; все на движке Chromium) — полная поддержка, включая WebHID; WebHID в Яндекс Браузере проверяется в Ф5. Firefox и Safari официально не поддерживаются. (В-08)
- **M-NFR-03 [MVP]** Безопасность: TLS снаружи и для WebRTC; пароли argon2, блокировка после неудачных попыток; проверка прав на сервере; неизменяемый журнал аудита административных действий и доступа к записям. 2FA для админов — **[УПР]**. SSO/AD — **[ПОЗЖЕ]** (В-12). (REQ-SEC-02/03, FS-SEC-01, FS-LOG-01)
- **M-NFR-04 [MVP]** Наблюдаемость: JSON-логи с correlation-id, метрики Prometheus, health/readiness-эндпоинты у всех сервисов. (FS-LOG-02)
- **M-NFR-05 [УПР]** Масштаб демонстрации: 10 одновременных операторов, 30 одновременных вызовов, 100 одновременных чатов на одном сервере; архитектура — горизонтально масштабируемая (рост до 50+ операторов без смены архитектуры). (REQ-TEL-14, REQ-OPS-03)
- **M-NFR-06 [УПР]** Резервное копирование БД и объектного хранилища (скрипт + инструкция). PITR, кластер PostgreSQL — **[ПОЗЖЕ]**. (REQ-OPS-04)
- **M-NFR-07 [УПР]** ПДн: согласие на обработку в веб-чате (текст с версией, фиксация факта); маскирование ПДн в логах; срок хранения записей настраивается. (FS-PD-01/02, REQ-SEC-04, В-11, В-16)

## 5. Сквозные демо-сценарии (критерии приёмки MVP)

1. **Звонок:** клиент звонит (демо-страница/SIP) → IVR: приветствие + объявление о сбое → меню «Бонусная программа → Баланс» → HTTP-запрос к мок-сервису → озвучен баланс → «0» — оператор → очередь по навыку → оператор отвечает на гарнитуре → видит карточку и историю → удержание, перевод → завершение → CSAT (DTMF) → запись доступна в карточке.
2. **Чат на сайте:** клиент пишет в виджет → автоответ + бот собирает телефон → перевод на оператора → оператору показаны подсказки (шаблон и статья БЗ) → ответ одним кликом → закрытие с темой → оценка.
3. **Telegram и email:** сообщения попадают в ту же очередь; клиент, писавший ранее в чат и звонивший, узнаётся — история едина.
4. **2-я линия:**
   - администратор заводит предприятие, добавляет одно подразделение сразу в два предприятия, назначает по матрице ответственного и куратора на подтему, задаёт для подтемы срок 10 дней (глобальный — 15);
   - оператор по звонку выбирает результат «Передать на 2-ю линию», предприятие и подразделение → ответственный, куратор и срок подставились, оператор меняет ответственного на другого → назначенным приходит письмо «Важно!»;
   - на следующий день в 08:00 приходит письмо «осталось N дней», после срока — «просрочено на N дней» (проверяется в тесте с подменой системного времени);
   - ответственный видит тикет выделенным в своём кабинете (фильтр «Я ответственный») и переадресует его другому ответственному сменой подразделения;
   - новый ответственный связывается с клиентом вне системы и закрывает тикет: способ ответа «письмо на бумаге», суть ответа, скан письма → оператор **возвращает на доработку** («нет подписи на письме») → ответственный прикладывает документ и закрывает повторно → оператор **принимает** → тикет и обращение закрыты;
   - супервизор видит этот тикет в списке всех согласований; история, сроки и способ ответа видны, отчёт по 2-й линии показывает возврат и просрочку.
5. **Настройка без программирования:** администратор меняет пункт IVR и публикует; добавляет шаблон, правило автоответа, тему с полями, новый Telegram-бот — всё работает без перезапуска.
6. **Обновление без простоя:** во время идущих звонков и чатов выполняется поэтапное обновление всех прикладных сервисов и одного медиаузла; ни один разговор не обрывается, ни одно сообщение не теряется (подтверждается автотестом).
7. **Отчёты:** супервизор видит панель реального времени и выгружает базовые отчёты в CSV.
8. **Интеграции:** внешняя система получает webhook о закрытии обращения и записывает результат «анализа» в поле обращения через API; включённый адаптер LLM (локальный OpenAI-совместимый сервер) даёт оператору черновик ответа.
9. **Права и важность:** сотрудник с областью «предприятие А, темы X» не видит обращений предприятия Б ни в списках, ни в поиске, ни в отчётах; обращение по особо важной подтеме автоматически помечено и находится быстрым фильтром.
10. **Отзывы с карт (Ф13):** отзыв из Rocket Data по объекту становится обращением нужного предприятия, обрабатывается и передаётся на 2-ю линию как обычное; ответ на отзыв уходит в Rocket Data по API.
