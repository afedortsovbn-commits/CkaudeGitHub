# 04. Открытые вопросы к заказчику

Вопросы не блокируют работу: для каждого принято **решение по умолчанию**, и планы 01–03 опираются на него. Если заказчик решит иначе, в колонке «Что изменится» указано, что придётся поправить.
Ссылки из других документов — по номеру `В-NN`.

## Продукт и объём

| № | Вопрос | Решение по умолчанию (предположение) | Что изменится при другом ответе |
|---|---|---|---|
| В-01 | Делаем универсальный продукт или решение под конкретного заказчика из ТЗ (сеть АЗС/ЭЗС, РБ)? | Универсальный продукт; домен АЗС/ЭЗС — только демо-данные (темы, мок самообслуживания) | Под конкретного заказчика — приоритет интеграций SAP/CRM (REQ-INT-01..03) выше, отдельная фаза |
| В-02 | Какой мессенджер первым? Нужны ли WhatsApp/Viber/VK/MAX в MVP? | Telegram в MVP; остальные — коннекторами после MVP | +1 фаза на каждый канал (≈ S–M), архитектура не меняется |
| В-13 | Языки интерфейса | Русский; строки через i18n | Добавление языка — перевод ресурсов |
| В-16 | Глубина функций ПДн (согласия, обезличивание, сроки) в MVP | Упрощённо (M-NFR-07): согласие в виджете с версией текста, маскирование в логах, настраиваемый срок хранения записей | Полный реестр согласий, API согласий — отдельная задача |

## Вторая линия

| № | Вопрос | Решение по умолчанию | Что изменится |
|---|---|---|---|
| В-03 | Кто согласует закрытие тикета, предложенное 2-й линией? | Оператор 1-й линии — владелец исходного обращения; если он недоступен — любой оператор очереди-владельца или супервизор | Если согласует супервизор/сам клиент — меняются права и уведомления в Ф8; при подтверждении клиентом — нужен механизм запроса подтверждения в канале |
| В-04 | Кто сообщает клиенту о решении? Может ли 2-я линия отвечать клиенту напрямую? | Ответ клиенту отправляет 1-я линия после согласования (текст — черновиком из решения, голос — задача «перезвонить»); прямой ответ 2-й линии — после MVP | Прямой ответ 2-й линии — доработка Ф8 (публичные комментарии уходят в канал клиента) |
| В-10 | Нужны ли многоуровневые согласования/исполнители вне КЦ (другие службы компании)? | Нет, одна группа 2-й линии на тему; «другие службы» заводятся как группы 2-й линии с пользователями системы | Внешние исполнители без учётной записи — email-интеграция тикетов |

## Телефония и гарнитуры

| № | Вопрос | Решение по умолчанию | Что изменится |
|---|---|---|---|
| В-06 | Есть ли тестовый SIP-транк оператора связи для демонстрации? | Нет; демо через WebRTC-страницу «Позвонить в КЦ» и SIPp; подключение транка — конфигурацией Kamailio | При наличии транка — добавить его настройки и проверить кодеки/DTMF (RFC 2833/4733) |
| В-07 | Какие модели гарнитур у операторов (для проверки кнопок через WebHID)? | Проверяем на доступной модели со стандартной HID Telephony usage page (Jabra/Poly — типичные); вендорные SDK — после MVP | Если модели без стандартной HID-поддержки — вендорный SDK/драйвер, отдельная задача |
| В-08 | Какие браузеры у операторов? | Chrome/Edge последних версий — полная поддержка; Firefox — без WebHID (выбор устройства вывода поддерживается с Firefox 116) | Safari как основной — нет setSinkId и WebHID; Firefox — нет WebHID; нужна отдельная проверка |
| В-15 | Нужны ли в MVP синтез (TTS) и распознавание (ASR) речи для IVR? | Нет; только загружаемые аудиофайлы и сборка чисел из фрагментов; TTS/ASR on-premise — после MVP | Выбор движка (напр. открытые RHVoice/Vosk/Whisper), доп. узлы IVR |
| В-11 | Сроки хранения записей разговоров и переписки | Настраиваемые; по умолчанию записи — 180 дней, переписка — бессрочно | Только значения настроек |

## Обновления и эксплуатация

| № | Вопрос | Решение по умолчанию | Что изменится |
|---|---|---|---|
| В-09 | Допустимо ли плановое окно для редких обновлений «класса C» (Kamailio, Traefik, PostgreSQL, MinIO — 02, 6.5) с эффектом ≤ 60 с: не принимаются новые вызовы/подключения, для идущих разговоров кратко недоступны удержание/перевод? | Да, в период низкой нагрузки; идущие разговоры не прерываются (coturn в MVP — 2 экземпляра, обновляется без окна) | Если недопустимо даже это — HA-пары Kamailio/Traefik (keepalived), Patroni, распределённый MinIO переносятся в MVP (+1 фаза, ≈ M–L, и минимум 2–3 сервера для демонстрации) |
| В-14 | Демонстрация MVP на одном сервере достаточна? | Да: дублирование прикладных сервисов и 2 узла Asterisk на одном сервере; многосерверное развёртывание — после MVP | Многосерверная демонстрация — сетевые настройки, TLS между узлами, общий доступ к записям |
| В-18 | Есть ли требования к мониторингу/SIEM заказчика (формат логов, куда отправлять)? | JSON-логи + Prometheus/Grafana/Loki в профиле `observability` | Экспорт в SIEM по syslog — небольшая доработка |

## ИИ, интеграции, безопасность

| № | Вопрос | Решение по умолчанию | Что изменится |
|---|---|---|---|
| В-05 | Допустимы ли облачные LLM (с передачей данных наружу) или только локальные? | Только локальные (ТЗ: строго on-premise); адаптер к OpenAI-совместимому API позволит подключить любой, облачный — только с явного разрешения администратора | Ничего в архитектуре; при запрете на уровне политики — блокировка внешних адресов в настройках |
| В-19 | Какую LLM и на каком оборудовании заказчик планирует для подсказок/ботов? | Не выбираем в MVP; тестируем с мок-сервером и, при наличии, локальной моделью через vLLM/Ollama | Выбор модели влияет на качество подсказок и промпты, не на архитектуру |
| В-12 | Нужна ли в MVP аутентификация через AD/SSO? | Нет; встроенные учётные записи; абстракция готова к OIDC (Keycloak) | +задача в Ф12 или отдельная фаза (Keycloak + сопоставление групп AD ролям) |
| В-20 | Какие внешние системы самообслуживания подключать первыми (баланс бонусного счёта, топливная карта, статус ЭЗС…), есть ли их API? | Мок-сервис с балансом и историей операций; реальные — после MVP через интеграционные операции | Для каждой реальной системы — описание операции в админке (без кода), если API — REST/JSON; SOAP/ESB — коннектор |
| В-17 | Планируется ли распространять продукт третьим лицам (коммерчески)? Влияет на лицензирование компонентов (Asterisk, Kamailio — GPL) | Используем как отдельные немодифицированные процессы — это совместимо с любым вариантом распространения нашего кода; окончательную оценку должен дать юрист | При модификации GPL-компонентов — публикация изменений; при несогласии — замена компонентов (сложно) |
| В-21 | Где должен жить код и как ведётся разработка (ветки, ревью)? | Код в `mvp/` этого репозитория; каждая фаза — ветка и PR в `main` | Другая схема — только правило в 03, разд. 1 |
